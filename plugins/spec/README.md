# spec (v0.4.0)

아이디어의 확정 정도에 맞는 무게의 계획 문서를 만들고, 독립 콜드 리더의 병렬 읽기로 그 문서를 측정하는 관문까지 — 작성과 검증을 한 쌍으로 묶은 플러그인.

**분업 원칙**: 의도는 문서에 산다(코드 조사는 작성자가 원한 것을 복원할 수 없다). 세계 상태는 코드에 산다(문서의 사본은 쓰는 순간부터 낡는다). 방법은 구현자의 것이다. 스펙은 "코드를 안 봐도 되게 하는 문서"가 아니라 **모든 의도 결정을 작성자에게 안 물어도 되게 하는 문서**다.

| 명령 | 하는 일 |
|---|---|
| `/spec:spec` | 확정 정도에 따라 세 모드로 갈라진다. **explore**: 무엇을 만들지 아직 탐색 중(후보 비교·UI 실험·MVP 프로브)이면 질문 1~3개로 가벼운 탐색 브리프(BRIEF.md)만 만든다 — 풀 스펙 없음, 게이트 없음. **feature/system(계약 모드)**: 방향이 정해진 작업은 인터뷰(질문마다 blocking test 통과 필수, 정량화는 숫자가 일하는 곳에만)로 구현 계약(SPEC.md)을 만들고, 완성되면 관문이 자동 발동. 스펙에는 Implementation Authority & Escalation 핸드오프 블록이 포함된다 |
| `/spec:spec-gate` | 콜드 리더 N명(기본 3, 무맥락·무도구, 1명은 적대 프레이밍으로 동의-편향 상관 완화)을 워크플로우 하나로 병렬 실행 — 출력은 schema로 강제, 2표 이상 겹침(앵커+범주 일치)은 스크립트가 셈. 판정 4종: **blocking**(통과 조건: 확정 0), **discretionary**(구현자 재량), **experimental**(실험이 답함 → Resolved by Experiment), **stale-assumption**(작성 시점 세계-상태 사실 → Context Snapshot 이동). 2라운드 후에도 blocking이 남으면 맹목 반복 대신 구조 진단(계속/분리/explore 강등/실험 이관)을 먼저 제시 |

**게이트가 재는 것과 안 재는 것 (G-15)**: 게이트는 **결정가능성**(구현자가 문서만으로 결정할 수 있는가)을 잰다. **바람직함**(옳은 제품인가)은 재지 않는다 — 모호하지 않게 명세된 틀린 제품은 만점으로 통과한다. `passed`는 "이 모델 계열의 콜드 리더 N명에게 보이는 모호성이 남지 않았다"는 바닥 보증이지 완전성 인증서가 아니다.

**의도 vs 세계-상태**: SPEC.md는 의도·경계·완료 기준의 단일 원천이다. 현재 코드 상태에 대한 사실(사전조사 file:line 인용)은 비규범 Context Snapshot 섹션에 격리되고, 실행 시 코드와 테스트에서 재확인한다 — 스냅숏과 코드가 어긋나면 낡은 건 스냅숏이지 코드가 스펙을 위반한 게 아니다.

**출력 위치**: `/spec`은 프로젝트 루트에 `SPEC.md`(계약 모드) 또는 `BRIEF.md`(explore 모드)를 만든다 — 커밋되는 단일 원천이며, `specs/NNN-slug/` 번호 디렉터리는 쓰지 않는다. 대시보드·게이트 리포트 같은 도구 상태는 루트의 `.spec/`에 두며, 이 디렉터리는 `*` 한 줄짜리 `.spec/.gitignore`로 스스로를 무시해 그 안의 무엇도 커밋되지 않는다(사용자의 루트 .gitignore는 건드리지 않는다). 이미 `SPEC.md`가 있으면 충돌이 아니라 개정 입력으로 삼는다 — 무시하고 새로 쓰는 건 명시적 확인이 있을 때만.

**explore → contract 승격 경로**: 후보를 만들고 고른 뒤 /spec을 다시 실행하면 계약 모드로 승격된다. BRIEF의 Hard Constraints는 그대로 계승, 선택된 후보의 특성이 인터뷰 재료가 되고, Open Questions는 실험 결과라는 증거와 함께 Decision Ledger에 착지한다 — 스펙은 예측이 아니라 살아남은 것의 성문화로 작성된다.

- salvo와의 관계: spec-gate는 메커니즘상 vote 병합 측정(독립 판독 N개를 코드가 2표 이상으로 집계)이며, 나중에 salvo 플랫폼의 preset으로 재등록될 예정이다. 지금은 별개 제품이라 독립 플러그인으로 분리했다.

## v0.4.0 변경 이력

2026-07-11, Codex 0.2.0 리뷰의 잔여 지적 반영 (0.3.0과 같은 날):

1. **정체성 문장 교체** — "문서만 읽고 구현할 수 있는 스펙" → "의도·경계·완료 기준은 문서에서, 세계 상태는 코드 재조사로, 방법은 자율로". 게이트의 문서-단독 판독은 유지(의도의 결정가능성 측정이 목적이므로)
2. **Implementation Authority & Escalation** — 스펙 말미 핸드오프 정책 블록(필수): 문서의 권위 범위, 재조사 의무, 코드 참조=증거, 에스컬레이션 조건 목록
3. **시스템 템플릿 조건부화** — Domain/State/Event Flow/Error Taxonomy에 포함 조건 명시, 생략 시 한 줄 사유
4. **stale-assumption 판정** — 세계-상태 사실에 기댄 규범 조항을 제4 판정으로 분리(앵커 단독 집계), Context Snapshot 이동 라우팅
5. **질문 전 blocking test** — 물어볼 가치 판정(관찰 가능 결과/경계 변경? 구현자 결정 불가? 실험보다 확정이 낫나? 변경 비용?)을 통과한 질문만 인터뷰에 올림
6. **정량화 조건화** — 숫자가 일하는 곳(합격·안전·비용·성능)에만; 탐색적 UX·취향의 거짓 정밀도 금지
7. **라운드 진단 (G-8 개정)** — 상한은 여전히 없지만 3라운드부터는 구조 진단(계속/서브스펙 분리/explore 강등/실험 이관)을 먼저 제시
8. **description 부정 트리거** — 일회성 프로토타입·단순 로컬 변경엔 계획 문서 자체가 불필요함을 명시

## v0.3.0 변경 이력

2026-07-11, Codex 세션 크리틱 + 4-에이전트 무맥락 탐구(신뢰 접지·의도 커널·합의 공격·극한 분석)에서 도출:

1. **Explore 모드** — 탐색 단계 작업을 풀 스펙 인터뷰로 끌고 가지 않는다. 구현 전 조기 확정은 후보 다양성을 붕괴시키고(수렴), 내성으로 답한 결정은 편향이라 반복해도 안 씻긴다(조우 부재)
2. **EXPERIMENTAL 판정** — "실험으로 답할 질문"을 blocking도 discretionary도 아닌 제3의 판정으로 분리. 사전 결정 강요는 추측을 계약에 굽는 행위
3. **프레이밍 회전 (G-14)** — 같은 모델 계열 리더 N명의 합의는 공유 맹점에 무력하므로, 1명에게 적대 프레이밍을 부여해 동의-편향 상관을 깬다. ≥2표 규칙이 오탐을 막으므로 집계는 불변
4. **보증 범위 명시 (G-15)** — 게이트는 결정가능성만 잰다는 사실을 문서·리포트에 명시. "게이트 통과"가 실제 의미보다 큰 보증으로 읽히는 것을 차단
5. **Context Snapshot 분리** — 사전조사 코드 사실을 계약 본문에서 비규범 섹션으로 격리, 실행 시 재확인 의무화. 기록된 코드 사실은 쓰는 순간부터 낡는다
6. **Decision Ledger 기입 기준** — 전 결정 기록에서 "되돌리기 비싼 결정만"으로. 모든 것을 기록하는 원장은 아무도 읽지 않는 침전물이 된다
