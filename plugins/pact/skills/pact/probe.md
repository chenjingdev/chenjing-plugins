# probe — 무엇을 만들지 계약하기

목표는 사용자가 처음부터 생각하지 못한 것까지 짚어서, 다 만든 뒤에야 보이는 문제를 줄이는 것이다. 결과물은 한 화면 분량의 명세 하나와 사용자의 승인 한 번이다.

## 1. 대화

**첫 메시지**는 두 가지가 전부다.
1. 질문을 건너뛰고 바로 명세 초안으로 가도 된다는 한 줄. 만들기 전에 명세 승인은 한 번 받는다는 것도 같이 말한다. 사용자가 그러자고 하면 대화를 끝내고, 지금까지 들은 것으로 명세를 써서(아래 4) 검수로 간다.
2. 실제 장면을 묻는 열린 질문 하나. 물음표는 하나다. 예: "이게 있었으면 좋겠다고 느낀 마지막 순간이 언제였어요?"

**그다음 대화**
- 한 메시지에 질문 하나만 한다. 물음표는 하나다. "언제였어요? 그때 뭐가 번거로웠나요?"처럼 덧붙인 물음도 질문 하나로 센다. 질문 뒤에 예시 답 목록을 붙이지 않는다. 사용자의 말에 담긴 의도가 당신의 선택지보다 정확하다.
- 사용자가 막히거나 "어떻게 생각해?"라고 하면 기준안이나 구체적인 예시를 먼저 내놓고 고치게 한다. 빈칸으로 다시 묻지 않는다.
- 추측은 추측이라고 표시한다("짐작인데, X 때문에 자주 막히시는 거죠?"). 사용자가 직접 말한 것만 `[사용자]`로 적는다. 당신이 채운 것은 `[AI 가정]`이다.
- 자료(회의록, 기존 문서, 코드)를 근거로 결론을 낼 때는 그 자료가 왜 그런 모양인지 확인한다. 정책 이야기만 나온 회의록은 기능이 이미 잘 정해져 있었기 때문일 수 있다.
- 쉬운 말을 쓰고 절차 용어를 쓰지 않는다.

**짚을 곳**은 기능과 정책 둘 다다.
- 기능: 누가 쓰나, 언제 쓰나, 무엇이 되면 성공인가, 하지 않을 것은 무엇인가. 바이브 코딩에서는 기능도 바꿀 수 있으니, 빼거나 바꾸는 편이 낫겠다는 제안도 당신의 일이다.
- 정책 점검 목록: 데이터 보관 기간, 누가 무엇을 보는가(권한, 마스킹), 접근 기록, 예외 상황, 시스템 경계(어디까지가 이 시스템의 일인가), 기존 규칙 따르기, 용어 해석 차이. 이 목록을 질문으로 읽어 주지 않는다. 대화에서 빈 곳을 찾는 데 쓴다.

질문이 다섯 개쯤 되면 "이 정도면 정리해도 될까요?"를 한 번 제안한다. 그다음은 사용자가 정한다.

## 2. 기능 고정

기능은 말로 정하고, 구조는 보고 정한다. 기능 범위는 질문 여러 개 대신 체크리스트 한 장으로 받는다.

1. 주제가 정해졌으면 명세 파일을 만든다: `node <pact>/scripts/spec.mjs new <프로젝트> <주제>`. 출력된 경로가 이번 명세다. 실행 폴더는 `node <pact>/scripts/spec.mjs run-dir <명세>`로 만든다(`.pact/<slug>/`, git에 안 올라간다).
2. 항목 JSON을 쓴다: `{"title": "<주제>", "items": [{"label": "…", "note": "…"}, {"label": "…", "suggested": true, "reason": "…"}]}`. 대화에서 짐작한 기능은 그냥 두고(체크됨), 당신이 더하자고 하는 기능은 `suggested`와 한 줄 이유를 단다(체크 해제, `(제안)` 표시).
3. `node <pact>/scripts/checklist.mjs render <items.json> <run-dir>`
4. `node <pact>/scripts/checklist.mjs serve <run-dir>`를 백그라운드로 실행하고, 출력된 `페이지: http://127.0.0.1:<포트>/`를 `open`으로 연다. 채팅에는 페이지에서 고르거나 채팅으로 답해도 된다고 한 줄 알린다.
5. 서버가 끝나면 `<run-dir>/checklist.txt`의 `기능: …` 줄이 답이다. 시간 초과로 끝났으면 채팅으로 받는다.
6. 채팅 답이 페이지보다 우선한다. 채팅으로 먼저 답이 오면 서버를 멈춘다.

## 3. 구조 고르기

화면이 있을 때만 한다. 화면이 없으면 건너뛴다.

1. 구조의 축 하나를 고른다. 예: 첫 화면에 무엇이 오나, 이동 방식, 주 동작이 무엇인가.
2. 기능은 같고 구조만 다른 저충실도 스케치 2~3장을 `<run-dir>/sketches/<A|B|C>.html`로 그린다. 장식 없이 구조만 보이게 한다.
3. `<run-dir>/sketches.json`(`{"title", "axis", "sketches": [{"key": "A", "caption": "…", "file": "sketches/A.html"}]}`)을 쓰고 `node <pact>/scripts/gallery.mjs <run-dir>`로 갤러리를 만들어 `open`으로 연다.
4. 판정 질문 하나를 한다: 어느 쪽이 맞는지, 섞을 부분이 있는지.
5. "전부 아님"이면 가장 어긋난 지점을 한 번 묻고 2라운드를 그린다. 라운드는 최대 2번이다. 2라운드에서도 정해지지 않으면 가장 가까운 것을 고르고 남은 차이를 `## 확인 필요`에 적는다.
6. 고른 스케치와 판정을 명세 `## 구조 판정`에 적는다. 고른 스케치 파일만 남기고 나머지 스케치 파일은 지운다. build는 판정과 고른 스케치를 입력으로 처음부터 짓는다. 스케치 코드를 그대로 쓰지 않는다.

## 4. 명세 작성

2에서 만든 명세 파일을 채운다. 아직 없으면(질문을 건너뛴 경우) `spec.mjs new`로 만든다. 형식은 `spec-template.md`를 따른다.
- 한 화면에 들어오게 쓴다. 펼친 부분은 40줄 안이다(frontmatter 포함, `<details>` 안은 빼고 센다). 길어지면 사용자가 꼭 봐야 할 것을 위로 올리고 나머지를 접는다.
- 기능은 `- F<n> <한 줄> [사용자]` 또는 `[AI 가정]`. 기능마다 예외 상황을 `  - 케이스: <발생 조건> → <표시·동작>`으로 단다. 케이스는 기능마다 두 개까지, 결과를 바꾸는 것만 펼친다.
- 여러 기능에 반복되는 결정은 `## 공통 규칙`에 `- R<n>`으로 한 번만 적는다.
- 펼쳐 두는 `[AI 가정]` 항목은 5개까지다. 결과를 바꿀 만한 것만 펼치고, 나머지 가정과 케이스는 섹션 끝의 `<details><summary>그 밖의 AI 가정 n개</summary>` … `</details>`에 넣는다. 접은 항목도 `- F<n>`/`- R<n>` 형식과 태그를 그대로 쓴다.
- `## 확인 필요`에는 결과를 바꾸는 것만 적는다.

쓴 뒤 `node <pact>/scripts/spec.mjs lint <명세>`가 아무것도 출력하지 않아야 한다. 출력이 있으면 고친다.

## 5. 명세 검수

명세를 쓴 대화와 떨어진 눈으로 본다. 기획자가 RFP를 쓴 사람이 아니었던 것처럼.

1. `pact:spec-checker`를 부른다. 명세 경로, 대화에서 `[사용자]`로 적은 요구 목록, 프로젝트 경로를 넘긴다.
2. 돌아온 세 무더기를 반영한다.
   - 이미 답이 있음: 명세에 채운다.
   - 사소함 — AI가 정함: 정하고 `[AI 가정]`으로 적는다.
   - 사용자만 답할 수 있음: 한 메시지에 중요한 순서로, 질문마다 기본안을 붙여 묻는다. 질문 라운드는 이것 한 번뿐이다.
3. 답을 반영하고 lint를 다시 돌린다. 검수를 반영한 뒤에도 4의 크기 기준(펼친 40줄, 펼친 `[AI 가정]` 5개)을 지킨다. 새로 정한 사소한 것은 접힌 칸에 넣는다.
4. 명세 경로와 당신이 정한 `[AI 가정]` 중 결과를 바꿀 만한 것을 짧게 보이고 승인을 한 번 받는다. pact 전체에서 받는 승인은 이것 하나다. 승인을 묻는 메시지는 그 질문 하나로 끝낸다.
5. 승인되면 `node <pact>/scripts/spec.mjs set-status <명세> approved`.

**위임은 승인이 아니다.** "알아서 해", "네가 정해", "몰라", "기본안대로"는 앞 질문의 답이다. 그 답으로 명세를 채우고, 그다음 4의 승인 질문을 따로 한다. 승인은 명세 경로와 요지를 본 뒤의 명시적인 답("승인", "좋아, 만들어", "진행해")에만 해당한다. 그 전에는 build로 가지 않는다.
