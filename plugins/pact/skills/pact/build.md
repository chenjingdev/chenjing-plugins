# build — 계약대로 이행하기

승인된 명세를 만든다. 계획은 당신이 안에서만 쓰고, 사용자에게 승인받지 않는다. 사용자가 이미 승인한 것은 명세다.

## 0. 들어오기 전에

- 명세 status가 `draft`면 build하지 않는다. 승인을 받지 않은 것이니 `probe.md` 5에서 명세를 마저 쓰고 6에서 승인을 받는다. status가 `approved`여도 승인이나 위임 기록(`<run-dir>/approvals.jsonl`)이 없으면 시작하지 못한다. 손으로 status만 고친 명세가 그렇다. 사용자의 승인을 받아 `spec.mjs approve`로 기록한다.
- 0.6.0 전에 만든 명세(frontmatter `pact: 1`)는 승인 기록 없이 이어 간다. `set-status`가 `참고: 옛 판이라 승인 기록 없음`을 알리면 보고서에도 그렇다고 적는다. `pact: 1`이어도 `draft`였던 명세는 기록이 있어야 한다.
- `node <pact>/scripts/spec.mjs run-dir <명세>`로 run-dir을 얻는다. 명세 파일명(날짜 포함, 확장자 제외)이 `<run-id>`다. 예: `2026-10-25-출결.md` → `.pact/2026-10-25-출결/`, 브랜치 `pact/2026-10-25-출결`.
- 예전 방식의 `.pact/<주제>/` 폴더(보고서, 사진)는 그대로 둔다. 그 안에 `wt`가 남아 있으면 `run-dir`이 멈춘다. 어느 명세의 작업인지 확인하고 사용자에게 알린 뒤에 정리한다.
- `<run-dir>/wt`가 이미 있으면 이어 하는 중이다(중단됐거나 verify에서 되돌아왔다). 폴더만 보고 믿지 않고 `<run-dir>/plan.md` 머리의 명세 경로가 이번 명세와 같은지, `git -C <run-dir>/wt branch --show-current`가 `pact/<run-id>`인지 본다. 맞으면 1·2를 건너뛰고 `plan.md`와 `<run-dir>/tasks/*-report.md`를 읽은 뒤 남은 작업이나 verify가 넘긴 실패부터 3으로 이어 간다. 다르면 멈추고 알린다.

## 1. 작업 공간 준비

1. `node <pact>/scripts/git-state.mjs <프로젝트>`로 확인한다.
   - `repo:false`면 멈추고 알린다: "git 저장소가 아니라 격리 작업을 할 수 없습니다 — git init 할까요?"
   - 이번 명세 파일은 `changed`(추적 중인 파일의 변경)에 있든 `untracked`(미추적 파일)에 있든 그 파일만 커밋한다(`docs(pact): <주제> 명세`). 새로 만든 명세는 대개 `untracked`에 있다.
   - 명세 말고 다른 `changed`가 있으면 그 목록을 알리고 멈춘다. 사용자의 작업을 섞지 않기 위해서다.
   - 다른 `untracked`는 worktree로 섞이지 않으니 멈추지 않는다.
2. `node <pact>/scripts/spec.mjs set-status <명세> building`. 승인이나 위임 기록이 없으면 거절한다. 위임 기록이면 지금 명세를 다시 보고, 위험 항목(`[위험: …]` 표시가 있는 기능·규칙 줄)이 생겼으면 거절한다. 그때는 명세와 위험 항목을 사용자에게 보이고 승인을 받아 `spec.mjs approve`로 기록한 뒤 다시 한다.
3. `git worktree add <run-dir>/wt -b pact/<run-id>`로 격리된 작업 공간을 만든다. 코드는 모두 이 worktree에서 바뀐다. 명세 파일은 메인 작업 트리에 있는 것만 고친다. worktree를 만들지 못하면 멈추고 알린다. 메인 작업 트리에서 대신 작업하지 않는다.

## 2. 작업 나누기

명세를 작업으로 나눠 `<run-dir>/plan.md`에 적는다. 맨 위에 명세의 절대 경로, 브랜치 `pact/<run-id>`, 시작할 때의 HEAD를 적는다. verify가 이 HEAD를 기준으로 그 사이 메인에 다른 변경이 들어왔는지 본다. 작업마다 목표, 관련 명세 항목, 완료 기준 명령을 적는다. 이 목록은 당신이 쓰는 것이다. 사용자에게 보여 주고 확인받지 않는다.

작업은 혼자 테스트할 수 있는 단위로 자른다. 설정, 뼈대, 문서 같은 준비는 그것이 필요한 작업에 넣는다.

## 3. 작업마다

1. `pact:worker`에 네 칸 지시를 넘긴다.
   - `## 목표`: 이 작업이 끝나면 무엇이 되나
   - `## 맥락`: 관련 명세 항목을 태그째(`[사용자]`, `[AI 가정]`) 그대로, 구조 판정, 앞 작업이 만든 것, worktree 경로, run-dir과 작업 번호. run-dir은 `<프로젝트>/.pact/<run-id>`의 절대 경로로 적는다. 훅이 이 경로로 어느 판의 승인 기록을 볼지 찾는다. 경로가 없거나 그 판에 승인·위임 기록이 없거나 승인 뒤 `[사용자]` 줄이 바뀌었으면 `pact:worker` 호출이 막히고, 막힌 까닭과 대신 할 일이 한 줄로 온다(아래 "`[사용자]` 항목을 바꿀 때").
   - `## 범위`: 건드려도 되는 파일과 건드리면 안 되는 것. 경로는 worktree 안의 절대 경로로 적는다. 하위 에이전트는 메인 프로젝트 폴더에서 시작하므로 상대 경로를 쓰면 메인 작업 트리를 고치게 된다.
   - `## 완료 기준`: 돌릴 명령과 기대 결과
2. 답장의 상태를 본다. `DONE_WITH_CONCERNS`면 걱정을 읽고 검토자에게 같이 넘긴다.
3. `pact:reviewer`에 지시, worker 보고서 경로, base/head SHA, 관련 명세 항목을 넘긴다.
4. 판정이 `고칠 것 있음`이면 같은 worker에 SendMessage로 지적을 넘긴다. 새 worker를 띄우지 않는다. SendMessage의 답은 알림으로 온다. 확인하려고 다시 묻거나 기다리는 명령을 돌리지 않는다.
5. worker가 고치면 같은 reviewer에 SendMessage로 고친 커밋 범위를 넘겨 한 번 더 검토받는다. 이 두 번째 검토에서도 고칠 것이 있으면 당신이 직접 고치고 완료 기준 명령을 돌린 뒤 넘어간다. 세 번째 검토는 없다. 첫 판정이 `통과`면 사소 지적이 있어도 다시 검토하지 않는다.

당신이 직접 고친 커밋도 verify의 검수 범위에 든다. 검토 두 번 상한은 그대로다.

## BLOCKED가 오면

- 질문이 `[AI 가정]` 항목이나 사소한 범위면 당신이 정한다. worker의 기본값이 괜찮으면 그대로 받는다. 같은 worker에 SendMessage로 답하고, 정한 것을 Ruling으로 남긴다.
- `[사용자]` 항목을 바꿔야 하거나 되돌리기 어려운 것(데이터 삭제, 외부 공개, 비용 발생)이면 그때만 사용자에게 묻는다. 이유와 대안, 기본안을 같이 낸다. 바꾸라는 답을 받으면 아래 "`[사용자]` 항목을 바꿀 때"를 따른다.
- 같은 곳에서 두 번째 BLOCKED가 오면 멈추고 사용자에게 상황을 알린다.

## `[사용자]` 항목을 바꿀 때

승인한 뒤에 `[사용자]` 항목(`[사용자]`나 `[사용자: …]` 태그가 붙은 기능·규칙 줄과 그 케이스)이 바뀌면 `pact:worker` 부르기, `snapshot`, 완료 검사가 바뀐 줄을 알리고 거절한다. 승인 기록에 승인할 때의 `[사용자]` 줄이 들어 있어서다. 줄의 글, 태그, 빼기, 더하기가 모두 바뀐 것이다. `[AI 가정]` 줄만 바뀐 것은 막지 않는다. 막혔다고 실패로 끝내지 않고 다시 승인을 받아 이어 간다.

- 사용자가 바꿔 달라고 했으면 명세를 고치고, 바꿔 달라고 한 그 말을 그대로 인용해 `spec.mjs approve <명세> - <<'EOF'`로 다시 기록한 뒤 하던 작업을 이어 간다. 부탁받은 변경이라 다시 묻지 않는다. status는 `building` 그대로다. 다시 승인해도 진행 상태는 되돌아가지 않는다. 인용하는 말은 앞 기록(승인이든 위임이든)에 쓴 어떤 메시지보다 새것이어야 하니, 앞서 쓴 말로 다시 기록하지 못한다.
- 사용자가 명세 파일을 직접 고쳤으면 부탁한 말이 없다. 거절이 알려 준 바뀐 줄을 보이고 이대로 두는지 한 번 묻는다. 그 답을 인용해 다시 기록한다.
- `[사용자]` 항목은 사용자가 바꾸라고 하기 전에 바꾸지 않는다. 바꾸고 싶으면 먼저 묻는다.
- `[AI 가정]` 항목 밑의 케이스 줄에 `[사용자]`나 `[사용자: …]` 태그가 붙어 있으면(검수 질문에 사용자가 답한 케이스) 그 줄만 `[사용자]` 줄이다. 머리 줄과 다른 케이스 줄은 알아서 고쳐도 되지만 그 케이스 줄은 사용자가 바꾸라고 하기 전에 바꾸지 않는다.
- 다시 승인한 기록과 승인 뒤 바뀐 줄은 검수 보고서에 인용한 말과 함께 실린다.

## 결정 기록

worker 답장의 `## 정한 것`과 당신이 정한 것을 명세 `## 결정 기록`에 옮긴다. 형식은 하나다:

`Ruling: <무엇을 정했나> — <왜> — <틀리면 무엇을 잃나>`

`[AI 가정]` 항목의 내용을 바꿨으면 명세 항목도 고친다. 이 기록은 verify 보고서에 실린다.

## 실패했을 때

테스트나 명령이 실패하면 원인을 먼저 찾는다. 재현하고, 원인을 찾고, 고치고, 다시 확인한다. 증상만 가리는 수정은 하지 않는다.

## 멈추지 않고 이어 간다

작업 사이에 사용자에게 진행 확인을 받지 않는다. 멈추는 경우는 세 가지뿐이다: 되돌리기 어려운 행동, `[사용자]` 항목 변경, 같은 곳에서 두 번째 BLOCKED. 단계 줄로 어디까지 왔는지 보이고, worker나 reviewer에 일을 넘길 때마다 무엇을 맡겼는지 한 줄 덧붙인다(예: `pact · build 2/4 — 판 저장을 worker에 맡겼어요`). 묻지는 않는다.

모든 작업이 끝나면 verify로 간다.
