# build — 계약대로 이행하기

승인된 명세를 만든다. 계획은 당신이 안에서만 쓰고, 사용자에게 승인받지 않는다. 사용자가 이미 승인한 것은 명세다.

## 1. 작업 공간 준비

1. `node <pact>/scripts/git-state.mjs <프로젝트>`로 확인한다.
   - `repo:false`면 멈추고 알린다: "git 저장소가 아니라 격리 작업을 할 수 없습니다 — git init 할까요?"
   - `dirty:true`면 `git status --porcelain`으로 어느 파일인지 본다. 이번 명세 파일 하나뿐이면 그 파일만 커밋한다(`docs(pact): <주제> 명세`). 다른 파일이 걸려 있으면 그 파일 목록을 알리고 멈춘다. 사용자의 작업을 섞지 않기 위해서다.
2. `node <pact>/scripts/spec.mjs set-status <명세> building`
3. `node <pact>/scripts/spec.mjs run-dir <명세>`로 run-dir을 얻고, `git worktree add <run-dir>/wt -b pact/<slug>`로 격리된 작업 공간을 만든다. 코드는 모두 이 worktree에서 바뀐다. 명세 파일은 메인 작업 트리에 있는 것을 고친다.

## 2. 작업 나누기

명세를 작업으로 나눠 `<run-dir>/plan.md`에 적는다. 작업마다 목표, 관련 명세 항목, 완료 기준 명령을 적는다. 이 목록은 당신이 쓰는 것이다. 사용자에게 보여 주고 확인받지 않는다.

작업은 혼자 테스트할 수 있는 단위로 자른다. 설정, 뼈대, 문서 같은 준비는 그것이 필요한 작업에 넣는다.

## 3. 작업마다

1. `pact:worker`에 네 칸 지시를 넘긴다.
   - `## 목표`: 이 작업이 끝나면 무엇이 되나
   - `## 맥락`: 관련 명세 항목을 태그째(`[사용자]`, `[AI 가정]`) 그대로, 구조 판정, 앞 작업이 만든 것, worktree 경로, run-dir과 작업 번호
   - `## 범위`: 건드려도 되는 파일과 건드리면 안 되는 것
   - `## 완료 기준`: 돌릴 명령과 기대 결과
2. 답장의 상태를 본다. `DONE_WITH_CONCERNS`면 걱정을 읽고 검토자에게 같이 넘긴다.
3. `pact:reviewer`에 지시, worker 보고서 경로, base/head SHA, 관련 명세 항목을 넘긴다.
4. 판정이 `고칠 것 있음`이면 같은 worker에 SendMessage로 지적을 넘긴다. 새 worker를 띄우지 않는다. 두 번째 검토에서도 고칠 것이 있으면 당신이 직접 고친다.

## BLOCKED가 오면

- 질문이 `[AI 가정]` 항목이나 사소한 범위면 당신이 정한다. worker의 기본값이 괜찮으면 그대로 받는다. 같은 worker에 SendMessage로 답하고, 정한 것을 Ruling으로 남긴다.
- `[사용자]` 항목을 바꿔야 하거나 되돌리기 어려운 것(데이터 삭제, 외부 공개, 비용 발생)이면 그때만 사용자에게 묻는다. 이유와 대안, 기본안을 같이 낸다.
- 같은 곳에서 두 번째 BLOCKED가 오면 멈추고 사용자에게 상황을 알린다.

## 결정 기록

worker 답장의 `## 정한 것`과 당신이 정한 것을 명세 `## 결정 기록`에 옮긴다. 형식은 하나다:

`Ruling: <무엇을 정했나> — <왜> — <틀리면 무엇을 잃나>`

`[AI 가정]` 항목의 내용을 바꿨으면 명세 항목도 고친다. 이 기록은 verify 보고서에 실린다.

## 실패했을 때

테스트나 명령이 실패하면 원인을 먼저 찾는다. 재현하고, 원인을 찾고, 고치고, 다시 확인한다. 증상만 가리는 수정은 하지 않는다.

## 멈추지 않고 이어 간다

작업 사이에 사용자에게 진행 확인을 받지 않는다. 멈추는 경우는 세 가지뿐이다: 되돌리기 어려운 행동, `[사용자]` 항목 변경, 같은 곳에서 두 번째 BLOCKED. 단계 줄(`pact · build 2/4`)로 어디까지 왔는지만 보인다.

모든 작업이 끝나면 verify로 간다.
