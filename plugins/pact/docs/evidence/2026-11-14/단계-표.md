- p1 작업 1 [중요] Origin을 Host하고만 견줘서 BASE_URL을 두고 리버스 프록시 뒤에서 띄우면 로그인을 포함한 모든 POST가 403
- p1 작업 1 [사소] 확인 전 메일로 다시 가입하면 비밀번호가 덮여, 초대 코드를 아는 사람이 남의 가입 대기 계정을 가로챌 수 있음(확인 화면에서 가입 때 비밀번호를 한 번 더 넣게 바꿈)
- p1 작업 1 [사소] 확인 메일 다시 받기 API가 로그인·횟수 제한 없이 불려 회사 메일 계정 발송 제한에 걸릴 수 있음(계정당 60초 쿨다운)
- p1 작업 1 [사소] STARTTLS 없는 SMTP에 메일 계정 비밀번호를 평문으로 보내고, 연결 시간 제한이 없어 가입 요청이 매달림

- p1 파일 이름의 탭 같은 제어문자가 명세 결정 기록에는 '_'로 바뀐다고 적혔는데 실제로는 지워짐(a/b<탭>c\d.txt가 a_bc_d.txt로 저장). 첫 판정에서 의심 1건이었다가 명세 문구를 고친 뒤 통과로 바뀜 — 진짜 고장: 아니오 · 고침
  - p1 판단: 서버 요청, 운영 명령, 자동 시험 47개로 가입부터 링크 끄기까지 흐름을 끝까지 돌렸지만 verify가 새로 찾아낸 실제 고장은 없었다(의심 1건은 명세 문구 오기). 화면 쪽(남의 줄에 버튼 안 보임, 지우기 확인 창, 꺼지는 날 표시, 거절 이유 표시, 처음 쓰는 사람)은 보지 못해 그 부분의 고장 여부는 모름.
  - p2 판단: 기록상 verify가 찾은 고장은 없다(실패 0 · 의심 0). HTTP 요청과 명령으로 50MB 경계, 7일 만료, 남의 판 403, 재시작 뒤 유지, README만 보고 따라 하기를 확인해 줬지만, 화면 모양·휴대폰 너비·복사 단추·지우기 확인 창은 못 봤고 검토에서 고친 폼 제출 문제가 실제 브라우저에서 풀렸는지도 확인하지 못했다.
- p3 S4: 50MB+1바이트를 길이를 알리고 보내면 문구 없이 연결이 끊김(ECONNRESET, 목록에는 남지 않음). 길이를 안 알리면 413과 50MB 문구가 옴. 화면의 사전 검사 문구와 서버 공간 부족 상황은 직접 못 봄 — 진짜 고장: 모름
  - p3 판단: verify가 새로 잡은 고장은 없고(실패 0, verify 뒤 코드 수정도 없음, results.json 형식만 손봄) 가장 큰 고장은 verify 전에 검토가 이미 잡았으므로, verify는 7일 만료·재시작 유지·끈 링크 재생성·초대 코드 미설정 같은 서버 동작을 독립적으로 다시 확인해 준 정도다. 서버 요청 방식이라 브라우저에서만 나는 고장은 이번 verify로 볼 수 없었고 그 부분은 모름으로 남았다.
- q1 N2 의심: 초대 코드를 10번 넘게 틀리면 그 접속 주소에서는 맞는 코드로도 10분간 가입이 막힘(명세 결정 기록에 적힌 설계 동작) — 진짜 고장: 아니오
- q1 명세 대조: 0바이트 파일도 올라감(명세에 없는 동작) — 진짜 고장: 아니오
  - q1 판단: 실패 0이라 verify가 새로 찾아낸 고장은 없다. 서버에 직접 요청해 본 흐름(50MB 경계, 만든 때의 판을 주는 링크, 기한 지난 링크, 남의 판 지우기 거절)은 build의 자동 시험 15개와 검토가 이미 다룬 것이라 verify가 없었어도 결과물은 같았을 것으로 보인다. 화면에서만 드러날 고장(지우기 버튼 노출, 관리 화면, 휴대폰 폭)과 재시작 뒤 데이터 유지는 확인되지 않은 채 남았다.
- q2 S9(1차): 로그인해 있다가 막힌 사람의 요청은 거절되지만 "막힌 계정입니다" 대신 까닭 없이 로그인 화면만 보임(원인: block이 세션을 지워 다음 요청이 401이 됨) — 진짜 고장: 예 · 고침
  - q2 판단: verify가 없었으면 로그인해 있다가 막힌 사람이 이유도 모른 채 로그인 화면만 보게 되는 흠 하나가 남았을 것이다. 서버 쪽 나머지는 처음 돌릴 때부터 통과했고, 끌어다 놓기 · 지우기 확인 창 · 링크 목록 · 남의 줄 버튼 같은 화면 쪽 흠은 도구가 없어 이 단계로는 알 수 없다.
- q3 A4 서버를 껐다 다시 띄워도 데이터가 남는지. 띄운 서버를 끌 수 없어 같은 DATA_DIR로 새 서버를 하나 더 띄워 비교했고 계정·파일·링크·횟수·기록·로그인 유지가 모두 같았음 — 진짜 고장: 아니오
  - q3 판단: verify는 실패를 하나도 못 찾았고, 서버 쪽 동작 16건(초대 코드·권한·링크 만료·막기·활동 기록·README만 보고 띄우기 등)이 실제로 돈다는 것과 메인이 고친 쓰기 오류 처리가 먹는다는 것(N3)만 확인했다. 끌어다 놓기·진행 표시·복사 버튼·지우기 확인 창·전체 흐름·화면 배치 10건은 한 번도 눌러 보지 못해, 화면 쪽 고장이 있어도 잡지 못했다.
- pb1 첫 판 의심 1건(N4): 가입 코드 없이 띄운 서버가 가입 시도에 '관리자에게 문의하세요'라고 안내하는데 이번 판에는 관리자가 없음 — 진짜 고장: 아니오 · 고침
  - pb1 판단: verify는 기능 고장을 하나도 찾지 못했고(build의 자동 시험 16개와 두 번의 검토가 이미 흠을 걸러 둠) 잡은 것은 관리자가 없는데 관리자에게 문의하라는 안내 문구 한 줄뿐이다. 화면에서만 보이는 흠(목록 모양, 확인 창, 주소 복사)은 확인하지 못한 채 남았다.
  - pb2 판단: verify는 실패도 의심도 하나 못 잡았고(서버 응답은 모두 명세대로), 이를 거치지 않았어도 남았을 고장은 확인된 것이 없다. 화면 쪽(끌어다 놓기, 버튼, 확인 창, 안내 문구)과 디스크 가득(R12)은 아예 검증하지 못했다.
- qb1 (1차 검수) 퍼센트 부호가 중간에서 잘린 공유 링크 주소(/s/%E0%A4%A 등)가 '더 이상 받을 수 없는 링크입니다' 화면이 아니라 400 오류 글자로 나옴(명세 결정과 어긋남) — 진짜 고장: 예 · 고침
- qb1 (1차 검수) 로그인 7일 유지를 실제로 기다려 보지 못해 의심. 저장소 시험(시계 6일 뒤 유지, 8일 뒤 401)으로 통과로 바꿈 — 진짜 고장: 아니오
  - qb1 판단: verify가 없었으면 깨진 공유 링크 주소가 안내 화면 대신 JSON 오류 글자로 보이는 흠(작은 것) 하나가 남았을 것이다. 서버 쪽 시나리오는 나머지 모두 통과했고, 화면 쪽 15개는 안 봤으므로 화면 고장이 있는지는 모름.
  - qb2 판단: verify는 고장을 하나도 찾지 못했고(실패 0·의심 0) 서버 쪽은 HTTP로 확인해 50MB 경계, 남의 파일 지우기 403, 한글 이름, 링크 다시 켜기, 7일 만료가 모두 기대대로였으니, 자동 테스트 25개가 이미 보던 것을 한 번 더 본 셈이라 결과물은 바뀌지 않았다. 화면 코드는 만든 쪽도 검토한 쪽도 한 번도 띄워 보지 못한 채 남았고 가입 코드 미설정 문구(R3)와 디스크 가득 참 문구(R9)도 서버로 못 봤다. (results.json은 A2를 통과로 적었으나 pact 보고서 표는 스크린샷이 없다며 통과 0·미검증 26으로 셈)

## 명세 검수의 판단과 까닭

- p1: 결과물을 바꿈 — 검수가 돌려준 사소 항목 18개가 링크 노출 범위(R17~R19)와 검수 기준(A5~A8)이 되었고, 사용자만 항목 3개는 공개 주소·계정 막기·삭제 명령·확인 메일 같은 운영 기능을 만들었다. 다만 H1~H9 가운데 검수에서 새로 잡힌 것은 없고, H6의 주인 확인은 검수 3 첫 답으로는 반영되지 않아 사용자가 승인 때 고친 뒤에야 바뀌었다.
- p2: 거의 안 바꿈 — 숨은 뜻 H1~H7은 첫 차례 목록 짚기로 이미 초안에 들어 있었고(같은 이름 판 쌓기 R4도 초안에 있었음) 검수가 새로 잡은 숨은 뜻은 없다. 사용자만 질문 둘 중 하나는 답이 갈리지 않아 초안 그대로였고 다른 하나는 공개 주소 옵션만 더했으며, 나머지는 세부 규칙과 검수 기준을 글로 박은 것이다.
- p3: 결과물을 바꿈 — 숨은 뜻 H1~H9에는 새로 닿은 것이 없고(그 아홉은 이미 사용자 답이나 AI 가정으로 들어 있었음), 사용자만 답할 두 가지도 사용자는 추천대로만 답했다. 다만 링크 권한을 올린 사람으로 좁히고 지우기 확인창, 디스크 부족 처리, 초대 코드 미설정 시 가입 닫기, 꺼지는 시각 표시, 팀 쪽 HTTPS 같은 동작과 한계가 명세에 들어가 화면과 서버 동작이 달라졌다.
- q1: 거의 안 바꿈 — 숨은 뜻은 하나도 새로 잡지 못했다(H1~H5·H7은 첫 답에서 이미 나왔고, 사용자만 답할 두 물음은 하나는 요구를 되풀이한 답, 하나는 '추천대로'로 끝나 기본안이 그대로 갔다). 더해진 것은 팀원 풀기·링크 여러 개·50MB 경계·막힌 사람의 링크 끄기 같은 작은 기본값이고, A2·A3·A6·A7 검사 문장은 검수 방식만 바꿨다.
- q2: 결과물을 바꿈 — 막힌 계정 처리, 지우기 확인, 비밀번호 재설정 명령, 초대 코드 전 가입 불가, 횟수 세는 규칙, 7일 시험 방법 같은 운영 · 안전 규칙이 초안에 없다가 명세에 들어와 코드와 README로 구현됐다. 다만 숨은 뜻 H1~H9는 하나도 새로 잡지 못했고 사용자에게 간 질문은 서버 주소 하나였으며 맡김으로 끝났다.
- q3: 결과물을 바꿈 — 운영자 역할과 서버 명령(초대 코드·계정 막기·비밀번호), 활동 기록 범위, 횟수를 세는 기준, 내려받기로만 주기, age-link 같은 빈 곳을 메워 결과물에 실제 기능과 보안 헤더로 들어갔다. 다만 H1~H9 중 새로 잡은 것은 없고(H6은 끝까지 빠짐), 사용자만 답할 수 있다던 두 물음은 추천대로 맡겨서 기본안으로 끝났다.
- pb1: 결과물을 바꿈 — 링크 끄기 권한, 주소 복사용 공개 주소, 받기 화면의 올린 사람 숨김 같은 동작이 명세에 들어가 만든 앱에 그대로 반영됐다. 다만 숨은 뜻은 하나도 새로 못 잡았고, 파일 크기 1GB(R6)는 사소함으로 돌려 그대로 둬서 H4는 승인 때 사용자가 고쳤다.
- pb2: 결과물을 바꿈 — 검수가 사용자만 답할 수 있는 두 가지(바깥 주소, 퇴사자 파일·링크)를 짚어 로그인 잠금, 바깥 주소 설정, 계정 막을 때 링크 끄기, 서버에서만 지우기가 결과물에 들어갔다. 다만 H1~H9 중 새로 잡은 뜻은 없다(H1~H4, H6은 probe 물음에서 나왔고 검수의 두 질문은 숨은 뜻과 무관했다).
- qb1: 결과물을 바꿈 — 사용자만 답할 수 있는 2건은 기본안 그대로(맡김, 빗나간 답)여서 바뀐 것이 없다. 그러나 사소함 18건에서 같은 이름 규칙(H5), 링크 한 개·받는 쪽 화면·빈 목록 문구, 만료 확인법과 초대 코드 안내를 README에 넣는 것이 명세에 들어가 결과물이 달라졌다. 새 숨은 뜻을 건져 낸 것은 없다.
- qb2: 결과물을 바꿈 — 검수가 빈틈 18개(사소 16, 사용자만 2)를 짚어 기본값과 검수 기준(가입 코드 미설정 때 가입 막기, 로그인 14일, 디스크 문구, 내려받기 전용, 7일 확인법 README 등)이 명세에 들어가 코드로 이어졌지만 모두 작은 기본값이고, 숨은 뜻은 하나도 새로 잡지 못했다. 사용자만 항목 2개는 "추천대로"로 맡겨져 새 정보가 없었고, 검수가 제안한 아이디 규칙(영문·숫자 3–20자)은 H6과 어긋난 기본값이어서 승인 때 사용자가 고쳐야 했다.
