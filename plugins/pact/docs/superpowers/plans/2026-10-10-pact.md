# pact Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 슈퍼파워를 대체하는 Claude Code 플러그인 `pact`를 만든다. 자연어 요청에 켜져서 크기를 가늠하고, probe → 명세 승인 한 번 → build → verify(스크린샷 보고서)로 알아서 이어진다.

**Architecture:** 스킬 하나(`skills/pact`)가 입구다. 단계별 지침은 같은 폴더의 참조 파일로 나누고, 단계 사이는 명세 파일의 `status` 값으로 넘어간다. 하위 에이전트 넷(spec-checker, worker, reviewer, verifier)은 `agents/`에 정의한다. 판단이 필요 없는 일(명세 파싱과 검사, 체크리스트 페이지, 갤러리, Playwright 준비, 보고서 생성, git 상태 확인)은 `scripts/`의 Node 스크립트가 맡는다.

**Tech Stack:** Claude Code 플러그인(스킬, 에이전트 마크다운), Node 20+ 내장 모듈만 사용(`node:test`, `node:http`, `node:fs`, `node:child_process`), verify용 Playwright `1.55.0`(실행할 때 준비).

**Spec:** `plugins/pact/docs/superpowers/specs/2026-10-10-pact-design.md`

## Global Constraints

- 사용자에게 보이는 글(스킬 본문의 안내 문구, 페이지, 보고서, 에이전트 보고 형식의 제목)은 한국어로 쓴다.
- 명세 항목 태그는 정확히 `[사용자]`와 `[AI 가정]` 두 가지만 쓴다.
- Ruling 형식은 정확히 `Ruling: <무엇을 정했나> — <왜> — <틀리면 무엇을 잃나>`이다.
- 명세 `status` 값은 `draft`, `approved`, `building`, `verifying`, `done` 다섯 가지다.
- 명세 위치는 대상 프로젝트의 `docs/pact/<YYYY-MM-DD>-<slug>.md`이고, 실행 산출물 위치는 `.pact/<slug>/`이다. `.pact/.gitignore`의 내용은 `*` 한 줄이다.
- 다른 플러그인에 의존하지 않는다. 플러그인 파일 어디에도 `superpowers:`, `tiers:`, `proto:` 호출이 없어야 한다.
- 금지 문구가 플러그인 파일 어디에도 없어야 한다: `1%`, `MUST`, `not negotiable`, `Delete it`, `Iron Law`, `No exceptions`, `letter of the rules`, `lying`, `반드시 스킬`, `예외 없이`.
- 스크립트는 npm 의존성 없이 Node 내장 모듈만 쓴다. Playwright만 예외이며, 대상 프로젝트에 있으면 그것을 쓰고, 없으면 `${CLAUDE_PLUGIN_DATA:-~/.pact}/playwright`에 설치한다. 대상 프로젝트의 `package.json`은 건드리지 않는다.
- TDD는 스크립트(여러 단계에서 쓰는 공용 로직)에만 먼저 적용한다. 프롬프트 파일은 쓴 뒤 정적 검사 테스트로 고정한다(`CLAUDE.local.md`).
- 버전은 `0.1.0`에서 시작한다.

## Review Focus

1. **사용자가 손으로 고친 명세.** 태그 오타(`[AI가정]`), `status` 누락, 섹션 이름 변경이 있어도 `spec.mjs lint`는 죽지 않고 무엇이 틀렸는지 한국어로 줄마다 알려야 한다. Task 1에서 테스트로 고정한다.
2. **체크리스트 페이지를 닫거나 전송이 실패할 때.** 서버는 시간 초과 시 종료 코드 1과 안내 문구로 끝나고, 페이지에는 복사 줄이 보여야 한다. Task 2에서 고정한다.
3. **화면이 없는 프로젝트이거나 스크린샷 파일이 없을 때.** 보고서는 `output` 텍스트만 있는 단계도 그리고, 없는 이미지는 "스크린샷 없음"으로 표시해야 한다. Task 4에서 고정한다.
4. **git 저장소가 아니거나 합칠 때 작업 트리가 더러울 때.** build는 시작 전에, verify는 합치기 전에 `git-state.mjs`로 확인하고 멈춰서 알려야 한다. Task 5에서 스크립트를 고정하고, Task 8에서 지침으로 고정한다.
5. **한글과 공백이 섞인 주제명.** `slugify('출결 대시보드 v2')`는 `출결-대시보드-v2`가 되어야 하고, 같은 날 같은 주제면 `-2`를 붙여 덮어쓰지 않아야 한다. Task 1에서 고정한다.

**Files:**

**Interfaces:**
- Produces:
  - `parseSpec(text: string) -> { frontmatter: Record<string,string>, sections: Record<string,string>, items: Array<{ id: string, text: string, tag: '사용자'|'AI 가정'|null, section: string }> }`
  - `lintSpec(text: string) -> string[]` (문제 한 줄씩, 한국어, 문제 없으면 `[]`)
  - `setStatus(text: string, status: string) -> string`
  - `slugify(topic: string) -> string`

  - `ensureRunDir(projectDir: string, slug: string) -> string` (`paths.mjs`; `.pact/.gitignore` = `*\n`)
  - CLI: `node scripts/spec.mjs status|lint|set-status|new <args>`
- Spec 형식 (`spec-template.md`, 섹션 이름은 이대로):

```markdown
---
pact: 1
topic: <주제>
status: draft
created: <YYYY-MM-DD>
---
# <주제>
## 목적
## 범위
## 하지 않는 것
## 기능
- F1 <기능 한 줄> [사용자]
  - 케이스: <발생 조건> → <표시·동작>
## 공통 규칙
- R1 <규칙> [AI 가정]
## 구조 판정
## 확인 필요
## 결정 기록
```

항목은 `## 기능`과 `## 공통 규칙` 아래 `- F<n>` / `- R<n>`으로 시작하는 줄이다. 케이스 줄(`  - 케이스:`)은 위 항목에 속한다.

### Task 2: 기능 체크리스트 페이지 `checklist.mjs`

**Files:**
- Create: `plugins/pact/scripts/checklist.mjs`
- Test: `plugins/pact/tests/checklist.test.mjs`

**Interfaces:**
- Produces:
  - `renderChecklist({ title: string, items: Array<{ label: string, note?: string, suggested?: boolean, reason?: string }> }) -> string` (self-contained HTML)
  - CLI `node scripts/checklist.mjs render <input.json> <run-dir>` → `<run-dir>/checklist.html`
  - CLI `node scripts/checklist.mjs serve <run-dir>` → 빈 포트에서 서비스하고 `페이지: http://127.0.0.1:<port>/`를 출력한다. 첫 `POST /submit` 본문을 `<run-dir>/checklist.txt`에 쓰고 출력한 뒤 종료 코드 0으로 끝난다. `PACT_CHECKLIST_TIMEOUT_MS`(기본 600000)가 지나면 `시간 초과 — 채팅으로 기능 범위를 알려 주세요`를 stderr에 쓰고 종료 코드 1로 끝난다.
- 페이지 결과 줄 형식: `기능: <체크된 항목, 쉼표로>` (자유 입력은 뒤에 이어 붙임). 제안 항목은 체크 해제 상태로 두고 `(제안)`과 이유를 표시한다. 전송 실패 시 복사 줄을 보인다. proto `SKILL.md`의 "Scope page recipe" 구조를 참고하되 새로 쓴다.

- [ ] **Step 1: 실패하는 테스트 작성**
  - `renderChecklist`: 제안 아닌 항목은 `checked`, 제안 항목은 `checked`가 없고 `(제안)`과 reason 텍스트를 포함한다. 결과 줄 초기값은 `기능: `로 시작한다. `fetch('/submit'`와 `id="fallback"`을 포함한다. 외부 URL(`http`로 시작하는 src/href)이 없다. label의 `<`는 이스케이프된다.
  - `serve`: 임시 run-dir에서 자식 프로세스로 띄우고, 출력된 포트로 GET 200, `POST /submit` 본문 `기능: a, b` → 프로세스가 0으로 끝나고 `checklist.txt` 내용이 `기능: a, b`이다.
  - `PACT_CHECKLIST_TIMEOUT_MS=200`이면 종료 코드 1, stderr에 `시간 초과`가 있다.
- [ ] **Step 2: 실패 확인** — `node --test tests/checklist.test.mjs` → FAIL
- [ ] **Step 3: 구현** — `scripts/checklist.mjs`
- [ ] **Step 4: 통과 확인** — `node --test tests/checklist.test.mjs` → PASS
- [ ] **Step 5: Commit** — `feat(pact): 기능 체크리스트 페이지와 일회용 서버`

### Task 4: 검수 보고서 `report.mjs`

**Files:**
- Create: `plugins/pact/scripts/report.mjs`
- Test: `plugins/pact/tests/report.test.mjs`

**Interfaces:**
- Consumes: `results.json` (verifier가 씀, 아래 형식)
- Produces:
  - `renderReport(results: Results, { runDir: string }) -> { html: string, summary: string }`
  - CLI `node scripts/report.mjs <run-dir>` → `<run-dir>/report.html`을 쓰고 `summary`와 경로를 출력한다.
- `Results` 형식 (verify.md와 verifier.md가 같은 형식을 쓴다):

```json
{ "spec": "docs/pact/2026-10-10-x.md",
  "scenarios": [ { "id": "S1", "title": "…", "kind": "spec|case|newcomer",
                   "items": ["F1"], "result": "pass|fail|doubt", "note": "…",
                   "steps": [ { "action": "…", "shot": "shots/S1-1.png", "output": null } ] } ],
  "specCheck": { "missing": ["…"], "extra": ["…"], "misunderstood": ["…"] },
  "rulings": ["Ruling: … — … — …"] }
```

- 순서: 맨 위 요약(`통과 n · 실패 n · 의심 n`) → 실패·의심 시나리오(펼침) → 명세 대조 → 결정 기록 → 통과 시나리오(`<details>`로 접음). 스크린샷은 run-dir 기준 상대 경로 `<img>`이고, 파일이 없으면 `스크린샷 없음`을 표시한다. `output`이 있으면 `<pre>`로 넣는다.

- [ ] **Step 1: 실패하는 테스트 작성**
  - 실패 1, 통과 2 → summary `통과 2 · 실패 1 · 의심 0`. HTML에서 실패 시나리오가 첫 통과 시나리오보다 앞에 오고, 통과는 `<details>` 안에 있다.
  - shot 파일이 실제로 없으면 `스크린샷 없음`, 있으면 `<img src="shots/S1-1.png"`이다.
  - `shot:null, output:"exit 0"`인 단계 → `<pre>`에 `exit 0`이 들어간다.
  - 시나리오가 0개여도 렌더된다(`통과 0 · 실패 0 · 의심 0`).
  - `specCheck`, `rulings`의 텍스트가 이스케이프되어 들어간다.
- [ ] **Step 2: 실패 확인** → FAIL
- [ ] **Step 3: 구현** — 스타일은 인라인, 외부 요청 없음.
- [ ] **Step 4: 통과 확인** → PASS
- [ ] **Step 5: Commit** — `feat(pact): verify 보고서 생성`

**Interfaces:**

- frontmatter: `spec-checker`와 `reviewer`는 `model: opus`, `disallowedTools: Edit, Write, MultiEdit, NotebookEdit, Agent`. `worker`와 `verifier`는 `model: sonnet`이다. verifier는 `Agent`만 막는다(스크린샷과 results.json을 써야 하므로).

내용 결정 사항 (본문은 구현자가 쓴다. 아래는 빠지면 안 되는 것):
- **spec-checker**
  - 입력: 명세 경로와 "사용자가 말한 요구" 목록. 이 목록은 메인 세션이 대화에서 `[사용자]`로 적은 것들이다.
  - 두 가지 일을 한다. (a) 빌더 입장: "이것만 보고 만들 수 있나, 잘못 짐작하면 결과가 달라지는 곳은?" (b) 갭 대조: 요구 중 명세에 없는 것, 명세 항목 중 어떤 요구에도 안 닿는 것.
  - 출력 형식은 세 무더기다: `## 이미 답이 있음`(답과 출처), `## 사소함 — AI가 정함`(정한 값 = `[AI 가정]` 후보), `## 사용자만 답할 수 있음`(중요한 순서, 질문마다 왜 결과가 바뀌는지). 마지막 줄은 `질문 라운드는 이것 한 번뿐입니다.`
- **worker**
  - 입력은 `## 목표` `## 맥락` `## 범위` `## 완료 기준` 네 칸이다. 하나라도 비면 `BLOCKED:`로 요청한다.
  - 범위 밖은 건드리지 않는다. 완료 기준 명령은 실제 숫자로 보고한다. 작업마다 worktree 안에서 커밋한다. push는 하지 않는다.
  - 결과를 바꾸는 결정(계약, 데이터 모양, 오류 동작, 경계, 기존 패턴 중 무엇을 따를지)이면 `BLOCKED:`로 멈추고, 질문마다 결정, 선택지, 자기 기본값을 적는다. 사소한 결정은 알아서 하고 `## 정한 것`에 Ruling 형식으로 적는다.
  - 보고하기 전에 짧게 자기 검토한다: 빠진 요구, 요청하지 않은 추가, 기존 패턴, 테스트가 진짜 동작을 확인하는지.
  - 자세한 보고는 `<run-dir>/tasks/<n>-report.md`에 쓰고, 답장은 15줄 이내로 한다: `## 상태: DONE | DONE_WITH_CONCERNS | PARTIAL | BLOCKED`, `## 바꾼 파일`, `## 확인`(명령 → 숫자), `## 정한 것`(Ruling 줄 또는 "없음"), `## 걱정·위험`, `보고서: <경로>`.
  - TDD 규칙은 Global Constraints의 문장을 그대로 넣는다.
  - "Don't guess", "Ask them now" 계열 문구는 넣지 않는다.
- **reviewer**
  - 입력은 작업 지시(brief), worker 보고서 경로, base/head SHA, 관련 명세 항목(태그 포함)이다.
  - 보고를 검증되지 않은 주장으로 보고 diff와 직접 대조한다.
  - `## 명세 대조`에는 `빠진 것` / `더한 것` / `잘못 이해한 것`을 쓴다. 더한 것이 `[AI 가정]` 항목이나 worker Ruling으로 설명되면 그렇다고 표시하고, 설명되지 않으면 지적한다.
  - `## 지적`은 `심각` / `중요` / `사소`로 나누고 file:line을 단다. `## 판정: 통과 | 고칠 것 있음`.
  - 테스트 전체를 다시 돌리지 않는다. 의심이 구체적일 때만 좁은 테스트 하나를 돌린다.
- **verifier**
  - 입력: 명세 경로, run-dir, 대상 실행 방법(URL 또는 명령), `node scripts/playwright.mjs ensure` 결과.

  - 웹이면 run-dir 안에 Playwright 스크립트를 써서 돌리고, 단계마다 `shots/<id>-<n>.png`를 찍는다. 화면이 없으면 명령을 실행하고 `output`을 기록한다.
  - `results.json`을 Task 4 형식 그대로 쓴다. 고치지 않는다(대상 소스 수정 금지).
  - 답장: `통과 n · 실패 n · 의심 n` + `results.json` 경로.
