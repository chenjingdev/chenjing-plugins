# pact 설계

- 날짜: 2026-10-10
- 위치: `chenjing-plugins/plugins/pact/`
- 표시: 항목 끝의 `[사용자]`는 사용자가 정한 것, `[AI]`는 대화 중 AI가 제안하거나 정한 것이다. pact 명세가 쓸 태그를 이 문서에서 먼저 써 본다.

## 1. 의도와 이유

사용자가 회사에서 RFP(한국기술교육대학교 AI 학습분석실 사업)를 보다가 떠올린 생각이다.

> 기능명세서가 보니까 개발자 입장에서 뭔가 디테일하게 적은 내용이 없더라고 정말 기능 명세, 어떤 기능이 필요한지 개발 관련된 거라면 어떤 스펙으로 해야 될지 정도의 간단한 그런 질문들이 있었고 어떻게 구현하는지는 전적으로 그냥 구현하는 [쪽]에서 알아서 정한다는 점이 꽤나 인상 깊었어

RFP에서 발주처는 무엇을, 왜, 어떤 제약 안에서 만들지와 어떻게 검수할지만 정한다. 어떻게 만들지는 수행사가 정한다. 바이브 코딩에서는 사용자가 발주처이고 AI가 수행사다. pact는 이 관계를 플러그인으로 옮긴다. 사용자와 AI가 무엇을 만들지 계약(명세)을 맺고, AI가 그 계약을 이행(build)하고 검수(verify)한다.

해결하려는 문제는 사용자의 말로 이렇다.

> 내가 시킨 대로는 다 만들었어 근데 막상 까보니까 이거는 내가 처음부터 생각하지 못한 문제 때문에 고려하지 못했던 그런 것들이 완성되고 난 뒤에 보이거든 이런 것들도 RFP를 작성할 때 도움을 줘서 처음부터 고려할 수 있게 해주면 좋지 않을까?

명세 자체에도 검수가 필요하다. 한기대 프로젝트에서 기획자는 RFP의 모호한 부분을 찾아 정책 기본안을 만들었고, 그것을 학교에 가져가 확인받았다(10/8 주간정례회의). 사용자는 이렇게 말했다. "충분히 그 RFP에 대한 검수 과정이 필요하지 않을까?"

질문 방식도 정했다. 사용자는 생각 못 한 걸 짚어 주는 소크라테스식 질문은 좋아하고 [사용자], 확인만 받는 질문과 구현 방식을 고르라고 넘기는 질문은 싫어한다 [사용자].

pact는 슈퍼파워를 **대체**한다 [사용자]. 슈퍼파워 위에 얹는 플러그인이 아니다.

## 2. 목표, 비목표, 실패로 볼 장면

**목표**
- 만들기 전에 사각지대를 짚어서, 완성한 뒤에야 보였을 문제를 명세 단계에서 잡는다.
- 사용자는 무엇을 만들지와 검수 기준만 정한다. 어떻게 만들지는 AI가 정하고 기록한다.
- 명세를 다른 눈으로 검수한다. 결과물은 명세 대조와 실제 사용 시나리오로 검수한다.
- 입구 하나(`/pact`)로 명세에서 검수 보고서까지 이어진다.

**비목표**
- 슈퍼파워와 함께 쓰는 것. pact가 슈퍼파워를 대체한다.
- tiers나 proto 플러그인을 호출하는 것. 개념만 가져온다 [사용자: proto는 미완성이라 개념만, build는 자체 worker와 reviewer로].
- 스킬 작성 방법(writing-skills)이나 세션 진단(diagnosing-superpowers) 같은 메타 기능.

**실패로 볼 장면** [사용자: 1~5번을 골랐다]

동작은 하더라도 아래 장면이 생기면 실패다.

1. **질문에 지친다.** 작은 앱 하나 만들려다 꼬리 질문이 15개 이어진다.
2. **문서가 장식이 된다.** 명세가 길어서 읽지 않고 승인한다.
3. **가정이 너무 많다.** AI 가정이 40개라 다 볼 수 없고, 완성품이 생각과 딴판이다.
4. **처음 문제가 그대로다.** verify는 "명세대로 다 됨"이라고 하는데, 써 보면 완성한 뒤에야 보이는 문제가 여전히 나온다.
5. **작은 일에도 무겁다.** 버튼 색 하나 바꾸는데도 probe가 돈다.

## 3. 제약

- Claude Code 플러그인이다. `chenjing-plugins` 마켓플레이스에 `plugins/pact`로 등록한다. 다른 플러그인처럼 `.claude-plugin/plugin.json`을 두고, 루트 `.claude-plugin/marketplace.json`에 항목을 추가한다.
- 입구는 하나다. 단계는 알아서 넘어간다 [사용자: 메모리 "명령·하위 명령이 늘면 부담, 입구는 하나"]. 사용자가 단계 이름을 외울 필요가 없어야 한다.
- **켜지는 때** [사용자 승인]: "만들어 줘", "고쳐 줘", "바꿔 줘" 같은 자연어 요청에 알아서 켜진다. 명령으로도 부를 수 있다. 다만 슈퍼파워의 "You MUST use this"나 1% 규칙 같은 강제 문구로 켜지게 하지 않는다. description에 언제 쓰는지만 적고, 켜지면 크기 가늠부터 한다. 명령 이름은 플러그인 스킬 기본값(`/pact:pact`)이면 충분하다 [AI: 주로 자연어로 켜지므로 명령 이름은 덜 중요하다. 훅 모듈로 `/pact`를 따로 등록하지 않는다].
- 다른 플러그인에 의존하지 않는다. 필요한 에이전트와 프롬프트는 pact 안에 둔다.
- TDD는 버그 수정과 여러 곳에서 쓰는 공용 로직에만 먼저 쓴다. UI, 프로토타입, 연결 코드는 구현한 뒤 테스트해도 된다. 테스트보다 먼저 쓴 코드를 지우지 않는다 [사용자: `CLAUDE.local.md`].
- 사용자에게 보이는 글은 한국어로 쓴다.

## 4. 수정 기준: 누가 정했는가 [사용자 승인]

pact 전체를 묶는 규칙이다. 명세의 모든 항목에는 누가 정했는지 태그가 붙는다.

| 그 항목을 누가 정했나 | AI가 바꾸고 싶을 때 |
|---|---|
| `사용자` (사용자가 직접 말한 것) | 먼저 묻는다. 이유와 대안을 같이 낸다. |
| `AI 가정` (AI가 채운 것) | 알아서 바꾸고, 바꾼 내용과 이유를 기록한다. |
| 되돌리기 어려운 것 (데이터 삭제, 외부 공개, 비용 발생) | 누가 정했든 묻는다. |

한기대 프로젝트에도 같은 구분이 있었다. RFP에 있는 기능은 교수님께 먼저 제안하고 협의했다(9/3). 명세에 없는 영상 보관은 수행사가 판단했다(9/3). 변경 이력은 추적표에 남겼다(8/31).

## 5. 흐름

```
"…만들어 줘 / 고쳐 줘" 또는 /pact:pact
 ├─ 0. 크기 가늠 ─ 작은 일 → 한 줄로 알리고 가벼운 길 (직접 고침 + 확인 하나)
 ├─ probe
 │   1. 대화       소크라테스식 질문, 한 메시지에 하나, 기본안이나 추측을 먼저
 │   2. 기능 고정   체크리스트 한 장 (AI 제안은 체크 해제 + 이유)
 │   3. 구조 고르기  화면이 있으면 스케치 2~3장 → 판정 하나, 최대 2라운드
 │   4. 명세 작성
 │   5. 명세 검수   다른 에이전트가 빌더 입장 + 갭 대조 → 사용자 몫만 한 번에 질문
 │   ── 사용자 승인 (유일한 승인) ──
 ├─ build    worker 구현 → reviewer 대조, Ruling 기록
 └─ verify   시나리오 → 브라우저 실행 + 스크린샷 → 보고서. 실패하면 build로 되돌림
            통과하면 로컬 커밋·합치기 → 보고서로 알림 (push만 물음)
```

[사용자: "진행 ㄱ"으로 이 흐름 전체를 승인했다]

### 5.0 크기 가늠

슈퍼파워 v7 brainstorming의 크기 판단을 가져온다 [AI].
- 요청에 필요한 것이 다 들어 있으면 바로 한다. 무엇을 했는지 말한다.
- 작은 변경이면 채팅으로 한 줄 설명하고 **가벼운 길**로 간다. 명세 파일을 쓰지 않는다. worktree, worker, reviewer를 쓰지 않고 메인 세션이 직접 고친다. 검수는 관련된 확인 하나만 한다. 테스트나 명령을 돌리고, 화면을 바꿨으면 그 화면 스크린샷 한 장을 찍는다. 결과는 보고서 파일 대신 채팅으로 알린다 [AI: 실패 장면 5번은 probe뿐 아니라 build와 verify에도 해당한다].
- 프로젝트급이면 probe를 시작한다.
- 크기 판단은 사용자가 뒤집을 수 있다.

### 5.1 probe

**대화**
- 첫 메시지는 두 가지다. 질문을 건너뛰고 바로 시작해도 된다는 한 줄, 그리고 실제 장면을 묻는 열린 질문 하나다 [AI: v7 그대로].
- 한 메시지에 질문 하나만 한다. 예시 답 목록을 붙이지 않는다 [AI: v7의 "Each message ends with one question" 문구].
- 사용자가 막히거나 "어떻게 생각해?"라고 하면 기준안을 먼저 내놓는다. 빈칸으로 다시 묻지 않는다 [사용자: 이 대화에서 "너의 질문이 좀 모호한데? 그 기준을 어떻게 세워야 될까?"라는 말이 나온 뒤 기준안을 내자 바로 정리됐다].
- 추측은 추측이라고 표시한다. 사용자가 말한 것만 `사용자`로 적는다.
- 자료를 근거로 결론을 낼 때는 그 자료가 왜 그런 모양인지도 확인한다 [사용자 교정: 한기대 회의록에 정책 빈틈만 나온 건 기능명세가 이미 잘 돼 있었기 때문이었다].
- 질문이 다섯 개쯤 되면 "이 정도면 정리해도 될까요?"를 한 번 제안한다. 그다음은 사용자가 정한다 [AI].
- 짚어야 할 영역은 기능과 정책 둘 다다. 정책 쪽 점검 목록은 한기대 기획자가 짚은 항목에서 가져온다 [AI]: 데이터 보관 기간, 누가 무엇을 보는가(권한, 마스킹), 접근 기록, 예외 상황, 시스템 경계(어디까지가 이 시스템 일인가), 기존 규칙 따르기, 용어 해석 차이. 바이브 코딩에서는 기능도 자유롭게 바꿀 수 있으니, AI가 기능을 빼거나 바꾸자고 제안하는 것도 probe의 일이다 [사용자: "기능을 좀 더 자유롭게 변경할 수도 있겠지"].

**기능 고정 (proto 개념)** [사용자: proto 개념을 가져온다]
- 기능은 말로 정하고, 구조는 보고 정한다.
- 기능 범위는 질문 여러 개 대신 체크리스트 페이지 한 장으로 받는다. AI가 추론한 기능은 체크된 상태로, AI가 제안하는 기능은 `(제안)` 표시와 한 줄 이유를 붙여 체크 해제 상태로 둔다. 자유 입력 칸이 있다.
- 채팅에서 받은 답이 페이지보다 우선한다.

**구조 고르기 (proto 개념)**
- 화면이 있을 때만 한다.
- 기능은 같고 구조만 다른 저충실도 스케치를 2~3장 그린다. 구조의 축 하나를 고른다. 예를 들어 첫 화면에 무엇이 오는지, 이동 방식, 주 동작이 무엇인지다.
- 판정 질문은 하나다. "전부 아님"이면 가장 어긋난 지점을 묻고 2라운드를 그린다. 라운드는 최대 2번이다.
- 판정 기록과 고른 스케치만 남기고 스케치 코드는 버린다. build는 이 둘을 입력으로 처음부터 짓는다.

### 5.2 명세 형식 [사용자 승인]

한기대 기획 산출물(`ubion-dev/ai-learning-analytics`의 화면설계 md, 공통규칙, 요구사항 갭)에서 구조만 빌리고 분량은 줄인다. 화면 하나에 9KB인 분량을 그대로 쓰면 실패 장면 2번이 된다.

| 칸 | 내용 | 빌린 곳 |
|---|---|---|
| 목적, 범위, 하지 않는 것 | 몇 줄 | 화면 md 머리말 |
| 기능 | 항목마다 `사용자` / `AI 가정` 태그 (날짜와 출처는 필요할 때만) | 화면 md의 항목별 근거 |
| 케이스 | 기능마다 예외 상황 몇 줄: 발생 조건, 표시, 동작 | 화면 md의 케이스 절 |
| 공통 규칙 | 반복되는 결정을 한 번만 | 공통규칙 CR-xx |
| 확인 필요 | 결과를 바꾸는 것만 | 미확정 사항 |
| 구조 판정 | 스케치를 했다면 판정 기록 | proto verdict |

- 명세는 한 화면에 들어오게 쓴다. 길어지면 사용자가 꼭 봐야 할 부분을 위로 올린다 [AI].
- `AI 가정`은 결과를 바꿀 만한 것 몇 개만 보여주고 나머지는 접어 둔다 [AI].
- 위치는 프로젝트 안의 `docs/pact/<YYYY-MM-DD>-<주제>.md`다 [AI].

### 5.3 명세 검수

- 명세를 쓴 대화와 분리된 새 에이전트가 읽는다 [AI: 기획자가 RFP를 쓴 사람이 아니었던 것처럼].
- 두 가지를 한다. 하나는 v7 builder-check처럼 "이것만 보고 만들 수 있는가"를 보는 것이다. 다른 하나는 한기대 요구사항 갭처럼 양쪽에서 대조하는 것이다. 사용자가 말한 요구 중 명세에 빠진 것이 있는지, 명세 항목 중 어떤 요구에도 연결되지 않는 것이 있는지 본다.
- 질문은 세 무더기로 나눈다. 대화나 프로젝트에 이미 답이 있는 것은 명세에 채운다. 사소한 것은 AI가 정하고 `AI 가정`으로 적는다. 사용자만 답할 수 있고 결과를 바꾸는 것은 중요한 순서로 한 번에 묻는다. 질문 라운드는 이것 한 번뿐이다 [AI: v7 그대로].
- 답을 반영한 뒤 사용자 승인을 받는다. pact 전체에서 받는 유일한 승인이다.

### 5.4 build [사용자 승인]

- 계획은 AI가 안에서만 쓴다. 사용자에게 계획 승인이나 실행 방식 선택을 묻지 않는다 [AI: 슈퍼파워 writing-plans:184-194의 이중 승인을 뺀다].
- 작업마다 worker 에이전트 하나, 검토 에이전트(reviewer) 하나를 둔다. 둘 다 pact 안에 정의한다.
- **worker 계약은 tiers worker를 바탕으로 한다.**
  - 넘기는 형식은 목표, 맥락, 범위, 완료 기준 네 칸이다.
  - 범위 밖은 건드리지 않는다.
  - 완료 기준 명령은 실제 숫자로 보고한다.
  - 결과를 바꾸는 결정이면 `BLOCKED`로 멈추고 선택지와 자기 기본값을 올린다.
  - 사소한 결정은 알아서 정하고 `Decisions I made`에 적는다.
- **슈퍼파워 implementer에서 더한다.**
  - `DONE_WITH_CONCERNS` 상태
  - 짧은 자기 검토: 빠진 요구사항, 과잉 구현, 기존 패턴을 따랐는지, 테스트가 진짜 동작을 확인하는지
  - 자세한 보고는 파일로 쓰고 답장은 짧게
- **reviewer는 슈퍼파워 task-reviewer를 바탕으로 한다.**
  - "Do not trust the report": 보고를 주장으로 보고 diff와 직접 대조한다.
  - Missing / Extra / Misunderstood 세 갈래로 본다. Extra는 `AI 가정` 태그와 대조한다.
  - 심각도를 나눈다(Critical / Important / Minor).
  - 읽기 전용이다.
- 슈퍼파워의 "Don't guess or make assumptions", "Ask them now"는 쓰지 않는다.
- 결정 기록은 Ruling 형식으로 남긴다 [AI]: `Ruling: <무엇을 정했나> — <왜> — <틀리면 무엇을 잃나>`. 이 기록이 명세의 `AI 가정`에 반영되고 verify 보고서에 실린다.
- 작업은 사이사이 멈추지 않고 이어 간다. 멈추는 경우는 되돌리기 어려운 행동, `사용자` 항목을 바꿔야 할 때, 두 번째 BLOCKED뿐이다 [AI].
- 격리된 작업 공간(worktree)에서 일한다. verify를 통과하면 묻지 않고 로컬에서 커밋하고 지금 브랜치에 합친 뒤 보고서로 알린다. push는 외부 공개라 그때만 묻는다 [사용자 승인: 슈퍼파워 finishing-a-development-branch처럼 합치기, PR, 버리기를 묻지 않는다. git으로 되돌릴 수 있으니 "되돌리기 어려운 것"에 넣지 않는다]. 실패하면 systematic-debugging 방식(원인 먼저, 수정은 그다음)을 쓴다 [AI: 슈퍼파워에서 남길 만한 부분].

### 5.5 verify [사용자 승인]

- 명세에서 시나리오를 뽑는다. 기능마다 정상 흐름 하나, 케이스마다 하나다.
- 명세에 없는 "처음 써 보는 사람" 시나리오도 더한다. 엉뚱한 순서로 누르기, 빈 값 넣기, 뒤로 가기 같은 것이다. 만든 뒤에 하는 두 번째 probe다. 실패 장면 4번을 막는 장치다 [AI].
- AI가 브라우저를 돌리고 모든 시나리오의 스크린샷을 찍어 보고서로 만든다 [사용자: "ai에게 돌리고 모든 시나리오에 대한 스크린샷을 찍은 후 보고서 형태"]. 웹은 Playwright를 기본으로 쓴다 [AI]. 대상 프로젝트에 이미 Playwright가 있으면 그것을 쓴다. 없으면 대상 프로젝트의 `package.json`은 건드리지 않고 pact 전용 위치에 설치한다. 처음에 브라우저를 내려받을 때는 한 줄로 알리고 진행한다 [AI].
- 보고서에는 시나리오마다 결과(통과, 실패, 의심), 스크린샷, 확인한 명세 항목을 적는다. 맨 위에는 실패와 의심만 모으고 통과는 접는다 [AI]. 명세 대조 결과(빠진 것, 더한 것, 잘못 이해한 것)와 build의 Ruling 목록을 같이 싣는다.
- 화면이 없는 프로젝트는 시나리오를 명령으로 실행하고 스크린샷 대신 실행 결과를 붙인다 [AI].
- 실패하면 verify가 고치지 않고 build로 되돌린다. 고칠지는 4절의 기준을 따른다 [AI].
- 완료라고 말하기 전에 증거를 확인한다. 이 원칙은 슈퍼파워 verification-before-completion에서 가져오고, "lying" 같은 위협 문구는 뺀다 [AI].

## 6. 문구 원칙

슈퍼파워 v7 문구를 조사한 결과다. 사용자가 이렇게 말했다. "슈퍼파워에서 적용한 스킬 문구같은거 참고해. 그런건 연구해볼만한 가치가 있으니까"

**쓰지 않는다** (과잉 집행의 원인)
- 1% 규칙과 "This is not negotiable." (using-superpowers:11, :15)
- Iron Law, "Delete it. Start over.", "No exceptions" (test-driven-development:34, :37-45, :254)
- "Violating the letter of the rules is violating the spirit of the rules." (TDD:14, verification-before-completion:12)
- 금지 응답 목록 (receiving-code-review:30)
- 세션 시작 훅으로 긴 강제 문구를 넣는 방식. 넣는다면 150단어 이하의 짧은 안내만 넣는다.

**가져온다**
- 메시지 모양 계약: "That's the whole message.", 한 메시지에 질문 하나
- 예시 질문과 추측을 먼저 내밀기 (brainstorming:78-81)
- 재진술할 때 추측을 표시하고 출처를 구분하기 (brainstorming:120-121, :64-65)
- 크기 판단 표, builder-check 세 무더기, Ruling 기록
- 행동을 바로잡는 Red Flags 표. "기본값은 말로 밝혀라" 같은 것만 가져오고 "그래도 무조건 해라"는 버린다.
- description에는 "언제 쓰나"만 적고 절차 요약은 넣지 않는다 (writing-skills:150)
- 사용자의 짜증 신호 목록 (systematic-debugging:233)
- 형식 선택 기준: 모양이 잘못 나오는 실패에는 금지 목록 대신 레시피나 계약 형식을 쓴다. 조건에 따라 다른 행동은 눈으로 확인할 수 있는 조건에 건다 (writing-skills:468-475).
- 설득 강도는 협업형 기준인 "Moderate Authority + Unity"를 쓴다 (persuasion-principles:131).

**단계 넘기기**
- 강한 description 대신 눈으로 확인할 수 있는 조건으로 넘긴다. 예: "명세에 사용자 태그 항목이 있고 승인됐으면 build", "build가 DONE이면 verify".
- 단계 파일의 마지막 줄에는 "다음은 X" 한 문장만 둔다.
- 지금 어느 단계인지는 한 줄로만 보인다.

## 7. pact를 시험하는 방법

슈퍼파워 writing-skills의 RED-GREEN-REFACTOR를 쓰되, 시험할 실패의 방향을 바꾼다.
- 슈퍼파워는 규칙을 어기는지를 압박 시나리오로 시험한다. pact가 막을 실패는 반대 방향이다. 작은 일에 probe 시작, 확인만 받는 질문, 질문 여러 개 묶기, 구현 방식을 사용자에게 묻기, 두 번 승인받기다.
- 그래서 문구 마이크로 테스트를 주로 쓴다. 지침 없는 대조군을 두고, 변형마다 5회 이상 돌리고, 결과는 사람이 읽는다. 대조군에서 실패가 나오지 않으면 지침을 쓰지 않는다.
- "언제 쓰지 말아야 하는가"를 시험하는 반례 시나리오가 크기 판단의 시험이다.
- 실패 장면 1~5번이 각각 시나리오 하나 이상이 된다.
- 시험은 결과물이다. 규칙마다 거쳐야 하는 관문이 아니다. tiers의 `tests/`처럼 `plugins/pact/tests/`에 시나리오와 실행 스크립트를 남긴다. 개발 중에는 AI가 돌리고 결과를 읽으며, 사용자에게는 요약만 보고한다. 문구를 바꿀 때마다 관련 시나리오를 다시 돌린다 [AI].
- 시험은 슈퍼파워 훅이 없는 깨끗한 프로필에서 돌린다. 이 폴더에는 슈퍼파워가 켜져 있어서 using-superpowers 훅이 결과를 오염시키기 때문이다. bench 플러그인의 깨끗한 프로필 방식을 참고한다 [AI].

## 8. 첫 적용: pact 자체

처음 쓸 프로젝트는 pact 자신이다 [사용자: "지금 이 프로젝트"]. 이 설계 대화가 사람이 손으로 돌린 첫 probe다. 대화에서 나온 교정은 probe 규칙에 반영했다(5.1의 기준안 먼저, 근거 자료 확인). 처음 판은 슈퍼파워 v7이 깔린 이 폴더에서 만든다. pact가 7절의 시험을 통과하면 `plugins/pact/.claude/settings.json`에서 슈퍼파워를 끄고 pact를 이 프로젝트 범위로 켠다. 그 뒤 작업은 pact로 한다. 전역으로 켜는 건 사용자가 말할 때 한다 [AI]. `chenjing-plugins` 루트의 로컬 슈퍼파워 설치는 그때 같이 정리할지 묻는다.
