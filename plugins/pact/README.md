# pact

RFP를 받은 수행사처럼 일하는 바이브 코딩 플러그인. 사용자는 발주처, AI는 수행사다. 무엇을 만들지는 함께 정해 짧은 명세로 계약하고(probe), 어떻게 만들지는 AI가 정해서 이행하고(build), 다 만든 것을 AI가 직접 써 보며 모든 시나리오를 스크린샷으로 남겨 검수한다(verify).

수정 기준은 하나다. 명세의 모든 항목에 누가 정했는지 태그가 붙는다. 사용자가 말한 `[사용자]` 항목은 바꾸기 전에 묻고, AI가 채운 `[AI 가정]` 항목은 알아서 바꾸고 기록한다. 데이터 삭제, 외부 공개, 비용처럼 되돌리기 어려운 일은 누가 정했든 묻는다.

## 설치

```
/plugin install pact --marketplace chenjingdev/chenjing-plugins
```

명세 검사, 기능 체크리스트 페이지, 검수 보고서 같은 도우미 스크립트를 node로 돌린다. node 18 이상이 깔려 있어야 한다.

## 켜는 법

따로 외울 명령이 없다. "○○ 만들어 줘", "이거 고쳐 줘"처럼 말하면 켜진다. 직접 부르려면 `/pact:pact`.

켜지면 먼저 크기를 가늠한다. 필요한 것이 다 들어 있는 일은 바로 하고, 작은 변경은 가벼운 길(직접 고치고 확인 하나, 결과는 채팅)로 처리한다. 프로젝트급만 아래 흐름을 탄다.

```
"…만들어 줘 / 고쳐 줘" 또는 /pact:pact
 ├─ 0. 크기 가늠 ─ 작은 일 → 가벼운 길 (직접 고침 + 확인 하나)
 ├─ probe
 │   1. 넓게 펼치기   기능 지도(갈래 5~8개)를 먼저 펼치고, 어디부터 볼지 하나만 묻는다
 │   2. 타고 내려가기  고른 갈래부터 넓혔다가, 진짜 갈림길만 걸러 낸 안 + 추천으로 묻는다
 │                  (들러리 안은 빼고, 하나만 남으면 정해서 알림)
 │   3. 좁히기       지도 전체를 갈래별 체크리스트 한 장으로 (AI 제안은 체크 해제 + 이유)
 │   4. 구조 고르기   화면이 있으면 스케치 2~3장 → 판정 하나, 최대 2라운드
 │                  ("알아서"로 맡기면 3·4는 AI가 정하고 채팅에 알림)
 │   5. 명세 작성
 │   6. 명세 검수    다른 에이전트가 빌더 입장 + 요구 대조 → 사용자 몫만 한 번에 질문
 │   ── 사용자 승인 (유일한 승인) → spec.mjs approve로 기록. 기록이 없으면 build가 시작되지 않는다 ──
 ├─ build    worker 구현 → reviewer 대조(worker 걱정은 훅이 reviewer 지시에 붙인다), 결정은 Ruling으로 기록
 └─ verify   시나리오 → 브라우저 실행 + 스크린샷 → 보고서. 실패하면 build로 되돌림
            고친 뒤엔 실패·의심·미검증과 고친 파일이 닿는 시나리오만 다시 검수
            완료 검사 통과 → 로컬 커밋·합치기 → 보고서로 알림 (push만 물음)
```

중간에 멈춰도 명세의 `status`(draft → approved → building → verifying → done)를 보고 이어 한다.

## 0.6.0에서 바뀐 것

지난 판들에서 지시로만 지키던 곳이 샜다. 0.6.0은 그곳을 코드와 기록으로 지킨다. 자세한 것은 아래 절에 있다.

- 훅: `hooks/guard.mjs` 하나가 PreToolUse와 SubagentStop에 걸린다. pact와 상관없는 호출은 읽지도 않고 통과시킨다(메인 세션이 agent id 꼴 `to`로 보내는 SendMessage만 받는 쪽을 찾으려고 `log/`를 읽는다).
- 승인·위임 기록: `spec.mjs approve`·`delegate`가 사용자 말을 대화 기록에서 찾아 남긴 기록이 있어야 만들기가 시작된다.
- 결과 잠금: `results.json`은 verifier만, `verification.json`·`approvals.jsonl`·`log/`는 훅과 스크립트만 쓴다. 완료 검사가 verifier가 끝날 때 남긴 지문과 `results.json`을 비교한다.
- `summary.json`: 보고서 맨 위 칸은 `results.json` 대신 메인 세션이 여기에 쓴다.
- 검수 번호 짝: spec-checker가 '사용자만 답할 수 있음' 항목마다 `검수 n`을 붙이고, 명세에 짝이 없으면 승인과 완료 검사가 거절한다.
- `[사용자]` 줄 확인: 승인 뒤 `[사용자]` 줄이 바뀌면 worker 부르기·`snapshot`·완료 검사가 거절하고, 사용자 말을 인용해 다시 승인하면 이어 간다.
- worker 걱정 넘기기: reviewer를 부를 때 훅이 그 작업의 worker 답에서 `## 걱정·위험`을 꺼내 지시 끝에 `## worker 걱정`으로 붙이고, reviewer는 답의 `## worker 걱정 처리`에 걱정마다 어떻게 했는지 적는다.
- worker 상태: `DONE`과 `BLOCKED` 둘이다. 마음에 걸리는 것은 상태와 상관없이 `## 걱정·위험`에 쓰고, 작업 지시에는 커밋 꼬리말을 넣지 않는다.

## 남는 것

| 위치 | 내용 |
|---|---|
| `docs/pact/<날짜>-<주제>.md` | 명세. 한 화면 분량, 항목마다 `[사용자]`/`[AI 가정]`, 결정 기록 |
| `.pact/<날짜>-<주제>/report.html` | 검수 보고서. 맨 위에 결론과 할 일(명세 `## 확인 필요`의 검수 항목이 저절로 올라온다), 그다음 실패·의심·미검증과 명세와 다른 것, 승인 기록(승인인지 위임인지, 인용한 말, 승인 뒤 바뀐 `[사용자]` 줄). 통과·작업 기록·결정 기록은 접힘 |
| `.pact/<날짜>-<주제>/` | 실행 폴더. 명세 파일명(날짜 포함)으로 구분한다. 체크리스트, 스케치, 작업 보고, 검수 기록(`verification.json`)이 들어가고 스스로 git에서 빠진다 |
| `.pact/<날짜>-<주제>/log/subagents.jsonl` | 하위 에이전트가 끝날 때마다 훅이 마지막 답을 한 줄씩 덧붙인 기록. reviewer에게 붙일 worker 걱정도 여기서 읽는다 |
| `.pact/<날짜>-<주제>/approvals.jsonl` | 승인·위임 기록. `spec.mjs approve`·`delegate`가 사용자 말을 대화 기록에서 찾아 맞춰 보고 한 줄씩 덧붙인다. 그때의 `[사용자]` 줄도 담는다 |
| `.pact/<날짜>-<주제>/results.json` | 검수 결과. verifier만 쓴다. 앞 검수의 결과는 `snapshot`이 `results-round<n>.json`으로 남긴다 |
| `.pact/<날짜>-<주제>/summary.json` | 보고서 맨 위 칸(`headline`·`todo`·`changes`·시나리오별 `decision`). 메인 세션이 쓴다 |

화면 검수에는 Codex CUA를 쓴다. 브라우저에서 결과물을 직접 써 보고 단계마다 스크린샷(JPEG)을 남긴다. 도구 이름은 호스트마다 달라 pact가 찾아 쓴다. 메인 세션이 검수 전에 한 번 확인해서, 쓸 수 없으면 오류를 바로 알리고 명령과 HTTP 요청으로 볼 수 있는 것만 확인한다. 화면으로만 볼 수 있는 단계는 `미검증`으로 남고, 미검증이 있으면 완료가 되지 않는다.

## 승인 기록

만들기는 승인이나 위임 기록이 있어야 시작한다. 사용자가 말로 한 승인을 코드가 기록으로 바꾼다.

```
node <pact>/scripts/spec.mjs approve <명세> - <<'EOF'    # 승인 질문의 답: "승인", "ㄱㄱ", "좋아, 만들어" (질문 도구의 답도 된다)
<사용자 말을 그대로>
EOF
node <pact>/scripts/spec.mjs delegate <명세> - <<'EOF'   # 승인까지 맡긴다는 말: "끝까지 알아서 해", "승인 없이 만들어" (사용자가 직접 쓴 말만, 질문 도구의 답은 안 된다)
<사용자 말을 그대로>
EOF
```

말은 `spec.mjs approve <명세> "<사용자 말>"`처럼 인자로 넘길 수도 있다. 다만 큰따옴표 안의 백틱과 `$`는 셸이 먼저 풀어 버리므로, 따옴표 붙인 heredoc(`-`)으로 표준 입력에 넣는 쪽이 안전하다.

- 두 명령은 인용한 말을 이 대화의 기록(`<설정 폴더>/projects/*/<세션 id>.jsonl`, 세션 id는 `CLAUDE_CODE_SESSION_ID`)에서 사용자가 한 말로 찾아 맞춰 본다. 작업 알림, 대화 요약, 인자 없는 명령 메시지, `system-reminder`, 다른 세션이 보낸 말, 도구 결과 안의 말은 사용자 말이 아니다. 질문 도구(AskUserQuestion)로 고른 답과, 에이전트가 일하는 도중에 사용자가 친 말(대화 기록에는 `attachment` 줄로 남는다)은 사용자 말이다. 단 질문 도구의 답은 승인에만 쓴다. 띄어쓰기와 문장부호는 빼고 맞춘다. 정리해서 10자 이하인 짧은 말("승인")은 메시지 전체와 같아야 하고, 그보다 길면 메시지 안에 들어 있으면 된다.
- 슬래시 명령의 인자(R9): 사람이 친 슬래시 명령(`/pact:pact 출결 앱 만들어 줘. 끝까지 알아서 해`)의 인자 글도 사용자 말이다. 대화 기록에서 `<command-name>`이 든 user 줄 가운데 origin이 human이고 `<command-args>`에 글이 있는 줄만 읽고, 인용은 그 인자 글에 대고 맞춰 본다. 명령 이름과 태그는 뺀다. 인자가 없거나 비었거나 공백뿐인 명령, origin이 없는 내장 명령(`/effort`, `/mcp` 등), 모델이 Skill 도구로 부른 스킬의 인자(assistant의 `tool_use`로만 남는다)는 사용자 말이 아니다. 인자 글은 부탁 한 덩이를 한 줄에 이어 쓴 것이라 위임에 한해 짧은 말이 인자 전체나 인자 안의 문장 하나(줄바꿈, 또는 `.`·`!`·`?`·`…` 뒤의 공백으로 나뉜 한 덩이)와 같으면 맞는다. `끝까지 알아서 해`는 `출결 앱 만들어 줘. 끝까지 알아서 해`의 뒤 문장이라 맞고, `끝까지 알아서 해줘 근데 승인은 내가 할게`는 문장 하나 안에 다른 말이 있어 맞지 않는다. 승인은 늘 메시지 전체와 같아야 한다.
- 승인은 spec-checker가 끝난 뒤의 말이어야 한다(`log/`의 가장 최근 spec-checker 기록보다 뒤). spec-checker 기록이 없으면 거절한다. 이미 검수했는데도 기록이 없으면 훅이 돌지 않는 것이니 플러그인 데이터 폴더의 `hook-error.log`를 본다. 이미 기록이 있으면 승인이든 위임이든 인용하는 말이 앞 기록들에 쓴 어떤 메시지보다 새것이어야 한다. 위임 중에 `[사용자]` 줄을 바꾸고 옛 위임 말로 다시 기록해 아래 확인을 비켜 가지 못하게 하려는 것이다. 처음 기록하는 위임은 처음 부탁에 있는 말이어도 된다. 위임은 질문 도구의 답을 받지 않는다(R2): 질문 하나의 답으로 온 "알아서"는 그 질문만 맡긴 것이라, `delegate`에 넣으면 질문 도구의 답이라고 거절하고 승인 질문의 답이면 `approve`로 기록하라고 알린다. 위임은 사용자가 직접 쓴 말(친 말, 일하는 도중에 친 말, 슬래시 명령의 인자)을 인용한다. 같은 말을 직접 쓴 것도 있으면 그쪽으로 기록한다.
- 맞으면 인용, 메시지 전문, 메시지 uuid와 시각, 대화 기록 경로, 기록한 시각, 종류(approve 또는 delegate), 그때의 `[사용자]` 줄(`user_lines`)을 `approvals.jsonl`에 한 줄 덧붙인다. status가 `draft`면 `approved`로 바꾸고, 만드는 중이거나 검수 중이면 status는 그대로 두고 기록만 더한다. 못 찾거나 확인하지 못하면 거절하고(종료 코드 1) 까닭과 대신 할 일을 한 줄로 알린다.
- 검수 번호의 짝(F5): spec-checker는 '사용자만 답할 수 있음' 항목마다 `검수 1`, `검수 2` … 번호를 붙인다. 기록할 때(approve·delegate)와 완료 검사에서 가장 최근 spec-checker 답의 그 칸을 읽어 번호마다 명세에 아래 셋 중 하나가 있는지 본다: 물어서 답을 받은 줄의 `[사용자: 검수 n]`, 사용자가 맡긴 줄의 `[AI 가정: 검수 n 맡김]`, `## 확인 필요`의 `- 검수 n: 안 물은 까닭`(위임 중이면 까닭은 '위임이라 기본안으로 정함'). 짝으로 세는 태그는 기능·공통 규칙 항목의 줄(머리 줄과 케이스 줄, 접힌 칸 포함) 끝에 단 것이다. lint가 태그로 읽는 규칙 그대로라서 목적·범위 칸의 태그, 줄 가운데의 태그, 전각 콜론(`：`)의 태그는 세지 않는다(전각 콜론이면 거절 문구가 그렇다고 알린다). spec-checker는 번호를 1부터 붙이되 명세에 이미 번호가 있으면 가장 큰 번호 다음부터 붙인다. 짝이 빠진 번호는 그 번호를 알리고 거절한다. 칸이 "없음"이면 통과하고, 번호도 "없음"도 읽지 못하면 거절한다. 답에 같은 이름의 머리말이 있어도 `#` 제목 칸을 먼저 보고, 번호나 "없음"을 읽은 칸을 고른다. 위임은 spec-checker 기록이 아직 없어도 기록되지만, 완료 검사는 새 명세에 spec-checker 기록이 없으면 거절한다.
- 승인 뒤 바뀐 `[사용자]` 줄(F3): `[사용자]`나 `[사용자: …]` 태그가 붙은 기능·규칙 줄은 그 케이스 줄과 함께 승인 기록의 `user_lines`에 들어간다. `[AI 가정]` 항목 밑 케이스 줄에 `[사용자]` 태그가 붙어 있으면(검수 질문에 사용자가 답한 케이스) 머리 줄은 빼고 그 줄만 따로 들어간다(`F3/1`: 그 항목의 `[사용자]` 케이스 줄 가운데 첫째). 그래서 머리 줄과 다른 케이스 줄은 AI가 고쳐도 걸리지 않고, F5가 짝으로 센 줄은 F3가 지킨다. `pact:worker` 부르기(훅), `snapshot`, 완료 검사가 가장 최근 기록의 줄과 지금 명세를 견줘서, 글·태그가 바뀌었거나 줄을 빼거나 더했으면 바뀐 줄을 알리고 거절한다. 바꿔 달라고 한 사용자 말을 인용해 `approve`로 다시 기록하면 이어 간다. 사용자가 파일을 직접 고쳤으면 한 번 묻고 그 답을 인용한다. `[AI 가정]` 줄만 바뀐 것은 막지 않는다.
- 위험 항목: 기능·규칙 줄(케이스, 접힌 칸 포함)에 `[위험: 지우기|공개|비용]` 표시가 있으면 `delegate`가 거절하고 승인을 받으라고 알린다. 콜론을 빠뜨린 `[위험 지우기]`·`[위험-지우기]`도 표시로 읽는다. 표시가 빠졌는지는 코드가 낱말로 찾지 않는다(낱말로 찾으면 진짜 명세 17개 모두에 걸려 위임이 늘 멈춘다).
- 기록이 없으면 `set-status approved`·`building`, `pact:worker` 부르기(훅), `verification.mjs snapshot`이 거절한다. 위임 기록이면 만들기를 시작할 때(`set-status building`, `pact:worker`) 지금 명세를 다시 보고, 위험 표시가 생겼거나 인용을 다시 맞춰 볼 수 없으면 거절한다. 질문 도구의 답으로 만든 옛 위임 기록(기록에 `answer_question`이 있다)도 거절한다. 사용자에게 승인을 다시 받아 `approve`로 기록하거나, 직접 쓴 새 말을 인용해 `delegate`로 다시 기록하면 이어 간다.
- 옛 명세(frontmatter `pact: 1`이고 승인 기록이 없고 status가 approved·building·verifying·done)는 기록 없이 이어 가고 `참고: 옛 판이라 승인 기록 없음`을 알린다. 검수 번호 짝과 `[사용자]` 줄 확인도 건너뛰고, 보고서 맨 위 상자와 승인 기록 칸에 '옛 판이라 승인 기록 없음'이라고 적는다. `pact: 1`이어도 draft면 기록이 있어야 한다. `spec.mjs new`는 `pact: 2`로 쓴다.

## 완료 검사

검수를 시작할 때 명세와 코드의 내용을 `.pact/<run-id>/verification.json`에 기록하고(`snapshot`), 결과 전체와 시나리오마다 그때의 `verification_id`를 적는다. 완료 전에 기능·케이스·처음 쓰는 사람 시나리오가 다 있는지, 단계마다 증거(스크린샷 또는 명령 출력과 종료 코드)가 있는지, 검수한 코드가 그대로 합쳐졌는지 본다. 스크린샷이 없거나 빈 파일이거나 실행 폴더 밖이면 그 시나리오는 미검증이다.

```
node <pact>/scripts/verification.mjs snapshot <명세> <worktree> <ui|command>   # 검수 시작 때
node <pact>/scripts/report.mjs <run-dir>                                         # 보고서 + 완료 검사 결과
node <pact>/scripts/verification.mjs finish <명세> <프로젝트>                     # 합친 뒤, 원래 프로젝트 폴더에서
```

`finish`가 통과할 때만 명세가 `done`이 된다. `spec.mjs set-status done`은 막혀 있다. 이 검사는 기록이 빠졌는지만 본다. 실제로 써 봤는지는 verifier의 일이다. 승인 기록도 본다: spec-checker가 짚은 `검수 n`의 짝과 승인 뒤 바뀐 `[사용자]` 줄(위 "승인 기록"). 옛 판은 건너뛴다.

고친 뒤에는 `snapshot`을 다시 만든다. 새 ID가 나오고 출력의 `changed_files`에 고친 파일이 든다. 이때 앞 결과(`results.json`)를 스크립트가 `results-round<n>.json`으로 남긴다(출력의 `saved_results`). `n`은 있는 round 번호 다음 번호이고, 있는 파일은 덮어쓰지 않으며, verifier가 아직 다시 돌지 않아 가장 높은 번호의 파일과 같으면 남기지 않는다. 실패·의심·미검증이었던 시나리오와 고친 파일이 닿는 시나리오만 다시 돌리고, 나머지는 앞 판의 결과를 그대로 둔다. 완료 검사는 같은 검수의 앞 판 ID를 인정한다.

### 결과 파일과 보고 칸

`results.json`은 verifier만 쓴다. 메인 세션이 보고서 맨 위 칸을 채우려고 고치던 것을 막으려고, 그 칸들(`headline`·`todo`·`changes`와 시나리오마다 `decision`)은 `.pact/<run-id>/summary.json`에 쓴다.

```json
{ "headline": "…", "todo": ["…"], "changes": ["…"], "decision": { "<시나리오 id>": "…" } }
```

`report.mjs`는 `results.json`, `summary.json`, 명세 `## 결정 기록`의 `Ruling:` 줄(rulings)을 합쳐 지금과 같은 보고서를 만든다. 칸마다 `summary.json`에 있으면 그것을, 없으면 `results.json`의 같은 칸을 읽는다. 0.5.0에서 `results.json`에 칸을 쓴 진행 중인 판이 그대로 보인다. 완료 검사는 의심의 `decision`도 같은 순서로 찾고, `summary.json`을 읽지 못하거나 칸의 모양이 틀리면 막는다.

검수 보고서(`report.html`)에는 승인 기록 칸도 있다. 기록마다 승인인지 위임인지, 인용한 말과 메시지 전문, 기록한 시각을 보이고, 앞 기록 뒤로 바뀐 `[사용자]` 줄은 그것을 다시 승인한 인용 옆에 둔다. 아직 다시 승인하지 않은 바뀐 줄이 있으면 맨 위에서도 알린다. 옛 판은 '옛 판이라 승인 기록 없음'이라고 적는다. 이 줄은 맨 위 상자에도 늘 있다. 메인 세션이 `summary.json`에 쓴 headline과 상관없이 스크립트가 붙이고, 새 판에는 없다. 완료 검사의 참고 줄(`notes`)도 싣고, 명세 `## 확인 필요`의 `검수 n` 항목(사용자에게 묻지 않고 정한 것)은 할 일 칸에 저절로 올린다.

완료 검사는 `results.json`의 지금 sha256을 가장 최근 verifier가 끝날 때 훅이 남긴 지문과 비교한다. 다르거나, verifier 기록이 없거나, 기록에 지문이 없으면 막는다. 코드를 고쳐야 하면 build로 되돌려 고친 뒤 verifier로 다시 검수하라고, 코드는 맞고 `results.json`만 바뀐 것이면 verifier만 다시 돌리라고 알린다. 훅이 막지 못하는 길(변수로 만든 경로, 파일에 적어 둔 스크립트, MCP 도구)로 바뀐 것을 잡는 마지막 그물이다. 0.6.0 전에 만든 명세(옛 판)에 verifier 기록이 하나도 없으면 비교를 건너뛰고 `참고:`로 알린다. 0.6.0에서 verifier가 다시 돌아 기록이 생긴 옛 판은 비교한다.

예전 방식의 `.pact/<주제>/` 폴더는 건드리지 않는다. 그 안에 `wt`가 남아 있으면 `run-dir`이 멈추고 사람이 정리한다.

## 훅

`hooks/hooks.json`이 PreToolUse와 SubagentStop에 훅 하나(`hooks/guard.mjs`)를 건다. 플러그인 훅은 pact를 쓰지 않는 대화에서도 도는 터라, `.pact/`·`docs/pact/`를 만지지도 않고 pact 에이전트나 스크립트도 아닌 호출은 아무것도 읽지 않고 바로 통과시킨다(메인 세션이 agent id 꼴 `to`로 보내는 SendMessage만 예외다. 받는 쪽이 reviewer인지 `log/`를 읽어 본다).

- PreToolUse: 메인 세션이 `pact:worker`를 부를 때 작업 지시의 판(`맥락` 칸의 run-dir)에 승인·위임 기록이 없거나 승인 뒤 `[사용자]` 줄이 바뀌었으면 막는다(옛 판은 통과). 지시문에서 판을 못 찾으면 "맥락 칸에 run-dir과 작업 번호를 넣는다"로 막는다. 위임 기록이면 지금 명세의 위험 항목과 인용을 다시 본다. 하위 에이전트가 Bash로 `spec.mjs approve`·`delegate`·`set-status`를 부르면 막고, 메인 세션도 approve·delegate 앞에 환경 변수(`HOME=`, `CLAUDE_CODE_SESSION_ID=`, `CLAUDE_CONFIG_DIR=` 등)를 덮어쓰면 막는다. 막을 때는 까닭과 대신 할 일을 한 줄로 알린다.
- PreToolUse(결과 잠금): 실행 폴더 바로 밑의 파일은 정해진 쪽만 쓴다. `results.json`·`results-round*.json`은 `pact:verifier`만, `verification.json`은 `verification.mjs snapshot`만, `approvals.jsonl`과 `log/` 밑은 훅과 pact 스크립트만 쓴다. 메인 세션과 다른 하위 에이전트가 Edit·Write·MultiEdit·NotebookEdit로 쓰거나 Bash로 쓰면(`>`·`>>`·`tee`·`sed -i`·`perl -i`, `cp`·`mv`·`rm`·`truncate`·`touch`의 대상, `python -c`·`node -e`·heredoc 한 줄 스크립트의 `open(…, 'w')`·`writeFileSync` 같은 쓰기) 막고, 까닭과 대신 할 일을 한 줄로 알린다. 읽기(`cat`·`jq`·`grep`)와 pact 스크립트 호출은 막지 않는다. `<run-dir>/wt/` 밑, `summary.json`·`report.html`·`shots/`·`plan.md`·`tasks/`, 그리고 명세(`docs/pact/<run-id>.md`)가 없는 폴더는 대상이 아니다. 옛 판도 똑같이 건다. 이름은 대소문자를 가리지 않고 본다(이 컴퓨터의 파일 시스템이 가리지 않는다). 훅이 못 보는 길도 있다: 변수로 만든 경로, 파일에 적어 둔 스크립트, MCP 도구(메인 세션도 CUA의 `js`로 `fs.writeFileSync`를 불러 실행 폴더에 쓸 수 있고, MCP 도구는 `hooks.json`의 matcher에 없다). 그 길은 완료 검사의 지문 비교가 막는다.
- 한계(결과 잠금): 훅은 명령 글에서 쓰기를 찾는 것이라, 셸 한 줄 안의 쓰기 가운데 읽지 못하는 꼴이 있다: `perl -e`·`ruby -e`·`awk`, `sed`의 `w` 명령, `curl -o`, `tar -C`, python의 `os.open`, node의 `fs.openSync`·`fs.promises.writeFile`. 이 꼴들은 막지 않는다. 위 결과 잠금 항목에 적은 못 보는 길(변수로 만든 경로, 파일에 적어 둔 스크립트, MCP 도구)도 마찬가지다. 이 길들로 결과 파일을 바꾸면 완료 검사의 지문 비교가 잡는다. 지문은 verifier가 끝날 때 훅이 남긴 `results.json`의 sha256이고, 지금 파일과 다르면 완료 검사가 막는다.
- PreToolUse(worker 걱정): 메인 세션이 `pact:reviewer`를 부르면 지시문의 판(보고서 경로의 run-dir)과 작업 번호(`작업 번호 n`, 없으면 보고서 경로가 하나일 때 그 번호)로 `log/`에서 그 작업의 가장 최근 worker 답을 찾아 `## 걱정·위험` 칸을 지시 끝에 `## worker 걱정`으로 붙이고 통과시킨다(입력의 다른 칸은 그대로 둔다). 판은 찾았는데 작업 번호를 못 읽으면 걱정이 말없이 빠지지 않게 호출을 막고, 까닭과 대신 할 일(지시 맨 앞에 `작업 번호 3`처럼 작업 번호를 숫자로 적어 다시 부른다)을 한 줄로 알린다. 지시문에서 판을 못 찾았을 때, 그 번호의 worker 기록이 없을 때, 걱정이 '없음'이거나 비었을 때, 이미 `## worker 걱정`이 있을 때는 그대로 통과한다. 메인 세션이 같은 reviewer에 SendMessage로 보낼 때도, `to`가 `log/`에 reviewer로 남은 agent id이면 그 작업의 가장 최근 worker 답(고친 뒤의 답)의 걱정을 message 끝에 붙인다. 이쪽은 막지 않고 그대로 통과한다: `to`가 agent id가 아니거나 `log/`에 없을 때, 그 reviewer의 작업 번호를 모를 때, 글이 그 reviewer의 작업과 다른 작업 번호를 말할 때, 이미 `## worker 걱정`이 있을 때, worker 기록이 없거나 걱정이 없을 때. 걱정은 worker 보고서가 아니라 `log/`의 worker 답에서 가져온다. 에이전트에 이름을 붙여 이름으로 보내면 받는 쪽을 알 수 없어 붙이지 않는다. SendMessage는 글에 pact 흔적이 없어도 `to`가 id 꼴이면 cwd 프로젝트(또는 글이 가리키는 프로젝트)의 `.pact/` 밑 `log/`를 읽어 받는 쪽을 찾는다. pact 프로젝트가 아니면 읽을 것이 없고, 아무것도 쓰지 않는다.
- 한계: tiers 플러그인의 delegate가 켜져 있으면 같은 `pact:reviewer` 호출에 tiers(model 고정)와 pact(걱정 붙이기)가 둘 다 입력을 바꾸고, 어느 쪽이 남는지는 정해져 있지 않다(불확실). tiers delegate는 기본으로 꺼져 있다.
- SubagentStop: `pact:spec-checker`·`pact:reviewer`·`pact:worker`·`pact:verifier`가 끝나면 마지막 답을 그 판의 `<run-dir>/log/subagents.jsonl`에 한 줄 덧붙인다. 실행 폴더는 하위 에이전트의 첫 지시에 든 경로로 찾고, 없으면 그 프로젝트에서 가장 최근에 바뀐 진행 중 명세로 찾는다. `pact:verifier`가 끝날 때는 그 순간의 `results.json` sha256도 같은 줄에 적는다. 완료 검사가 이 지문과 지금 파일을 비교한다. `pact:reviewer`의 작업 번호는 첫 지시에서 훅이 붙인 `## worker 걱정` 칸 앞까지만 읽는다. 걱정 글 속의 번호와 경로가 작업 번호와 판을 바꾸지 않게 한다.
- 훅이 고장나도 대화를 막지 않는다. 오류는 플러그인 데이터 폴더(`${CLAUDE_PLUGIN_DATA}`, 없으면 `~/.claude/plugins/data/pact-chenjing-plugins`)의 `hook-error.log`에 한 줄 남는다.

## 시험

```
cd plugins/pact
node --test tests/                          # 스크립트와 지침 파일 정적 검사
node tests/behavior/run.mjs all --runs 5    # 실패 장면 행동 시험 (pact vs 대조군)
node tests/behavior/board.mjs               # 결과판만 다시 만들기 → tests/behavior/out/board.html
```

행동 시험은 깨끗한 프로필(`PACT_TEST_PROFILE`, 기본 `~/.bench/_claude`)에서 `claude -p`로 돌린다. 처음이면 `CLAUDE_CONFIG_DIR=~/.bench/_claude claude`로 한 번 `/login` 한다. 결과 transcript는 `tests/behavior/out/`에 남고, 돌릴 때마다 판정 결과가 판(`out/runs/`)으로 쌓인다. 시험이 끝나면(사용 한도로 끝나도) `out/board.html` 결과판이 새로 만들어지고 stderr에 `결과판: <경로>`가 나온다. 서버 없이 브라우저로 파일을 열면 된다: 장면·검사별 통과율 표, 칸을 누르면 실패한 회차의 대화.

실행 캐시는 시나리오, fixture 파일, 요청한 모델, CLI 실행 파일과 설정, runner 코드를 묶은 fingerprint로 구분한다. 판정 기준(`checks`)만 바뀌면 같은 실행을 다시 판정만 한다. 실행 조건을 알 수 없는 옛 transcript는 결과판에 남지만 새 캐시로는 쓰지 않는다.

설계와 근거는 `docs/superpowers/specs/2026-10-10-pact-design.md`에 있다.
