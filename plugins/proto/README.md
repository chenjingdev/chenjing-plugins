# proto

해석-발산 병렬 프로토타이핑. 흐릿한 아이디어 한 줄을 **스타일이 아니라 해석에서 갈라지는** 실물 프로토타입 3개로 병렬 구현해 나란히 보여주고, 사용자는 실물 위에서 객관식 판정만 한다. 코드는 버리고 판정을 축적한다.

## 존재 이유

텍스트 스펙은 의도를 과소결정한다. 같은 문장을 읽고도 사람과 AI는 서로 다른 화면을 상상한다. "맞긴 한데 쓸모없다"는 판정은 문서가 아니라 실물에서만 나온다. 그리고 생성 비용이 사실상 0인 시대에는, 실물 N개를 만들어 그중 하나를 고르는 것이 인터뷰보다 싸다.

proto는 그 전제 위에서 동작한다. 흐릿한 한 줄을 받으면 **빌드 전에 사용자에게 아무것도 되묻지 않고** 곧바로 세 개의 실물을 만든다. 세 개는 색이나 문구가 다른 게 아니라 아이디어를 *어떻게 해석했는가*가 다르다 — 무엇을 위한 도구인지(telos), 사용자의 자세, 다루는 단위의 입도, 시점, 주도권 중 이 아이디어에서 실제로 갈리는 한 축을 골라 그 축 위의 세 지점으로 만든다. 사용자는 실물을 눌러보고 객관식으로 판정만 한다. 생성하는 쪽은 사용자가 아니다.

이 도구가 내놓는 것은 **의도의 증거**(생존 프로토타입 1개 + 판정 ledger)이지 본 제품이 아니다. 본 빌드는 이 실물 위에 얹지 말고, ledger의 판정과 생존 실물을 입력으로 삼아 처음부터 새로 짓는다.

## 설치

```
/plugin marketplace add chenjingdev/chenjing-plugins
/plugin install proto@chenjing-plugins
```

## 사용법

```
/proto:proto <흐릿한 한 줄 아이디어>
```

예: `/proto:proto 내 하루를 기록하는 뭔가`

빌드 전 질문은 없다. 첫 갤러리가 뜨고 나서야, 실물을 앞에 두고 객관식 판정을 묻는다.

## 흐름 요약

1. **입력** — 한 줄 아이디어. 되묻지 않는다.
2. **substrate 분류** — UI형 / CLI형 / 파이프라인·데이터형 중 하나로 자동 분류. 어느 쪽이든 최종 산출은 self-contained HTML 한 장이라 갤러리 방식은 동일하다.
3. **모드 분류** — 씨앗이 단순하면 **일괄 모드**(최대 3라운드). 복잡한 실재 프로젝트면 **단계 모드**: 첫 라운드는 골격(주 구조+주 행동)만 가르고, 이후 라운드마다 직전 생존작을 통째로 계승한 채 **한 번에 한 측면씩** 가른다. 10~20라운드 반복이 정상이고, 종료는 사용자가 고른다.
4. **해석 갈림축 확정** — 이 아이디어에서 해석이 실제로 갈리는 축 하나를 자동 선택(강한 축이 없으면 아이디어에서 새로 발굴). 단계 모드에선 라운드마다 그 측면의 축을 새로 잡는다.
5. **공유 데이터셋 저작** — 목 데이터 1벌을 만들어 세 후보가 공유. 빈 구간·깨진 레코드·폭주 구간을 데이터에 심는다. 아이디어가 실제 데이터 소스(메모리 시스템·저장소·로그)를 지목하면 허구 대신 그 소스에서 수확하고, 실제 모순·오염 레코드·공백을 엣지로 그대로 쓴다.
6. **병렬 생성 (N=3)** — 빌더 3개를 한 번에 병렬 실행. 각 후보는 4상태(폭주=첫 화면 / 빈 상태 / 오류 / 로딩)를 자체 in-frame 토글로 전환(단계 모드의 세부 라운드는 초점 측면이 닿는 상태만). 대기 중에는 "지금 만드는 중인 3개 해석"과 예상 소요를 정직하게 보여준다.
7. **검증 게이트** — 세 후보의 소스를 읽어 4상태가 실재하는지, 그리고 **셋이 구조·상호작용에서 실제로 갈리는지** 확인. 두 후보가 같은 구조에 스킨만 다르면 해당 빌더만 1회 재생성, 그래도 안 갈리면 다른 축으로 전환하고 그 사실을 알린다. 단계 모드에선 초점 밖이 베이스와 같은지도 확인한다.
8. **갤러리 제시** — 세 후보를 격리 iframe으로 나란히 임베드한 단일 갤러리를 렌더로 제시하고, **동시에 세 후보를 브라우저 탭으로도 연다** — 갤러리는 비교용, 탭은 실제로 만져보는 곳. 각 프레임 위에 해석 라벨.
9. **판정** — 실물을 앞에 두고 객관식. "어느 해석이 의도에 가장 가깝나?" (A/B/C/전부 아님). '전부 아님'이면 어긋난 지점을 물어 다음 라운드의 축을 조정한다. "A의 UI + C의 서사" 같은 하이브리드 판정도 1급으로 기록해, 다음 라운드에서 칭찬받은 부분들의 **결합 구조**를 가른다(이때 빌더는 칭찬받은 실물을 직접 읽고 계승한다). 단계 모드에선 매 라운드 "이 측면 확정, 다음으로 / 한 번 더 / 여기서 종료"를 함께 묻고, 다음 측면이 진짜 갈릴 때만 "다음엔 뭘 가를까?"를 객관식으로 얹는다(평소엔 자동 선택 후 한 줄 통보). 빌드 전 질문 0은 그대로다.
10. **ledger 축적 → 종료·핸드오프** — 라운드마다 판정 비트와 방향만 ledger에 적는다. 일괄 모드는 최대 3라운드에서, 단계 모드는 사용자가 종료를 고를 때까지 이어간 뒤 종료: 생존 실물 1개를 보존하고 나머지는 버린다. 단계 모드의 최종 생존작은 확정된 결정을 전부 품은 누적본이다.

## 산출물

실행 결과는 프로젝트의 `.proto/<타임스탬프>-<슬러그>/` 아래에 남는다.

- **`ledger.md`** — 라운드별 판정 기록. 각 블록은 (축, 후보 3개의 해석 한 줄, 판정 결과, 어긋난 지점, 다음 방향 벡터)와 실물 앵커만 담는다. **산문 요구사항은 적지 않는다** — 이 도구는 요구사항을 서술하는 곳이 아니라 판정을 축적하는 곳이다.
- **`survivor.html`** — 살아남은 프로토타입 한 장. 파일 상단에 배너 주석이 박혀 있다:

  > 이 파일은 의도의 증거입니다. 본 빌드는 이 코드 위에 짓지 말고 처음부터 새로 지으세요 — ledger.md의 판정과 이 실물을 입력으로만 쓰세요.

본 빌드로 넘어갈 때는 이 두 파일(`ledger.md`, `survivor.html`)을 **입력**으로 쓴다. survivor의 코드를 이어서 확장하지 않는다.

## 원칙

- **빌드 전 질문 0개** — 이 스킬의 제1계율. 되묻지 않고 먼저 실물을 만든다.
- **N=3 고정** — 라운드마다 정확히 세 후보.
- **스타일이 아니라 해석이 다르다** — 세 후보는 같은 것의 스킨이 아니라 서로 다른 해석이다. 두 개가 스킨만 다르면 게이트에서 걸린다.
- **얇은 후보, 많은 라운드** — 후보는 구조 아이디어 하나를 증명하는 탐침이지 기능 완제품이 아니다. 복잡한 아이디어일수록 한 라운드에 다 넣지 않는다. 풍부함은 라운드가 쌓아 올린다.
- **피그마 수준 충실도** — 후보는 시각적 이해를 돕는 프로토타입이지 동작하는 앱이 아니다. 클릭은 미리 그려둔 화면 전환이면 충분하다. 살아있는 로직(타이머·시뮬레이션·계산)은 스코프 크리프다.
- **30초 판정** — 갤러리가 뜨고 30초 안에 세 후보의 갈림이 보이고 판정이 나올 수 있어야 한다. 갤러리 헤더는 갈림 지점을 평문 한 문장으로 말한다. 30초 안에 판정이 안 되면 사용자 탓이 아니라 라운드 스코프가 넓은 것이다.
- **사용자는 판정만 한다** — 발산·생성은 시스템의 몫, 사용자는 실물 위에서 객관식 판정만 한다.
