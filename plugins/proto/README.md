# proto

구조 갈림 스프린트. 본 빌드 직전 5분 — 필수 기능을 체크리스트 페이지 하나로 확정하고, **같은 기능 집합을 서로 다르게 배치한** 저충실도 스케치 2~3장을 나란히 보여주고, 판정 하나를 받고, 고른 스케치와 판정 몇 줄만 남기고 끝낸다.

## 존재 이유

무엇을 하는 도구인지(기능 목록)는 말로 몇 초면 확정된다. 말로 확정 안 되는 건 구조다 — 어느 기능이 첫 화면에 오는지, 기능 사이를 어떻게 이동하는지, 무엇이 원클릭인지. 그 판단은 문서를 읽어서가 아니라 실물을 봐야 나온다.

그리고 실물끼리 비교가 되려면 기능이 같아야 한다. 기능이 다른 세 장은 서로 다른 세 제품이라 하나를 고를 수 없다. 그래서 proto는 둘을 나눈다: **기능은 인터뷰로 확정하고, 구조는 스케치로 나눠 판정받는다.** 인터뷰 체크리스트에는 AI가 제안하는 추가 기능도 실린다 — 아무도 말하지 않은 기능이 나올 통로는 이것뿐이고, 체크된 것만 스케치에 들어간다.

짧게 끝나는 도구다: 기본 1라운드, 최대 2라운드. 워커 위임도 검증 파이프라인도 없다. 두 라운드로 안 풀리는 아이디어는 이 도구를 더 돌릴 일이 아니라 스펙 작업으로 넘길 일이다.

산출물은 고른 스케치 1장 + 판정 기록(verdict.md)이며, 본 제품이 아니다. 본 빌드는 이 둘을 입력으로 삼아 처음부터 새로 짓는다.

## 설치

```
/plugin marketplace add chenjingdev/chenjing-plugins
/plugin install proto@chenjing-plugins
```

## 사용법

```
/proto:proto <흐릿한 한 줄 아이디어>
```

예: `/proto:proto 내 하루를 기록하는 뭔가`

## 흐름

1. **입력** — 한 줄 아이디어.
2. **스코프 인터뷰** — 추론한 후보 3~4개(실제 프로젝트면 문서 한두 개만 읽어서) + AI 제안(보통 2~3개, 한 줄 근거를 댈 수 있는 만큼)을 체크리스트 HTML로 띄운다. 일회용 로컬 서버가 페이지를 서빙하고, 체크 후 확인을 누르면 결과가 세션으로 자동 전달되며 즉시 다음 단계로 넘어간다. 잘못 보냈다면 채팅으로 정정한다(채팅이 항상 페이지보다 우선). 전달이 안 되는 환경에서는 복사-붙여넣기로 폴백. 객관식 도구의 선택지 개수 제한이 없다. 유일한 빌드 전 질문.
3. **갈림축 선택** — 같은 기능 집합을 다르게 배치하는 구조 기준 하나: 첫 화면에 올 기능 · 이동 방식(모드 전환/화면 분할/고정 순서) · 주 동작 · 한 화면에 보이는 양.
4. **직접 2~3장 스케치** — 메인 세션이 워커 없이 직접 그린다. 모든 장에 필수 기능 전부, 클릭까지 동작하게. 구조가 두 갈래뿐이면 두 장만 그린다.
5. **한 번 훑기** — 모든 장에 스코프가 다 있는지, 구조가 실제로 다른지, 클릭해도 반응 없는 UI가 없는지 확인하고 그 자리에서 고친다.
6. **갤러리 제시** — 격리 iframe 갤러리를 렌더로 제시하고 각 장을 브라우저 탭으로도 연다. 헤더에 "기능은 같고 구조가 이렇게 다르다"를 한 문장으로 적는다.
7. **판정** — "어느 구조가 의도에 가장 가깝나?" (A/B/C/전부 아님). 전부 아님이면 어긋난 지점 하나를 묻고(스코프 자체가 틀렸으면 인터뷰를 한 번 정정) **더 좁은 질문**으로 라운드 2를 한 번만 더 — 라운드 2의 판정으로 무조건 종료.
8. **핸드오프** — verdict.md(스코프·갈림축·판정·사용자 원문 인용·방향) + survivor.html(이 위에 짓지 말라는 배너 포함)만 남기고 나머지는 삭제.

## 산출물

`.proto/<타임스탬프>-<슬러그>/` 아래 두 파일:

- **`verdict.md`** — 판정 기록 몇 줄. 요구사항 문서가 아니라 스코프·판정·사용자 원문 인용.
- **`survivor.html`** — 고른 스케치. 상단 배너: *"이 파일은 판정 기록의 근거입니다. 본 빌드는 이 코드 위에 짓지 말고 처음부터 새로 지으세요."*

본 빌드로 넘어갈 때 이 두 파일을 **입력**으로 쓴다. survivor의 코드를 이어서 확장하지 않는다.

## 원칙

- **빌드 전 질문은 스코프 인터뷰 하나** — 기능 목록만 말로 확정하고, 나머지는 실물을 보고 판정한다. AI가 떠올린 기능도 이 체크리스트를 거쳐야만 스케치에 들어간다 — 몰래 추가된 기능은 판정을 흐린다.
- **같은 스코프, 다른 구조** — 기능이 다르면 비교가 안 되고, 스타일만 다르면 고를 이유가 없다. 차이는 배치·이동·주 동작에만 둔다.
- **2~3장, 기준은 하나** — 세 장을 채우려고 만든 변형은 판정을 어렵게 할 뿐이다. 두 갈래면 두 장.
- **와이어프레임까지만 + 그린 것은 전부 동작** — 흑백 박스·라벨·클릭 지점까지만. 살아있는 로직 없음. 클릭해도 반응 없는 UI는 아예 그리지 않는다.
- **직접 그린다** — 워커 위임 없음. 이 크기에서는 위임을 준비하고 기다리는 시간이 직접 그리는 시간보다 길다.
- **기본 1라운드, 최대 2** — 거절에 더 크거나 복잡한 개념으로 답하지 않는다. 라운드 2는 반드시 더 좁게.
- **30초 판정** — 갤러리가 뜨고 30초 안에 차이가 보이고 고를 수 있어야 한다. 안 되면 스케치에 너무 많이 담은 것이다.
