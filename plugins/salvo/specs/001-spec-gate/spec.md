**Input**: User description: "spec 문서를 실행자 모델(예: Opus)이 콜드 리드해서 '구현 중 스스로 결정해야 할 것들'을 열거하고, 그 목록이 해소될 때까지 작성자에게 환류하는 Claude Code 스킬. 강한 모델로 쓴 spec을 약한 모델이 막힘 없이 구현할 수 있는지 사전 실측하는 게이트."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - spec의 막힘 지점 사전 발견 (Priority: P1)

spec 작성자가 게이트를 호출하면, 실행자 모델 서브에이전트가 **대화 맥락 없이 spec 문서만** 읽고 "이 문서만으로 구현할 때 내가 스스로 정해야 하는 것·물어보고 싶은 것"을 구조화된 목록으로 반환한다. 작성자는 이 목록을 보고 spec을 보강한다.

**Why this priority**: 이 스킬의 존재 이유. 이것 하나만 있어도 "실행자가 막히는가"를 실측할 수 있다.

**Independent Test**: 의도적으로 모호한 항목 3개를 심은 spec으로 게이트를 실행해, 반환 목록이 심은 모호함을 전부 포착하는지 확인.

**Acceptance Scenarios**:

1. **Given** 미해소 모호함이 있는 spec 문서, **When** 게이트를 실행하면, **Then** 실행자 서브에이전트가 반환한 이슈 목록이 파일에 기록되고 사용자에게 요약 표시된다.
2. **Given** 게이트가 이슈 N건을 반환한 상태, **When** 작성자가 spec을 보강하고 게이트를 재실행하면, **Then** 해소된 이슈는 사라지고 라운드 번호가 증가한 새 결과가 기록된다.
3. **Given** 확정 blocking 이슈 0건인 spec, **When** 게이트를 실행하면, **Then** 문서 상태가 `gate: passed`로 갱신된다 (갱신 주체는 작성 세션 — FR-005).

---

### User Story 2 - 게이트 이력의 문서 내 기록 (Priority: P2)

게이트 실행 결과(라운드 번호, 이슈 수, 잔여 이슈, 통과 여부)가 spec 문서의 frontmatter 또는 부속 파일에 누적 기록되어, 나중에 구현 세션(Opus)이 "이 spec은 몇 라운드 검증을 통과했는지" 신뢰도를 확인할 수 있다.

**Why this priority**: 기록이 없으면 게이트 통과가 구현 세션에 전달되지 않아 게이트의 신뢰 가치가 사라진다.

**Independent Test**: 게이트를 2라운드 실행한 뒤 기록 파일에 라운드별 이력이 남는지 확인.

**Acceptance Scenarios**:

1. **Given** 게이트를 2회 실행한 spec, **When** 기록을 열람하면, **Then** 라운드별 (시각, 이슈 수, 이슈 요약)이 시간순으로 남아 있다.

---

### User Story 3 - 잔여 이슈의 명시적 수용(waive) (Priority: P3)

작성자가 "이 이슈는 구현자가 재량으로 정해도 됨"이라고 판단한 항목을 명시적으로 수용 처리하면, 해당 항목은 재실행 시 다시 제기되지 않고 수용 사유와 함께 기록된다.

**Why this priority**: 모든 이슈를 0으로 만드는 건 비현실적일 수 있다. 단, 수용은 암묵이 아니라 명시여야 한다.

**Independent Test**: 이슈 1건을 수용 처리 후 재실행 → 그 항목이 잔여 목록에서 빠지고 `waived` 섹션에 사유와 함께 남는지 확인.

**Acceptance Scenarios**:

1. **Given** 잔여 이슈 1건, **When** 작성자가 수용 사유와 함께 waive하면, **Then** 게이트는 `passed (1 waived)`로 판정하고 사유가 기록된다.

### Edge Cases

- spec 파일이 존재하지 않거나 빈 파일일 때 → 게이트는 실행을 거부하고 이유를 보고한다.
- 실행자 서브에이전트 스폰이 실패(모델 불가용 등)할 때 → 실패를 기록하고 부분 결과를 남기지 않는다.
- 라운드를 거듭해도 이슈가 수렴하지 않을 때(매 라운드 새 이슈 발명) → 라운드 상한은 없다. 확정 blocking 0건까지 반복한다. 매 라운드가 사용자 인터뷰 환류로 끝나므로, 발산 판단과 중단은 그 시점의 사용자 몫이다. (사용자 결정: R2-2 — 상한 제거, D-9로 D-4 대체)
- spec 문서가 실행자 컨텍스트 한도를 넘을 만큼 클 때 → 게이트는 분할 없이 거부하고 문서 축소를 권고한다.
- 실행자가 spec 범위 밖의 질문(예: 배포 인프라)을 제기할 때 → 범위 밖 표시와 함께 별도 분류한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 스킬은 spec 문서 경로를 입력받아, 실행자 모델 서브에이전트에 **해당 문서 내용만**(대화 맥락 배제) 전달해야 한다.
- **FR-002**: 실행자 서브에이전트는 (a) 물어봐야 할 질문 (b) 스스로 내려야 할 결정 (c) 정의 안 된 용어 (d) 검증 불가능한 수락 기준의 4분류로 구조화된 이슈 목록을 반환해야 한다.
- **FR-003**: 게이트의 대상 아티팩트는 **spec.md 단일 문서**다. plan/tasks 등 하위 산출물은 실행 모델(Opus) 세션의 영역이므로 게이트 대상이 아니다. (사용자 결정: "spec만 제대로 만들면 된다")
- **FR-004**: 게이트 실행 결과는 라운드 번호와 함께 기능 디렉터리 내 부속 파일(`gate-report.md`)에 누적 기록되어야 한다.
- **FR-005**: 확정 blocking 0건(또는 전 확정 blocking waived) 판정 시 spec 문서의 상태 필드가 `gate: passed`(waive 존재 시 `passed-with-waivers`)로 갱신되어야 한다. 갱신 주체는 게이트가 아니라 **작성 세션**(스킬을 구동하는 세션)이며, 시점은 판정 직후 같은 스킬 실행 안이다. (사용자 결정: R1-1 A안 — 게이트는 spec.md를 절대 수정하지 않는다)
- **FR-006**: 이슈는 2분류를 따른다 — **blocking**(구현 방향·범위가 갈려서 실행자가 스스로 정할 수 없는 것)과 **discretionary**(실행자가 재량으로 정해도 되는 세부 — 네이밍, 내부 구조, 마이너 UX). 판정의 객관화를 위해 콜드 리드는 **독립 리더 3명 병렬**로 수행하며(리더 수는 호출 인자 `--readers`, 기본 3), **2명 이상이 같은 지점을 blocking으로 제기한 것만 '확정 blocking'** 으로 집계한다. 통과 기준은 **확정 blocking 0건**이며, discretionary와 1인 단독 제기 blocking은 정보성으로만 표시하고 통과를 막지 않는다. (사용자 결정: "디테일은 Opus가 할 수 있다" + R2 점수화 D-8)
- **FR-007**: 게이트는 이슈 목록만 반환하고 spec 수정은 하지 않는다 — 수정 권한은 작성자(작성 세션)에게만 있다. 여기서 '게이트'는 콜드 리더 서브에이전트와 gate-report.md 기록 단계를 뜻하며, 게이트의 쓰기는 gate-report.md가 유일하다. 각 blocking 이슈에는 실행자가 **선택지 형태의 제안 답변(A/B/C)**을 첨부하며, **되묻기 인터뷰 루프(각 blocking을 선택지+직접입력 질문으로 순차 질의)는 게이트 스킬 실행의 일부로 자동 구동된다 — 별개의 후속 작업이 아니다** (사용자 결정: R1-2 B안). 제안은 '실행자 추측' 라벨을 달고, 사용자가 명시적으로 채택할 때만 작성 세션이 spec에 반영한다(환류 직후, 같은 스킬 실행 안).
- **FR-008**: waive 처리는 사용자의 명시적 확인(사유 입력 포함)을 통해서만 가능해야 한다.
- **FR-009**: 콜드 리드에 앞서 **기계 린트**를 바닥(floor) 검사로 수행한다. 전제 템플릿은 fableus spec 템플릿이며, 필수 섹션 = `*(mandatory)*` 태그가 붙은 섹션이다. **반려(하드 폴) 조건은 정확히 두 가지**: ① 필수 섹션 공백 ② `[NEEDS CLARIFICATION:` 마커(대괄호+콜론 형식으로 매칭) 1개 이상. 모호 형용사 잔존 수와 수락 기준의 관찰 가능성(숫자/검증 술어 부재)은 **경고(정보성)로만 보고**하고 반려하지 않는다 — 무-임계 문체 검사는 정상 문서도 반려시킨다(실측: 이 문서 자신이 "적정/드물" 등을 포함). 린트는 재현 가능한 사전 필터일 뿐 통과 판정을 대체하지 않는다 — 통과는 언제나 확정 blocking 0건이다. (사용자 결정: R2 점수화 D-8 + R3-2 D-11)
- **FR-010**: 다중 리더의 **"같은 지점" 합의 집계는 앵커 기반**이다 — 리더는 각 이슈에 앵커(대상 FR 번호 또는 섹션명)를 필수로 태깅하고, 동일 앵커의 blocking 제기는 기계적으로 합산한다. 앵커가 불일치하는 이슈만 작성 세션이 의미 기준으로 병합하되, 병합 근거를 gate-report.md에 투명하게 기록한다. 집계에 별도 LLM 심판을 두지 않는다 — 배격한 주관성이 집계 단계로 회귀하는 것을 막는다. **"같은 지점"의 정의는 앵커 일치 그리고 논지 일치다 — 동일 앵커라도 논지가 다르면 별개 이슈로 분리 집계하며, 분리 근거 역시 리포트에 기록한다.** (사용자 결정: R3-1 D-10 + R4 D-12)

### Key Entities

- **GateReport**: 라운드 번호, 실행 시각, 실행자 모델 식별자, 이슈 목록(4분류), 판정(passed / blocked / passed-with-waivers).
- **Issue**: 분류(질문/결정/용어/수락기준), 본문, 심각도, 상태(open / resolved / waived), waive 사유(있을 때).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 모호 항목 3개를 심은 벤치마크 spec에서 게이트가 3개 전부를 1라운드에 포착한다.
- **SC-002**: 게이트 통과(passed) spec을 받은 구현 세션이 구현 중 작성자에게 되묻는 질문 수가 0건이다 (시험 구현 1건 기준).
- **SC-003**: 게이트 1라운드의 소요 시간이 5분 이내다 (실행자 서브에이전트 1회 왕복 기준).
- **SC-004**: 게이트 미통과 spec 대비 통과 spec의 구현 재작업(구현 후 spec 재해석으로 인한 수정) 발생 건수가 감소한다 (동일 기능 A/B 1회 기준).

> **SC 검증 자산의 범위**: SC 검증용 픽스처(모호함을 심은 벤치마크 spec)와 시험 구현은 스킬 산출물 범위에 포함되지 않는다 — 산출물은 스킬(SKILL.md·리더 프롬프트·라운드/리포트 로직)뿐이며, SC는 작성자/검증 세션의 사후 검증 기준이다. (사용자 결정: R2-1 A안 — D-7)

| D-6 | 되묻기 인터뷰 루프(blocking별 선택지+직접입력 순차 질의)는 게이트 스킬 실행의 일부로 자동 구동된다. 답변은 사용자 채택 시에만 작성 세션이 spec에 반영. [본문 FR-007] | R1 콜드 리드가 스킬 범위 미정으로 판정(R1-2). 사용자가 B안 채택 — 환류까지가 스킬의 한 실행. | A안(목록+요약까지만, 인터뷰는 후속 수동) — 게이트→보강 루프가 끊겨 기각. C안(플래그 옵션) — v1 복잡도 증가로 기각. |
| D-7 | SC 검증 픽스처(벤치마크 spec)·시험 구현은 산출물 범위 밖 — 스킬만 납품한다. SC는 작성자/검증 세션의 사후 검증 기준. [본문 Success Criteria 주석] | R2 콜드 리드가 납품 범위 미정으로 판정(R2-1). 사용자가 A안(스킬만) 채택. | B안(SC-001 픽스처 1건 동봉)·C안(평가 스크립트까지) — 검증 자산은 필요 시 별도 제작이 낫다고 판단해 기각. |
| D-8 | 판정을 객관화한다: ① 기계 린트를 바닥 검사로 선행(FR-009), ② 콜드 리드는 독립 3-리더 병렬 + 2인 이상 합의만 확정 blocking(FR-006, `--readers` 기본 3). 통과 = 확정 blocking 0건. [본문 FR-006·FR-009] | 사용자 요구: "기계적으로 평가해 특정 점수를 못 넘으면 계속 인터뷰". 단일 리더 판정의 분산이 주관성의 실체 — 합의 투표로 분산 축소, 린트로 재현 가능한 바닥 확보. | LLM 루브릭 점수(0-100)+문턱 — 캘리브레이션 불량, 숫자 옷 입힌 산문이라 기각. 린트 단독 — 형식 점수만으로는 유창한 산문이 게이트를 속일 수 있어(천장 위조) 기각. |
| D-9 | 라운드 상한을 제거한다 — 확정 blocking 0건까지 반복. 발산 판단·중단은 매 라운드 인터뷰 환류 시점의 사용자 몫. (D-4 대체) [본문 Edge Cases] | R2 콜드 리드: 이어 세기 해석 시 "보강 후 재시작" 경로가 동작 불가(R2-2). 매 라운드가 이미 사용자 환류로 끝나 별도 기계 상한이 중복 장치라 판단, 사용자가 상한 제거 채택. | 상한 유지+리셋 / 상한 파라미터화(기본 3) — 환류 자체가 사람 체크포인트라 이중 장치로 판단해 기각. |
| D-10 | 합의 집계는 앵커 기반 — 리더가 이슈마다 앵커(FR/섹션) 필수 태깅, 동일 앵커는 기계 합산, 불일치분만 작성 세션이 의미 병합(근거를 리포트에 기록). 집계용 LLM 심판 금지. [본문 FR-010] | R3 확정 blocking(3/3): 매칭 방식이 판정을 통째로 좌우하는데 미정. | D-11 | 린트 반려 조건은 정확히 2개(필수 `*(mandatory)*` 섹션 공백, `[NEEDS CLARIFICATION:` 마커 ≥1)로 한정. 문체 검사(모호 형용사·관찰 가능성)는 경고만. 전제 템플릿 = fableus spec 템플릿. [본문 FR-009] | R3 확정 blocking(3/3): 반려는 콜드 리드를 막는 하드 게이트인데 임계 미정. 무-임계 형용사 검사는 이 문서 자신도 반려시킴(리더 3 실측 지적). | 네 검사 전부 하드폴+설정 외부화 — 설정 부담·오반려 위험으로 기각. 문체 검사 린트 제거 — 경고 정보도 유용해 잔류시키고 반려만 제외. |
| D-12 | "같은 지점" = 앵커 일치 AND 논지 일치 — 동일 앵커라도 논지가 다르면 별개 이슈로 분리 집계한다(분리 근거 리포트 기록). [본문 FR-010] | R4 실측: 상이 논지 이슈 3건이 모두 FR-007에 앵커돼, D-10 문자 적용(기계 합산)과 FR-006의 "같은 지점" 정의가 충돌 — 독해에 따라 판정이 passed/blocked로 갈림. 논지 기준을 정본으로 채택(각 이슈에 타 리더 1~2명이 재량 분류 + 수렴 답 제시 = 확정 기준 미달의 방증). | 앵커 기계 합산 우선(FR-007 그룹을 확정 1건으로) — 상이 논지의 오병합이라 기각. |

## Assumptions

- 실행자(콜드 리더) 모델은 기본 Opus로 하되 호출 시 오버라이드 가능하다 — 실제 구현을 맡을 모델과 같은 모델이 읽는 것이 이상적이라는 가정.
- spec의 적정 상세도(altitude)는 "실행 모델이 재량으로 채울 수 있는 수준"이며, 그 경계는 고정 규칙이 아니라 실행 모델 실측(콜드 리드 결과에서 실행자가 blocking으로 분류하는 항목의 패턴)으로 캘리브레이션한다.
- 게이트 호출은 수동이다(작성 흐름의 특정 단계에 자동 훅으로 걸지 않는다) — v1 범위 축소를 위한 가정.
- 대상 spec 문서는 마크다운이며 단일 파일 기준 실행자 컨텍스트에 들어가는 크기다.
- 이 스킬은 Claude Code 환경(서브에이전트 스폰 가능)에서 동작한다.
