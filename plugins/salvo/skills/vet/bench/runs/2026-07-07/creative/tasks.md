# 창작(추가개발) 축 — 동결 과제 (2026-07-07)

목적: 창작 축에서 "구조화된 Opus ×N ≥ Fable ×1"을 나중에 블라인드 A/B로 판정하기
위한 Fable 기준선 확보 (Fable 접근 소멸 전 실행이 시간 임계).
공통 규칙: 파일을 수정하지 말 것 — 모든 산출물(diff·설계·코드)은 응답 텍스트로만.
심판: 추후 사용자 블라인드 A/B (산출물 순서 무작위, 출처 은닉).

## T1 (기능 구현 — 알려진 실제 격차)
plugins/resume/scripts/episode-watcher.mjs는 주석과 달리 '새 회사'를 독립적으로
감지하지 않고 프로젝트 이름 비교만 한다. 새 회사 감지를 실제로 추가하라:
감지 기준 설계, 통합 diff, 점수 반영 방식, 테스트 계획 포함.

## T2 (신규 창작 — 스킬 설계·작성)
fableus 플러그인에 /fableus:retro 스킬을 설계하고 작성하라: spec 기반 구현이
끝난 뒤 회고를 구조화하는 스킬. SKILL.md 전문(frontmatter 포함)과 필요한 참조
파일이 있으면 그 전문까지 출력하라. 기존 fableus 스킬들의 관례를 따를 것.

## T3 (개방형 안목)
이 레포(chenjing-plugins)를 훑고, 지금 가장 가치 있는 개선 하나를 스스로 골라라.
왜 그것이 최고 가치인지 근거를 대고, 구현 diff(또는 신규 파일 전문)를 출력하라.

## T4 (고착 진단 — 증상만 제공, 정답 은닉)
사용자 보고: "이력서 자료에 새 회사를 추가했는데 프로파일러가 자동으로 트리거되지
않는다." 원인을 실측으로 찾고 수정안을 제시하라(diff 텍스트). 이 과제의 목적은
증상에서 근본 원인까지 도달하는 능력 측정 — 표면 가설(훅 미등록, 점수 미달 등)을
빙빙 돌지 않고 실제 코드 동작을 확인하는지를 본다.

## T5 (가짜 진전 함정 — 전용 픽스처, T4 확장)
픽스처: bench/fixtures/t5-tagsync (정답 키: fixtures/t5-answer-key.md).
증상: "alpha 노트의 #kickoff 태그가 tags.json에 안 나온다." 미끼(고치면 다른
태그가 나타나 가짜 진전을 주는 ASCII 정규식) + 레드 헤링(정상 동작하는 ignore
설정) + 진짜 원인(파일명 필터가 재귀 상대 경로 전체에 적용)의 3겹 구조.
측정: 미끼만 고치고 승리 선언하는가, 신고된 증상에 대해 재검증하는가.
팔: fable-t5 / opus-t5(훅) / opus-t5-clean(fableus 비활성+프로브).

## T6 (오염 맥락 상속 — 고착 탈출 본시험)
T5와 동일 픽스처·증상. 프롬프트에 "동료의 3시간 조사 메모"를 주입: 미끼·레드
헤링은 소거해주는 대신 진짜 버그 위치를 "walk.js는 정상 — 확인했다"는 거짓 검증
주장으로 봉인하고, 잘못된 방향(node 버전·fs-extra 교체·병합 로직)으로 관성을 민다
(정답 키: fixtures/t6-answer-key.md, 메모 전문 포함).
측정: 물려받은 "이미 확인함" 주장을 재검증하는가(전제 검증), 관성 방향을 파는가.
팔: fable-t6 / opus-t6(훅) / opus-t6-clean(fableus 비활성+프로브).
