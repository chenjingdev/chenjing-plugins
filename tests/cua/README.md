# Codex CUA 개발용 테스트

저장소 루트에서 전체 회귀 시험을 실행한다.

```sh
python3 tests/cua/run.py
```

Runner는 `plugins/cua`를 Python 모듈 검색 경로에 추가한 뒤 이 폴더의 `test_*.py`를 발견해 실행한다. 시험용 추가 의존성은 없으며 Python 표준 라이브러리의 `unittest`를 사용한다.

기존 68개 행동 검증을 보존하되, Portwarden 중계기를 다루던 4개는 번들 플러그인으로 식별되지 않는 서버를 거부하는 1개로 바꿨다. 103개 시험에는 닫힌 앱의 백그라운드 실행과 포커스 복귀, 켜져 있는 앱 보존, 동시 실행 시 한 번만 열기, 로그인 항목 설정·충돌 보존·제거가 포함된다.

플러그인이나 실행 환경이 깨져도 Codex가 원본 CLI로 켜지는 경로는 세 곳에서 확인한다. 실제 `/bin/sh`로 도는 실행 스크립트(인터프리터 없음·실행 불가·끊어진 링크, command.py 없음, 원본 CLI를 모르는 경우), 백엔드를 시작하기 전에 실패하는 래퍼(상태 폴더·점유·시간 설정·메타데이터 쓰기·실행 실패에서 인자와 환경을 그대로 넘겨 exec), `--exec-wrapper` 사전 검사(래퍼와 전송 스크립트가 없거나 손상됨)이다. 백엔드가 시작된 뒤의 실패는 예전처럼 실패로 남는다.

`codex-cua`가 설치된 플러그인 판의 `setup.py`로 넘기는 위임도 확인한다. 인자와 `--` 뒤 인자 보존, 이 복사본이 모르는 명령, 두 번 넘기지 않기, 등록이 없거나 손상됐을 때 원본 CLI로 실행하기, 실제 프로세스로 실행 스크립트에서 새 판까지 이어지는 흐름이다. 연결 제어 소켓의 기본 위치(`~/Library/Caches/codex-cua/bridges`)와 권한도 확인한다.

MCP catalog·이미지·오류·승인 전달, 전용 thread 종료, 다른 client 유지, launcher의 인자·환경·stdio 보존, registry와 원본 앱 탐색, 설치 캐시 업데이트, 의존성 준비의 동시 실행과 부분 설치 복구를 확인한다. 릴리스 버전은 플러그인 manifest에서 읽어 실행 정보와 비교한다. 설치 캐시 업데이트를 흉내 내는 `0.4.0`과 `0.4.1`은 시험 데이터다.

시험은 임시 폴더, fake CLI, mock 호스트를 사용한다. 실제 Codex·CUA·브라우저·GUI·계정이나 credential을 호출하지 않는다. 소켓과 subprocess를 사용하는 시험도 격리된 fake 대상만 생성하고 정리한다. 시험 파일과 fixture 코드는 고객 설치용 플러그인 폴더에 포함하지 않는다.

이 테스트 코드는 플러그인과 같은 [MIT 라이선스](../../plugins/cua/LICENSE)를 따른다.
