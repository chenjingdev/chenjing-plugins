# pact를 지시 대신 코드와 기록으로 지키기
## 목적
하네스 철학("경계는 두껍게, 방식은 얇게")으로 pact를 고친다. 지난 18판에서 지시로만 지키던 곳이 샜다. '사용자만 답할 수 있음' 38개 중 18개만 물었고, 메인이 검수 결과를 손으로 고친 일이 3번, worker 걱정 173건 중 56건은 다룬 흔적이 없다.
## 범위
plugins/pact 0.6.0. 훅(hooks/hooks.json)을 처음 넣고 스크립트와 지시 문서를 고친다. Claude Code에서 pact를 쓰는 대화가 대상이다.
## 하지 않는 것
- reviewer·spec-checker의 셸 명령 검사, worker의 worktree 밖 수정 막기 — 18판에서 0건이라 걸리면 그때 넣는다
- GitHub에 올리기와 이 컴퓨터에 설치하기 — 다 만든 뒤 따로 묻는다
- 다음 판 후보: 이번 판 성적 한 장, 잔소리 줄이기(체크리스트 줄인 판 비교, 규칙 출구)
## 기능
- F1 검수 결과(results*.json, verification.json)는 verifier와 pact 스크립트만 쓴다. 다른 쪽이 고치려 하면 막는다 [사용자]
- F2 만들기는 승인이나 위임 기록이 있어야 시작한다. 위임은 사용자 말을 인용해 스크립트로만 켠다 [사용자]
  - 케이스: 위임인데 명세에 지우기·외부 공개·돈 드는 항목이 있음 → 시작하지 않고 승인을 기다린다
- F3 승인 뒤 [사용자] 줄이 바뀌면 실패로 끝내지 않고 다시 승인을 받아 이어 간다 [사용자]
- F4 spec-checker·reviewer·worker의 마지막 답이 실행 폴더 log/에 저절로 남는다 [사용자]
- F5 spec-checker의 '사용자만 답할 수 있음' 항목은 물어서 답을 받았거나 안 물은 까닭이 `## 확인 필요`에 있어야 완료 검사를 통과한다 [사용자]
  - 케이스: 빠진 항목이 있음 → 어느 항목인지 알리고 막는다
- F6 worker 보고의 걱정이 reviewer 작업 지시에 저절로 붙는다 [사용자]
- F7 worker 상태는 DONE·BLOCKED 둘이고 걱정은 따로 칸에 쓴다. 작업 지시에서 커밋 꼬리말 모델명 지시를 뺀다 [사용자]
## 공통 규칙
- R1 훅은 pact가 걸린 호출(.pact/·docs/pact/ 쓰기, pact 에이전트, pact 스크립트)만 보고 나머지는 바로 통과시킨다 — 플러그인 훅은 모든 대화에서 돈다 [AI 가정]
- R2 위임으로 적는 말은 승인까지 맡긴다는 말("끝까지 알아서 해", "승인 없이 만들어")뿐이다. 질문의 답으로 온 "알아서"·"ㄱㄱ"는 그 질문만 맡긴 것이다 — 이것까지 위임으로 치면 승인 묻기가 사라진다 [AI 가정]
- R3 승인·위임 기록은 인용한 말을 이 대화 기록의 사용자 메시지에서 찾아 맞춰 본다. "승인"처럼 짧은 말은 메시지 전체와 같아야 한다 — '이미 승인받았다고 믿는' 버릇을 막는다 [AI 가정]
- R4 F3의 다시 승인은 그 변경을 부탁한 사용자 말을 인용해 적고 다시 묻지 않는다. 부탁한 말이 없으면(사용자가 파일을 직접 고침) 한 번 묻는다 — 승인 뒤 바뀐 5번이 모두 사용자가 부탁한 것이었다 [AI 가정]
- R5 0.6.0 전에 만든 명세(지금 진행 중 4개)는 승인 기록 없이 이어 가고 보고서에 그렇다고 적는다. 결과 파일 잠금은 똑같이 걸린다 — 하던 일을 멈추지 않게 [AI 가정]

- R6 막을 때는 까닭과 대신 할 일을 한 줄로 알린다 — 까닭 없이 막으면 AI가 다른 길로 돌아간다 [AI 가정]
- R7 훅이 오류로 죽으면 막지 않고 통과시키고 오류를 기록한다. 스크립트 검사(approve·delegate·snapshot·finish)는 반대로 확인을 못 하면 거절한다 — 훅 고장이 모든 대화를 멈추지 않게, 완료 판정은 느슨해지지 않게 [AI 가정]
- R8 위임은 새 status가 아니라 승인 기록의 한 종류다. `spec.mjs approve`·`delegate`가 인용한 말을 받아 실행 폴더에 기록을 남기며 status를 approved로 바꾸고, 기록이 없으면 set-status approved·building, pact:worker 부르기, snapshot이 거절한다. 보고서에 승인인지 위임인지와 인용한 말을 보인다 — 명세 본문에 두면 검수 지문이 바뀐다 [AI 가정]
- R9 승인으로 인용하는 말은 spec-checker가 끝난 뒤의 말이어야 하고, 위임은 처음 부탁에 있어도 된다. 맞춰 볼 때 띄어쓰기·문장부호는 빼고, 기록에 메시지 id와 대화 기록 경로를 남겨 만들기를 시작할 때 다시 맞춰 본다 — 검수 전에 받은 '좋아'를 승인으로 쓰지 않게 [AI 가정]
- R10 위험 항목은 기능·규칙 줄의 태그 앞에 `[위험: 지우기|공개|비용]`으로 표시한다. lint는 위험 낱말(지우기·삭제·덮어쓰기·공개·배포·push·결제·비용 같은 말)이 있는데 표시가 없으면 참고로만 알리고, 위임으로 시작할 때는 표시 없는 위험 낱말에도 멈춘다 — 표시가 없으면 코드가 위험을 모른다 [AI 가정]
- R11 spec-checker는 '사용자만' 항목에 `검수 n` 번호를 붙인다. 명세는 답한 줄에 `[사용자: 검수 n]`, 맡긴 줄에 `[AI 가정: 검수 n 맡김]`을 달고, 안 물은 것은 `## 확인 필요`에 `- 검수 n: 안 물은 까닭`으로 적는다. 위임 중이면 '위임이라 기본안으로 정함'을 까닭으로 쓰고 보고서 할 일에 올린다. F5 확인은 승인·위임을 기록할 때도 한다 — 번호가 있어야 코드가 짝을 맞추고, 다 만든 뒤에 걸리면 되돌리기 비싸다 [AI 가정]
- R12 F3의 '[사용자] 줄'은 [사용자] 태그가 붙은 F·R 줄과 그 케이스다. 빼기·태그 바꾸기·더하기도 바뀐 것으로 보고 worker 부를 때, snapshot, finish에서 본다. 보고서에 승인 뒤 바뀐 줄과 인용한 말을 보인다 — 어디서 바뀌어도 알아차리려고 [AI 가정]
- R13 메인이 쓰던 보고 칸(headline·todo·changes·decision)은 실행 폴더의 `summary.json`에 쓰고, rulings는 report.mjs가 명세에서 읽는다. 고친 뒤 이전 결과는 스크립트가 `results-roundN.json`으로 남긴다 — F1 잠금 뒤에도 지금처럼 보고서를 만들려고 [AI 가정]
- R14 verifier가 끝날 때 훅이 results.json 지문을 기록하고, 완료 검사는 지금 파일이 그 지문과 다르면 거절한다. 승인 기록·log/·지문 기록도 훅과 스크립트만 쓴다 — 셸 명령으로 쓰는 길은 훅이 다 막지 못한다 [AI 가정]
- R15 log/에는 verifier의 마지막 답도 남긴다. 실행 폴더는 하위 에이전트 첫 지시에 든 경로로 찾고, 없으면 그 명세가 있는 프로젝트에서 가장 최근에 바뀐 진행 중 명세로 찾는다. 폴더가 없으면 만들고 기록은 덧붙여 쓰며, 못 찾으면 플러그인 데이터 폴더의 오류 기록에 남긴다 — 보통은 하나다 [AI 가정]
- R16 worker 상태의 PARTIAL도 뺀다. reviewer 답에 `## worker 걱정 처리` 칸을 두고 붙은 걱정마다 어떻게 했는지 적는다. 걱정은 worker 보고 파일이 아니라 log/의 worker 답에서 가져온다 — PARTIAL은 204건 중 0번이었고, 붙이기만 하면 걱정이 또 흘러간다 [AI 가정]
- R17 커밋 꼬리말은 작업 지시에서 통째로 빼고 worker는 자기 하네스가 주는 꼬리말을 쓴다. 꼬리말이 다르다는 것은 걱정으로 올리지 않는다 — 걱정 25건이 이것이었다 [AI 가정]
- R18 훅은 손으로 만든 입력 JSON으로 단위 시험한다. 검수 때 `claude -p --plugin-dir`로 실제 대화를 한두 번 돌려 막기와 기록이 실제로 도는지 본다(구독 사용량 조금, 사용자 설정과 다른 플러그인 없이) — hooks.json의 이름이 틀리면 단위 시험은 통과해도 훅이 안 돈다 [AI 가정]
