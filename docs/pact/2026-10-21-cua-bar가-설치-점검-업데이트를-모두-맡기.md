# CUA Bar가 설치·점검·업데이트를 모두 맡기
## 목적
앱 하나만 깔면 Claude Code에서 CUA를 쓰게 한다. MCP·스킬의 설치와 제거, 환경 점검, 새 판 업데이트를 CUA Bar가 모두 맡고 Claude 플러그인은 따로 깔지 않는다. 사용자 원문(2026-10-21): "어짜피 앱이 그 역할 하니까 그냥 앱에서 바로 mcp설치 시키면 되지 않나?", "mcp랑 스킬 설치시키고 지울때도 앱에서 삭제시키게 하고. 잘 환경셋팅 됐는지 검토하는것도 앱에서 하고", 자동 업데이트 제안에 "ㅇㅇ".
## 범위
CUA Bar 앱(`apps/cua-bar`), 앱에 담을 연결 엔진(지금의 `plugins/cua`), 받는 곳(cua.chenjing.org), README, 옛 CUA 도구 이름을 쓰는 pact 플러그인 세 파일.
## 하지 않는 것
- Claude 플러그인과 마켓플레이스로 나눠 주는 길. 플러그인이 없어지면 앱 없이 MCP를 깔 길도 없어서, 같은 날 정한 '앱 없이 setup.sh 한 줄'도 없앤다 [AI 가정]
- 다른 기기의 0.7.0을 옮기는 코드. 아직 배포 전이라 이 맥만 손으로 옮긴다.
- 다음 판 후보: 업데이트 되돌리기(옛 판으로 돌아가기)

  - 케이스: Codex가 꺼져 있음 → 연결 시험을 건너뛰고 "Claude 대화를 열면 켜져요"라고만 한다

## 결정 기록
- Ruling: 이 맥은 만들고 검수한 뒤 때를 묻지 않고 바로 옮긴다 (사용자 2026-10-21 "바로") — R16을 그에 맞게 고쳤다 — 틀리면 열려 있던 Claude 대화의 옛 CUA 도구가 끊겨 새 대화를 열어야 한다.
- Ruling: pact 플러그인은 판을 올리고 push한다 (사용자 2026-10-21 "올리고 푸시"). 새 이름 `mcp__cua__js`를 먼저 찾고 없으면 옛 이름 `mcp__plugin_cua_cua__js`를 찾는다 — 옛 플러그인이 남은 다른 맥에서도 화면 검수가 이어지게 — 틀리면 그런 맥의 pact 검수가 화면 없이 돈다.
- Ruling: install-engine --json의 `setup`은 command(status와 같은 낱말), login_environment(ready·conflict·failed), relay(파일 상태 ready·missing·invalid)이고, `removed`는 지운 판 이름 배열이다 (작업 1, 작업 3 두 번째 검토에서 실제 출력에 맞춰 고침) — 설치 결과를 그대로 적으려고 — status의 낱말로 읽으면 relay가 늘 준비 안 됨으로 보인다.
- Ruling: install-engine은 사본의 setup을 새 프로세스가 아니라 같은 프로세스에서 사본 루트로 돈다 (작업 1) — 시험이 launchctl을 건드리지 않게 — 개발 중 같은 판인데 코드가 다르면 번들 코드가 setup을 한다.
- Ruling: 같은 판 사본이 온전한지는 매니페스트 판, 파일 목록과 크기, 소유자와 권한으로 보고 내용은 비교하지 않는다. 원본 안의 링크·특수 파일은 거절하고 `__pycache__`·`*.pyc`·`.DS_Store`는 복사하지 않는다 (작업 1) — 열린 대화가 쓰는 사본을 바꾸지 않고 번들 변조를 막으려고 — 같은 판·같은 크기로 다시 빌드하면 옛 내용이 남는다.
- Ruling: 옛 판은 어떤 프로세스의 명령 줄에든 그 경로가 있으면 남기고, 프로세스 목록을 못 읽으면 아무것도 지우지 않는다 (작업 1) — 모르면 지우지 않는 쪽이 안전해서 — 정리가 한 번 밀린다.
- Ruling: setup.sh·start-mcp.sh는 폴더 링크와 파일 링크를 모두 따라가 실제 판 폴더를 쓴다. install-engine 중 pip·venv 출력은 버리고 실패 한 줄만 낸다 (작업 1) — 판 폴더를 확실히 쓰고 앱이 한 줄로 읽게 — 의존성 설치가 실패하면 이유가 종류만 나온다.
- Ruling: 엔진 사본 위에 `engine/current` 링크를 두고 MCP는 그 링크의 `start-mcp.sh`로 한 번만 등록한다. 옛 판 정리는 current가 가리키는 판, 그보다 높은 판, 쓰는 프로세스가 있는 판을 남기고, install-engine은 `.setup.lock`을 잡는다 (작업 1 검토) — 판이 바뀌어도 MCP를 다시 등록하지 않아 정리가 등록된 판을 지우는 틈이 없게 — 틀리면 링크가 깨졌을 때 새 Claude 대화의 CUA가 뜨지 않는다(점검 탭이 잡는다).
- Ruling: `.setup.lock`은 같은 스레드가 다시 잡으면 통과한다 (작업 1) — install-engine이 잠근 채 의존성 준비를 불러서 — 다른 스레드는 그대로 막힌다. 첫 설치의 의존성 준비 동안 새 Claude 대화는 최대 320초 기다린다.
- Ruling: 판 높낮이는 점 숫자로 비교하고, 숫자가 같은 다른 이름은 남긴다 (작업 1) — 높은 판을 잘못 지우는 쪽이 더 나빠서 — 낮은 시험판이 다음 높은 판까지 남는다.
- Ruling: current 링크를 바꾸지 못하면 install-engine은 실패한다. launcher는 링크가 안 풀려도 늘 같은 문자열이고, 앱은 그것을 풀지 않고 그대로 등록한다 (작업 1) — 등록과 비교만 하면 되게 — 풀어서 등록하면 정리가 등록된 판을 지우는 틈이 다시 생긴다. 원본 루트가 root 소유면 install-engine이 실패한다(dmg로 끌어 놓은 앱은 사용자 소유다).
- Ruling: Codex 유무는 앱이 직접 본다(/Applications·~/Applications의 Codex.app·ChatGPT.app, `CODEX_CUA_APP_PATH`) (작업 3) — 엔진이 없으면 status로 물을 수 없어서 — status가 읽히면 status가 우선한다.
- Ruling: 번들 밖 개발 빌드는 install-engine도 MCP·스킬도 건드리지 않는다 (작업 3) — 개발 실행이 실제 Claude 설정을 바꾸지 않게 — 개발 빌드에서는 고치기가 아무것도 안 한다.
- Ruling: 바뀐 것이 없으면 설치는 말없이 끝나고, 바뀌었으면 "새 Claude 대화부터 CUA가 붙어요"(Claude Code가 없어 엔진만 깔았으면 "연결 설정을 마쳤어요")를 한 번 알린다 (작업 3) — 켤 때마다 알림이 뜨지 않게.
- Ruling: 제거는 먼저 Codex 호스트를 한 번 확인하고, Claude Code가 앱의 MCP를 못 지우면 결과에 `claude mcp remove -s user cua`를 직접 하라고 덧붙인다 (작업 3) — 호스트가 살아 있으면 MCP·스킬도 안 바꾸고, 말없이 남기지 않으려고.
- Ruling: 개발자 도구 카드의 버튼은 도구가 이미 생겼으면 전체 설치를 돌린다. 스킬은 표식 판과 내용이 번들 것과 같을 때만 준비로 본다 (작업 3) — 한 버튼으로 이어지고 손상된 스킬도 다시 깔려고 — 표식 있는 폴더를 손으로 고치면 켤 때 덮인다.
- Ruling: 제거는 status를 읽었고 호스트가 없을 때, 또는 엔진이 아예 없을 때만 Claude 쪽을 지운다. status를 못 읽으면(시간 초과, 실행 실패, 출력 오류) 아무것도 바꾸지 않고 거절한다. 엔진 setup이 깨져 있으면 엔진 uninstall을 먼저 돌려 그 거절을 따른다 (작업 3 검토) — F2의 "아무것도 바꾸지 않는다"를 지켜 반쯤 지운 상태가 남지 않게 — 엔진이 느릴 때는 제거를 한 번 더 눌러야 한다.
- Ruling: Claude 설정 충돌 카드는 버튼 있는 카드 뒤, 버튼 없는 다른 문제 앞에 둔다 (작업 3 검토) — 자기 cua MCP를 일부러 둔 사람에게도 다시 켜기 같은 버튼이 가려지지 않게 — 충돌이 덜 눈에 띈다(점검 탭에는 늘 보인다).
- Ruling: 켤 때 status가 시간 초과여도 MCP·스킬은 깔고, 엔진 단계만 미뤘다가 그 실행에서 status가 처음 읽힐 때 설치를 한 번 더 돈다 (작업 3 검토) — launcher 경로는 status와 무관하고 R1을 고치기 없이 이루려고 — 엔진 사본이 아직 없으면 그 사이 열린 새 대화에서는 CUA가 뜨지 않는다.
- Ruling: Claude Code는 정해진 자리(~/.local/bin, /opt/homebrew/bin, /usr/local/bin, ~/.claude/local, ~/.bun/bin, ~/.volta/bin, ~/.npm-global/bin, ~/Library/pnpm, ~/.nvm/versions/node/*/bin 높은 판부터)에서만 찾고 로그인 셸은 돌리지 않는다 (작업 3 검토) — 셸 설정이 도는 부작용 없이 흔한 설치를 잡으려고 — 다른 자리에 깐 claude는 못 찾으며, 점검 탭이 "못 찾음"으로 보인다.
- Ruling: 연결 시험 호출과 그 런타임을 알아보는 표시는 시험 스레드의 새 폴더 이름(`codex-cua-probe-…`) 하나다. 시험이 끝나면 그 폴더에서 일하는 런타임만 끝내고 폴더를 지운다. status는 그 폴더의 연결·중계기 기록·활동 줄을 연결, 작업 중, 점유에서 빼고, 중계기는 그 폴더에서 활동 줄을 남기지 않는다 (작업 2) — 평범한 스레드에는 중계기도 주인 이름도 없고 release-session이 같은 방식이라서 — 이름이 같은 폴더에서 일하는 다른 대화는 안 보인다(사실상 없음).
- Ruling: 호스트가 ready가 아니면 연결 시험은 기존 낱말 `host_unavailable`로 곧장 끝나고 아무것도 켜거나 끄지 않는다. 폴더를 못 만들면 시험 없이 `failed`다 (작업 2) — 앱이 이미 아는 낱말이라서 — 앱은 시작 중과 꺼짐을 `status.host.state`로 가려야 한다.
- Ruling: `host.engine_version`은 호스트가 ready·starting·stopping일 때만 내고, 판 비교는 문자열 그대로 한다 (작업 2) — 닫힌 기록의 판은 낡은 정보라서 — 같은 판 번호로 다시 빌드한 개발 빌드는 못 잡는다.
- Ruling: install-engine의 정리는 판을 바꾸기 직전 current가 가리키던 사본도 그 설치에서는 남기고 다음 설치 때 지운다 (작업 1 검토의 사소 지적, 메인이 고침 6a30ecd) — 바꾸기 직전에 시작한 대화가 그 사본으로 들어가는 중일 수 있어서 — 옛 사본 하나가 다음 설치까지 남는다.
- Ruling: 같은 판 엔진의 깨진 곳을 고치는 설치는 install-engine의 setup이 모두 ready일 때만 "연결 설정을 마쳤어요"라고 하고 "새 Claude 대화부터 CUA가 붙어요"는 말하지 않는다 (작업 3 검토 반영) — 다시 돌려도 안 바뀌는 상태에서 켤 때마다 배너가 뜨지 않고, Claude 쪽이 그대로일 때 새 대화를 말하지 않게 — 일부만 고쳐지면 말이 없고 카드만 남는다.
- Ruling: 설치는 Codex 유무와 개발자 도구를 보기 전에 status를 한 번 읽고, Codex는 status가 말하면 그 말(`codex.installed`)을, 말이 없거나 못 읽으면 앱의 디스크 확인을 따른다 (작업 3 검토 반영) — 엔진이 받지 않는 Codex가 읽을 때마다 설치를 부르는 연쇄를 막으려고 — 엔진이 늦게 마음을 바꾸면 다음 정상 읽기까지 기다린다.
- Ruling: ~~status의 시간 초과와 실행 실패는 둘 다 "엔진을 못 물어봄"으로 보고 엔진 단계만 미룬다. 제거는 다섯 오류를 모두 거절한다 (작업 3 검토 반영)~~ → 아래 두 번째 검토의 Ruling으로 바뀜.
- Ruling: 판 없는 엔진은 앱 판을 알 때만 엔진 문제로 본다. 문제 순서는 Codex 없음 > 설치 문제 > Codex 연결 없음 > 충돌 > 끝난 연결 > 남은 점유 (작업 3 검토 반영) — 개발 빌드는 비교할 판이 없어서 — 개발 빌드가 판 없는 엔진을 문제로 안 본다.
- Ruling: `~/.claude.json`의 읽은 결과는 변경 시각·ctime·크기·inode가 같으면 다시 파싱하지 않는다. build-app.sh는 rsync `-l`로 링크를 링크로 복사해 뒤의 검사가 거르게 한다 (작업 3 검토 반영) — 2~5초마다 657KB를 파싱하지 않고, 링크가 말없이 빠지거나 풀려 들어가지 않게 — 시각 해상도 안의 같은 크기 두 번 쓰기는 이론상 놓친다.
- Ruling: 업데이트는 도우미를 띄운 뒤에 옛 번들을 백업으로 옮기고, 받은 앱의 번들 ID(`dev.chenjing.cua-bar`)와 파일 이름(`CUABar-v<판>-macos-arm64.dmg`, 판은 x.y.z)을 글자 그대로 본다 (작업 5) — 도우미를 못 띄우면 되돌릴 수 있고, 같은 팀의 다른 앱이나 다른 판 문서가 들어오지 않게 — 번들 ID를 바꾼 판과 선행 0이 있는 판은 자동 업데이트가 막힌다.
- Ruling: 다시 켜기가 Codex 종료를 기다리는 중이면 바꿔 끼우지 않는다. 미룬 것은 상태를 읽을 때마다 다시 보고, 실패한 판은 다음 하루 확인·다음 실행 때 다시 한다 (작업 5) — 메모리에만 있는 기다림이 사라지지 않고 5초마다 받기를 반복하지 않게 — 업데이트가 최대 10분, 일시 실패는 최대 하루 늦다(그동안 버튼으로 받는다).
- Ruling: 확인 자체가 실패하면(오프라인 등) 기록도 알림도 없고, 문서는 읽혔는데 file·sha256·size가 틀리고 판이 더 높으면 실패로 기록해 버튼과 알림을 낸다. 하루 확인은 마지막 시각을 저장하지 않고 켜질 때마다 확인한 뒤 24시간씩 기다린다 (작업 5) — 사이트에 새 판이 있는데 모르게 되지 않고 "켜질 때 한 번"을 지키려고 — 자주 켜는 맥이 /version을 더 자주 부른다.
- Ruling: 업데이트 표시는 `~/Library/Application Support/CUABar/update-pending.json`, 실패 기록은 UserDefaults `update.failedVersion/failedStep/failedAt/failureNotifiedVersion`이다. 앱 판보다 낮은 표시는 지우고 높은 표시는 건드리지 않는다 (작업 5) — 옛 GitHub 확인의 `update.*` 키와 섞이지 않고 낡은 표시가 엉뚱한 때 뜨지 않게 — 옛 키는 쓰지 않은 채 남는다.
- Ruling: 시작하지 못하는 명령(launchFailed, 예: 실행 권한이 빠진 codex-cua)은 설치가 다시 쓰는 문제로 보고 카드에 "연결 명령을 실행하지 못했어요"와 고치기를 둔다. 시간 초과만 "엔진을 못 물어봄"으로 엔진 단계를 미룬다. 제거는 명령이 돌기는 하는데 status를 못 말하면(commandFailed·invalidOutput·unsupportedSchema) 엔진 제거기를 먼저 돌리고(제거기가 host.json을 보고 스스로 거절한다), 답이 아예 없을 때(시간 초과·시작 못 함)만 아무것도 바꾸지 않고 거절한다 (작업 3 두 번째 검토, 메인이 고침 c9337e5) — 기다려도 안 풀리는 경우에 "잠시 뒤"라고 하지 않고 F2를 지키려고 — 시작 못 하는 명령이 있는 동안에는 제거가 거절된다(고치기가 먼저다).
- Ruling: claude는 찾은 폴더를 PATH 맨 앞에 두고 돌린다. 그래도 시작하지 못하면(종료 127) 실패로 굳히지 않고 Claude Code가 없을 때처럼 이번 실행에서는 MCP·스킬을 건너뛴다. 카드는 MCP·스킬을 말하지 않고, 기다리지도 않으며(따라잡기가 읽을 때마다 돌지 않게), 다음 앱 실행 때 한 번 더 한다 (작업 3 두 번째 검토, c9337e5) — nvm으로 깐 claude가 옆의 node를 찾게 하고, 못 찾을 때 켤 때마다 실패 카드가 남지 않게 — 그런 맥은 점검 탭의 줄로만 안다.
- Ruling: 남이 정한 로그인 환경 값(login_environment conflict)은 설치 문제가 아니다. 설치를 다시 돌리지 않고, Codex 연결 없음 다음 자리에 버튼 없는 카드("Codex 로그인 설정이 다른 값과 겹쳐요 / 점검 탭에서 겹치는 값과 치우는 방법을 보세요")로 알린다. 같은 판을 고친 뒤 결과의 conflict는 준비로 셈하고, 그 밖에 준비되지 않은 곳이 남으면 "다시 설정했지만 고쳐지지 않은 곳이 있어요 — 점검 탭에서 보세요"를 낸다 (작업 3 두 번째 검토, c9337e5) — setup은 남의 값을 덮지 않아 고치기가 아무것도 못 하므로 — 점검 탭(작업 4)이 겹치는 키와 `launchctl unsetenv` 안내를 보여야 한다.
- Ruling: 엔진의 답이 없을 때 MCP는 `engine/current/start-mcp.sh`가 실제로 있을 때만 넣고, 없으면 엔진 단계와 함께 미룬다. 스킬은 그대로 깐다. 미룬 것을 따라잡는 설치는 그 읽기의 답을 넘겨받아 status를 다시 묻지 않는다 (작업 3 두 번째 검토, c9337e5) — 앱 엔진이 한 번도 풀리지 않은 맥에서 뜨지 않는 서버를 등록하지 않고, status가 들쭉날쭉할 때 설치가 연달아 돌지 않게 — 따라잡기 전에 바뀐 상태는 다음 읽기에서야 반영된다.
- Ruling: 받은 앱과 dmg의 서명은 `codesign -dv` 출력의 TeamIdentifier 글자가 아니라 요구 사항으로 검증한다(anchor apple generic, Developer ID 인증서, 팀 OU S3KC8R8VDL, 앱은 identifier dev.chenjing.cua-bar까지). dmg는 attach 전에 본다. install.sh도 같은 요구 사항으로 바꾼다(작업 6) (작업 5 검토) — 글자 읽기는 ad hoc 서명이나 끼워 넣은 줄도 통과시켜 공격 받은 사이트가 다른 앱을 넣고 켤 수 있어서 — 인증서 구조가 바뀐 판은 자동 업데이트가 막힌다.
- Ruling: 지금 프로세스가 같은 요구 사항을 만족하는 정식 판일 때만 업데이트를 확인하고 바꿔 끼운다. ad hoc 로컬 빌드는 개발 빌드처럼 확인도 버튼도 없다 (작업 5 검토, R7을 넓힘) — 검수 중인 로컬 빌드가 말없이 바뀌거나 로그인 항목이 풀리지 않게 — ad hoc으로 깐 맥은 정식 판을 한 번 손으로 깔기 전까지 저절로 올라가지 않는다.
- Ruling: 업데이트 뒤 문구("CUA Bar를 x.y.z로 올렸어요…")는 배너가 아니라 시스템 알림 하나(`updated-<판>`)로 내고, 그때 설치 루틴의 배너는 비운다 (작업 5 검토) — 업데이트는 팝오버가 닫혀 있을 때만 하고 새 판도 닫힌 채 켜져 배너는 아무도 못 봐서 — 알림을 꺼 둔 사람은 알림 센터에서도 못 본다.
- Ruling: 앱 자리 맞바꾸기는 `renamex_np(RENAME_SWAP)` 한 번으로 하고 되돌리기도 SWAP으로 한다. 바꾼 뒤에는 detach를 기다리지 않고 끝내며, 도우미는 옛 프로세스가 끝난 뒤 1초 쉬고 `open -g`를 부르고 10분까지 기다린다. 켜질 때와 설치 전에 지난 실행이 남긴 `.CUABar-update.*`(옛 사본이 없는 것)와 마운트를 치운다. 정식 판이 아니라서 업데이트가 꺼져 있으면 진단 복사에 그렇다고 적는다 (작업 5 검토, 재검토의 사소 반영) — 앱 자리가 비거나 새 판을 못 켜는 틈을 줄이고, 꺼진 업데이트를 알아챌 길을 두려고 — 남은 마운트는 다음 실행까지 남는다.
- Ruling: `doctor --probe`는 시험 동안만 SIGTERM 처리기를 달아 첫 신호를 중단으로 바꾸고, 끊긴 정리는 SIGKILL 전 2초 안에 끝낸다(호스트 1.0초, ps·lsof 0.6초, 런타임은 기다리지 않음). 중계기 기록의 cwd는 읽기에 실패하면 처음 시작한 폴더를 적고, 시험 줄은 시험 폴더 중계기 기록의 writer로 거른다 (작업 2 검토 반영, 9f50d46) — 앱이 시간 초과나 취소로 끊어도 시험 런타임과 폴더가 남지 않게 — 그 안에 답하지 못하는 ps는 포기하니 런타임이 Codex가 내릴 때까지 남을 수 있다.
- Ruling: 받은 앱과 dmg는 `codesign --verify -R '=<요구 사항>'`으로 보고(종료 3은 팀 불일치, 그 밖은 서명 실패, 둘 다 "받은 파일" 문구), Security 프레임워크는 지금 프로세스가 정식 판인지(SecCodeCopySelf)에만 쓴다. 맞바꾸기가 안 되는 볼륨(RENAME_SWAP 불가)은 실패로 끝내고 두 번 옮기기로 물러나지 않는다. 업데이트 알림을 보내지 못한 빌드는 그 문구를 배너로 낸다 (작업 5 검토 반영, 7547183) — 요구 사항 문자열을 한 곳에 두고 앱 자리가 비는 길을 다시 만들지 않으려고 — 진단에서 dmg와 앱 중 어느 쪽이 걸렸는지 안 보이고, APFS가 아닌 볼륨의 앱은 저절로 안 올라간다. 0.7.0 릴리스 dmg와 그 앱은 이 요구 사항을 만족한다(메인 확인).
- Ruling: 점검 탭은 F3의 아홉 줄을 지킨다. 개발자 도구는 '파이썬 환경' 줄에, 옛 cua 플러그인은 'MCP' 줄에 붙인다. 카드에 오른 문제의 줄은 카드와 같은 목록으로 판단해 "위 카드에서 고쳐요"만 보인다 (작업 4) — 줄 수를 늘리지 않고 카드와 줄이 엇갈리지 않게 — 옛 플러그인을 찾는 사람은 MCP 줄을 봐야 한다.
- Ruling: 연결 시험은 앱도 `host.state == ready`일 때만 부르고, 결과와 시각은 메모리에만 둔다. `doctor --probe`는 통과하지 않으면 종료 1로 끝나며 보고서를 찍으므로 0과 1을 모두 읽는다. `approval_required`·`cleanup_unconfirmed`도 통과하지 못한 시험으로 보고, `host_unavailable`은 시험하지 않은 것으로 본다 (작업 4) — 꺼짐과 시작 중을 가르고, 낡은 결과가 남지 않게 — 앱을 다시 켜면 "아직 시험하지 않았어요"로 돌아간다.
- Ruling: 설치 직후 시험은 설치와 같은 작업(`perform(.runSetup)`) 안에서 돌고 알림은 그 뒤에 낸다. '고치기 뒤에도 그대로'는 이 실행에서 설치가 한 번이라도 끝났는지로 본다 (작업 4) — 시험이 설치와 겹치지 않고 알림이 시험 결과를 담게 — 시험 동안(최대 25초) 카드가 "연결을 설정하는 중"으로 보인다.
- Ruling: 업데이트 직후 연결 시험이 실패하면 그 문장을 업데이트 알림(`updated-<판>`) 본문 끝에 붙이고 배너는 비운다. 알림이 꺼져 있으면 배너의 업데이트 줄 끝에 붙인다. 업데이트가 아닌 설치는 지금처럼 배너 끝에 붙인다 (메인, 작업 4·5 합치기 7e7149b) — 실패를 알림과 배너에서 두 번 말하지 않고, 닫힌 팝오버의 배너로만 말해 놓치지 않게 — 틀리면 알림을 꺼 둔 사람만 배너로 본다.
- Ruling: 바꿔 끼우기는 연결 시험이 도는 동안에도 미룬다(`isQuietForUpdate`에 `isProbing`). 상태를 읽은 뒤에는 미룬 설치(그 읽기의 답을 넘김)를 먼저, 미룬 업데이트를 그 뒤에 돌린다 (메인, 합치기 7e7149b) — 시험 중인 엔진 명령 아래에서 앱이 바뀌지 않게, 설치와 업데이트가 같은 읽기에서 겹치지 않게 — 틀리면 업데이트가 시험 한 번(최대 25초)만큼 늦어진다.
- Ruling: 엔진 setup.py의 `PLUGIN_ID`와 runtime_paths.py의 `PUBLIC_PLUGIN_ID`에 남은 `cua@chenjing-plugins`는 그대로 둔다 (작업 6 검토) — source.json의 엔진 신원을 비교하는 내부 값이라 바꾸면 이미 풀린 엔진 사본의 묶음이 무효가 되고, 사람에게 보이지 않는다 — 틀리면 낡은 말 grep에 두 곳이 남는다.
- Ruling: Codex가 없으면 점검 탭은 Codex 줄을 카드가 맡는 줄("위 카드에서 고쳐요")로 두고, 엔진·MCP·스킬·파이썬 환경·래퍼·중계기 줄은 "대기 — Codex가 생기면 맞춰요"로 둔다. 다만 앱이 깔지 않은 cua MCP·스킬과 옛 cua 플러그인은 Codex가 없어도 그 줄에 충돌과 명령을 보이고, 명령 뒤 안내는 "Codex를 깔면 앱이 연결해요"로 쓴다 (작업 4 검토 반영 e372119, 두 번째 검토 반영 메인 9d045cb) — Codex가 없을 때 설치는 엔진을 풀지 않으니 그 줄들은 문제가 아니라 미룬 것이고(F1 케이스 1), 남의 것은 Codex가 생겨도 설치가 그대로 두므로 기다려서는 풀리지 않는다(F1 케이스 2) — 틀리면 Codex가 없는 동안 정말 깨진 엔진도 대기로 보인다.
- Ruling: 명령 복사는 받은 글만 넣고, 앱 판·로그인 항목·업데이트 줄은 진단 복사에만 붙인다(`copyDiagnosis`) (작업 4 검토 반영) — 붙인 줄이 터미널에서 명령으로 돌지 않게 — 틀리면 없음.
- Ruling: Claude Code가 없을 때 받는 법은 공식 문서가 권하는 네이티브 설치 `curl -fsSL https://claude.ai/install.sh | bash`로 보인다 (작업 4 검토, code.claude.com/docs/en/setup) — npm 설치는 Node 22 이상이 먼저 있어야 해서 Claude Code가 없는 맥에서 대개 실패한다 — 틀리면 공식 설치 주소가 바뀔 때 줄이 낡는다.
- Ruling: 앱이 깔지 않은 스킬은 지우라고 하지 않고 `mv ~/.claude/skills/cua ~/cua-skill-backup`(skills 폴더 밖)으로 옮겨 두라고 안내하고, 충돌을 알리는 카드·배너는 "치우는 방법"이라고 쓴다 (작업 4 검토) — 사용자의 파일을 지우게 하지 않되, skills 안의 다른 이름은 그대로 스킬로 읽혀 충돌이 남아서 — 틀리면 홈 폴더에 백업 폴더가 하나 남는다.
- Ruling: 설치가 도는 동안 '연결 시험' 버튼은 꺼지고 누른 시험은 거절하되, 설치 직후 시험은 그대로 돈다. 그 시험 동안(최대 25초) `.runSetup`이 작업 중으로 남아 연결 탭의 줄 버튼이 기다리고 자동 정리가 미뤄지는 것은 받아들인다 (작업 4 검토) — 엔진 사본이 바뀌는 중에 시험이 돌아 엉뚱한 실패를 남기지 않게, 시험과 설치가 같은 작업 안에서 겹치지 않게 — 틀리면 설치 직후 25초 동안 줄 버튼이 늦게 듣는다.
- Ruling: 저장소 루트 README는 새로 만들지 않고 marketplace.json 최상위 설명에 "CUA는 플러그인이 아니라 CUA Bar 앱(https://cua.chenjing.org) 하나로 깐다"를 더한다 (작업 6) — 지시가 가정한 루트 README가 git 기록 전체에 없고 새 파일은 요청 밖이다 — 틀리면 GitHub 첫 화면에 CUA Bar 안내가 없다.
- Ruling: 판 0.8.0은 엔진 매니페스트와 host_mcp.py의 VERSION 두 곳만 바꾸고 시험 기대값은 고치지 않는다 (작업 6) — 엔진 시험은 매니페스트를 읽어 비교하고 Swift 시험의 0.7.0은 가짜 앱 판이다 — 틀리면 가짜 값에 기대는 시험이 다음 판 때 깨진다(그때 시험이 알려 준다).
- Ruling: install.sh는 SHA-256 확인 뒤 attach 전에 dmg를 팀 요구 사항(identifier 없음)으로, 복사한 앱은 `codesign --verify --deep --strict` 뒤 앱 요구 사항으로 검증한다. 끝 안내("켜진 앱이 cua MCP와 스킬을 저절로 깝니다…", "'점검' 탭")는 앱을 켠 경우에만 낸다 (작업 6, 검토 반영 f4536be) — 앱 업데이트와 같은 확인을 거치고 낯선 이미지를 마운트하지 않게, 앱이 켜져야 깔리므로 — 틀리면 팀 글자만 맞지 않는 dmg는 한 줄 설치도 거절한다.
- Ruling: package-release.sh의 x.y.z 검사는 남기고 이유만 앱 업데이트의 파일 이름 규칙(`CUABar-v<x.y.z>-macos-arm64.dmg`)으로 고친다. 문서는 GitHub 릴리스를 선택으로 적고 `/version`의 `release` 칸은 그대로 둔다 (작업 6) — 앱 업데이트와 한 줄 설치가 GitHub를 보지 않고 R5가 릴리스를 할 때마다 묻는 일로 둬서 — 사용자가 GitHub 릴리스를 계속 필수로 본다면 문구를 고쳐야 한다.
- Ruling: 엔진 README는 "앱 없이 엔진만 따로 까는 길은 제공하지 않는다"고 쓰고 setup·start는 개발과 진단용으로 둔다. 앱 README의 "지우기"는 앱 지우기가 남기는 것(앱 파일, 연결 기록, 업데이트가 남긴 옛 앱 한 벌, 설정 plist, 호스트 상태 폴더)과 "필요 없으면 직접 지워요"를 적는다 (작업 6, 검토 반영 f4536be) — 명세가 앱 없는 설치를 없앴고, 지운 뒤 남는 것을 사람이 알게 — 틀리면 앱 없이 쓰려는 사람이 길이 막혔다고 읽는다(명령은 그대로 있다).
- Ruling: R14의 "Codex를 다시 켜면 새 설정이 적용돼요"는 카드에 다른 문제가 없을 때(준비됨·작업 중) 카드의 다음 할 일로 오르고, 남은 점유처럼 다른 문제가 카드를 차지하는 동안은 점검 탭의 Codex 호스트 줄에 보인다 (verify S19, 메인) — 카드는 한 번에 하나이고 손볼 문제가 먼저이며, 0.7.0부터 같은 순서다 — 틀리면 다른 문제가 남아 있는 동안 다시 켜기 안내를 카드에서 못 본다.
