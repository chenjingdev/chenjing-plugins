# CUA 메뉴 막대 앱
## 목적
Codex를 평소처럼 켜도 Claude가 CUA로 바로 붙게 하고, 메뉴 막대에서 상태를 보고, AI가 정리 없이 끝나며 남긴 브라우저 점유를 풀어 다음 연결이 막히지 않게 한다.
## 범위
회사 맥의 cua 0.6.0(자동 연결)과 Portwarden의 CUA 기능(연결 목록·종료·놓아주기·중계기)을 떼어 agent-bar 같은 macOS 메뉴 막대 앱 하나로 다시 만든다. 체크리스트 25개가 모두 이번 판이다.
## 하지 않는 것
- Codex 없이 혼자 도는 CUA, Codex의 모델·권한·승인 설정 바꾸기, cmux-cua 설정 바꾸기, macOS 밖의 운영체제.
## 기능
- F1 Codex를 Dock·Spotlight·업데이트 뒤 재실행 등 평소처럼 켜도 Claude가 바로 붙고, 꺼져 있으면 Claude 대화를 열 때 뒤에서 켠다(대화를 여는 것이 곧 쓰는 것이라 따로 고르는 스위치는 없다). 앱은 로그인할 때 자동으로 뜬다 [사용자]
  - 케이스: 앱이나 플러그인이 깨짐 → Codex는 연결 없이 원래대로 켜지고 아이콘이 문제로 바뀐다
  - 케이스: Codex가 연결 없이 켜져 있음 → 끄지 않고 "하던 Codex 작업이 끊긴다"를 적은 알림으로 다시 켤지 묻고, 누르면 정상 종료(강제 종료 없음) 뒤 다시 켠다
- F2 아이콘 하나로 준비·문제·작업 중을 구분하고, 올리면 한 줄 요약 툴팁, 누르면 연결 목록이 열린다. 문제마다 다음에 할 일 한 줄이 있고, 누를 곳은 한 군데다: 앱 전체 문제는 상태 카드의 고치는 버튼, 연결 하나의 문제는 목록 맨 위 그 줄의 버튼(2026-10-19 사용자 결정으로 바꿈) [사용자]
- F3 줄마다 버튼은 그 상태에 맞는 하나다. AI가 살아 있는 연결은 "탭 풀기"(잡은 브라우저 탭만 풀고 연결은 그대로), 끝난 연결과 주인 없는 cmux-cua 연결은 "정리"(탭을 풀고 남은 연결을 끈다), 주인이 사라진 점유는 세션 ID로 "탭 풀기". 손볼 것은 "모두 정리"로 한 번에 한다(2026-10-19 사용자 결정으로 바꿈) [사용자]
  - 케이스: 탭 풀기가 안 됨 → 확장 초기화 방법과 함께, 초기화하면 끊길 살아 있는 연결 목록을 보인다
- F4 Claude·Codex 연결 목록(작업 폴더, 시작 시각, 메모리, 살아 있는지, 오래 쉬는지). 끝난 연결의 정리는 탭을 푼 뒤 정상 종료하고, 시간 안에 안 꺼지면 묻지 않고 강제로 끈다. 살아 있는 AI의 연결은 앱에서 끄지 않는다(그 AI 쪽에서 끈다). 이 기능은 Portwarden에서 빼서 옮기고, 원래 작업은 브랜치로 남긴다(2026-10-19 사용자 결정으로 묶음 종료·강제 종료 버튼을 뺌) [사용자]
  - 케이스: 탭을 풀지 못한 채 강제로 꺼짐 → 남은 점유를 F3의 주인 없는 점유로 보인다
- F5 AI가 정리 없이 끝나면 앱이 대신 점유를 놓아주고, 점유가 오래 남으면 알린다 [사용자]
- F6 cmux-cua 같은 다른 도구 상태, 지금 어느 AI가 화면·포커스를 쓰는지, 최근 조작 기록과 진단 복사 버튼을 한 곳에 보인다 [사용자]
- F7 agent-bar처럼 GitHub Releases에서 받고, 앱에서 Claude 플러그인을 설치·갱신하고, 새 버전을 알린다 [사용자]
- F8 Mac이 잠겨 Codex CUA 서비스의 자동 잠금 해제가 실패하면, 앱이 묻지 않고 그 서비스를 다시 켜(정상 종료만) 다음 호출이 다시 풀어 보게 하고, cuabar 스킬은 30초쯤 뒤 다시 부르게 한다. 잠금 한 번에 다섯 번까지다(2026-10-25 사용자 결정 "예. 최대 5번까지 시도하게") [사용자]
  - 케이스: 다섯 번 다시 켜도 안 풀림 → 잠금마다 한 번 알리고, 누르면 기록 탭이 열린다
  - 케이스: 실제 입력이 있어 자동 잠금 해제가 멈췄거나 ChatGPT 스레드에 붙일 수 없다는 거절 → 다시 켜지 않고 화면 잠김으로 적는다
- F9 새 판이 저절로 올라가 켜지면 Claude Code에 CUA의 옛 이름(0.8.0의 `cua` MCP·스킬, 옛 플러그인 `cua@chenjing-plugins`·`cua@ubion`, 옛 도구 이름 `mcp__cua__…`·`mcp__plugin_cua_cua__…`를 적은 허락 규칙·훅)이 남았는지 읽어, 있으면 업데이트 알림에 한 줄을 붙이고 점검 탭에 고칠 명령·규칙을 복사 버튼과 함께 보인다. auto 모드에서 `mcp__cuabar` 허용 규칙이 없으면 점검 탭이 그 한 줄을 안내한다. 앱은 설정 파일을 고치지 않는다(2026-10-26 사용자 결정 "예") [사용자]
  - 케이스: 옛 이름이 남은 채 업데이트 알림을 누름 → 점검 탭이 열린다
- F10 Codex 26.1023부터 Codex는 앱이 시작하거나 다시 연 대화만 브라우저를 쓰게 한다. 엔진이 여는 대화(Claude 다리의 대화, 탭 풀기용 숨은 대화)의 브라우저 호출은 늘 거절되므로, 세션 ID로 푸는 탭 풀기는 이유 `browser_blocked`로 끝나고 앱은 "Codex가 Claude 대화의 브라우저 사용을 막아서 풀 수 없어요" 한 줄만 보인다. 확장 초기화 안내를 열지 않고 보던 탭도 옮기지 않으며, 모두 정리는 처음 막히면 남은 세션을 더 묻지 않고, 자동 정리는 그 뒤 앱을 다시 켤 때까지 남은 점유(세션)를 시도하지 않는다(끝난 연결의 정리는 브라우저를 거치지 않아 그대로 한다). Claude에는 사용자 설정이 아니라 Codex의 제한이고 데스크톱 앱 조작은 되며 브라우저 일은 Codex 앱에 직접 시키라고 알린다(2026-10-28 사용자 요청) [사용자]
  - 케이스: 모두 정리에서 첫 세션이 `browser_blocked` → 나머지 세션은 묻지 않고, 화면은 그대로다
  - 케이스: 막은 뒤 새 점유가 생김 → 자동 정리는 시도하지 않는다
  - 케이스: 막은 뒤 새 끝난 연결이 생김 → 자동 정리가 그 연결만 정리한다(`release --ended --connections-only`)
## 공통 규칙
- R1 앱은 사용자가 누르기 전에는 Codex·Chrome·AI를 끄지 않고, 어떤 창도 앞으로 끌어오지 않는다 — 하던 작업과 포커스를 지키려고 [AI 가정]
- R2 기록과 진단 복사에는 화면, 요청 내용, 시크릿을 넣지 않고 이 맥 밖으로 보내지 않는다 — 기존 cua 플러그인 규칙 [AI 가정]
- R3 앱을 지워도 Codex는 깨지지 않고 원래대로 켜지며, 기록 탭 맨 아래의 앱 지우기는 연결 설정과 중계기까지 되돌린다 — 앱이 사라진 뒤 Codex가 못 켜지는 일이 없게 [AI 가정]

- Ruling: 0.6.0 이하에서 올릴 때는 `/cua:setup`을 한 번 돌리라고 README에 적었다 (P1) — 옛 `command.py`로 `codex-cua setup`을 한 번만 돌리면 옛 실행 스크립트가 남는다 — 틀리면 그 사용자는 셸 단계 대체 실행 없이 쓴다(연결은 된다).
- Ruling: `--root-resolved`는 그 이름(`ROOT_RESOLVED_FLAG`)을 정의한 setup.py에만 넘긴다 (P1) — 0.7.0 이전 판은 모르는 인자를 Codex 인자로 넘겨 doctor·start·uninstall을 깨뜨렸다 — 틀리면 그 이름을 바꾼 미래 판에서 등록부를 한 번 더 읽는다.
- Ruling: Codex 시작 경로(`--exec-wrapper`)에서는 `--` 뒤의 인자만 원래 CLI에 넘긴다 (P1) — 내부 인자가 Codex에 새지 않게 — 틀리면 `--` 앞에 붙인 인자가 버려진다.
- Ruling: Codex를 켜는 동안에는 파이썬 환경을 고치지 않는다(`ensure_dependencies(repair=False)`, 사용자 스위치가 아닌 내부 인자) (P1) — Codex 시작이 pip·잠금 때문에 늦어지지 않게 하고, 고치기는 setup과 Claude 대화 시작이 맡는다 — 틀리면 환경이 망가진 동안 Codex는 연결 없이 켜진다. 준비 확인의 10초 제한은 남는다.
- Ruling: `CODEX_HOST_CUA_AUTOSTART=0` 끄기 스위치를 지웠다 (P1) — F1 [사용자] "대화를 여는 것이 곧 쓰는 것이라 따로 고르는 스위치는 없다" — 틀리면 회사 맥 0.6.0 시험 설치에서 이 스위치를 쓰던 곳이 그 기능을 잃는다.
- Ruling: 실행 점유 파일은 `O_NOFOLLOW`로 연다 (P1) — 확인과 열기 사이의 틈과 끊긴 링크를 함께 막는다 — 알려진 손실 없음.
- Ruling: 시험에서 금지된 호출을 잡는 덫은 `BaseException`으로 만든다 (P1) — `main()`의 대체 실행이 `AssertionError`를 삼켜 회귀가 통과할 수 있었다 — 없음.
- Ruling: 등록된 플러그인이 0.7.0보다 낮은 판이어도 Codex 시작을 그 판에 넘긴다. 0.7.0이 거절하지 않고 README에 적었다 (P1 검토) — 정상 갱신에서는 생기지 않고, 거절하면 0.7.0 setup과 옛 래퍼가 섞이거나 Claude가 붙지 않는다 — 틀리면 그 상태에서는 0.7.0의 실패 경로 강화를 못 받는다. 이 맥은 지금 0.5.0이 등록돼 있어 실기 확인은 0.7.0을 등록한 뒤에 한다.
- Ruling: 원래 CLI 경로를 기록하지 않은 옛 실행 스크립트에서 파이썬 환경까지 준비되지 않으면 Codex가 켜지지 않는 좁은 경우는 고치지 않고 README의 보호 밖으로 둔다 (P1 검토) — `/cua:setup`과 앱의 설치가 새 실행 스크립트를 쓰므로 옛 명령으로 한 번만 setup한 사이에만 생기고, 앱 찾기로 메우면 시험이 실제 /Applications에 기댄다 — 틀리면 그 사이 환경이 깨졌을 때 Codex가 안 켜진다.
- Ruling: 일하는 중(active)인 연결을 하나 놓아줄 때는 한 번 묻는다. 쉬는 연결과 끝난 연결은 묻지 않는다 (P3 뒤 메인) — Codex 대화는 진행 중인 턴을 놓으면 그 턴의 다음 브라우저 조작이 시간 초과까지 멈추고(E1 Q4), 중계기는 앱의 턴 번호를 바꿀 수 없다. Claude 대화도 하던 탭이 닫힌다 — 틀리면 일하는 연결을 놓을 때 한 번 더 누른다.
- Ruling: 대화 끝 정리(turn_ended)는 Codex를 다시 켜지 않는다. 호스트가 없으면 연결 없이 답하고 점유 기록은 열린 채 둔다. Codex를 켜는 것은 실제 도구 호출뿐이다 (P2 뒤 메인) — Claude는 턴마다 정리를 부르므로, 사용자가 끈 Codex가 턴이 끝날 때마다 다시 켜질 수 있었다 — 틀리면 끊긴 뒤 남은 점유는 다음 호출이나 앱의 놓아주기에서 풀린다.
- Ruling: 중계기가 꺼져 주인을 알 수 없는 런타임은 "Codex만" 묶음 종료에서 빼고, 하나씩 끄기와 "전체"로만 끈다 (P4 뒤 메인) — R8: Claude 대화의 런타임일 수 있다 — 틀리면 중계기가 꺼진 동안 Codex 런타임을 하나씩 꺼야 한다.
- Ruling: 살아 있는 브리지가 재연결 전에 쓰던 옛 호스트의 세션은 주인 없는 점유로 보고 콕 집어 풀기로 푼다. 살아 있는 세션은 살아 있는 브리지의 지금 세션과 살아 있는 중계기의 열린 범위뿐이다 (P2·P4 뒤 메인) — 재연결 뒤 옛 세션의 점유는 아무도 끝낼 수 없었다 — 틀리면 Codex를 다시 켤 때마다 남은 탭이 브리지가 끝날 때까지 막힌다.
- Ruling: 중계기 덮어쓰기의 `omit_tools_from`·`tools`는 앱 판과 맞는 번들 플러그인 `.mcp.json`에서만 가져오고, 맞지 않으면 덮어쓰지 않는다 (P3) — `mcp get`이 이 둘을 숨긴다 — 틀리면 그번 시작은 중계기 없이 켜진다.
- Ruling: 덮어쓰기 값은 백엔드에 주기 전에 원래 CLI로 다시 읽어 env만 다른지 확인한다 (P3) — `-c`는 못 읽는 값을 조용히 문자열로 받는다 — 틀리면 시작마다 약 40 ms가 더 든다.
- Ruling: 중계기를 단 백엔드가 시작 중에 죽으면 중계기 없이 한 번 더 띄운다(`relay_reason: backend_rejected`) (P3) — 덮어쓰기가 그 시작의 유일한 새것이고, 백엔드가 없으면 Codex가 아예 안 된다 — 틀리면 시작이 한 번 더 걸린다.
- Ruling: 중계기 고정 사본은 지원 폴더가 이미 있을 때만 새로 쓰고, 폴더를 만들지는 않는다 (P3) — 폴더 만들기는 setup의 일이다 — 틀리면 setup을 한 번도 안 한 맥에는 중계기가 없다.
- Ruling: host.json에 `relay`, `relay_launcher`와 함께 꺼진 이유 `relay_reason`(정해진 낱말)을 적는다 (P3) — 진단과 엔진이 왜 꺼졌는지 알아야 한다 — 읽는 쪽은 모르는 키를 무시한다.
- Ruling: 중계기의 놓아주기는 하위 에이전트 범위를 `SubagentStop`, 나머지를 `Stop`으로 끝낸다 (P3) — 번들 플러그인의 훅이 그렇게 보낸다 — 틀리면 하위 에이전트 놓아주기만 확인되지 않음으로 남는다.
- Ruling: 중계기 뒤의 런타임은 중계기 없을 때와 같은 환경을 받는다(경로 원복, `CODEX_CUA_*` 제거). 셸 대체 실행도 같다 (P3) — 런타임이 자기를 다시 띄울 때 중계기를 또 띄우지 않게 — 없음.
- Ruling: 중계기 시간 — 제어 놓아주기는 실행 중 호출을 2.5초, 범위마다 4초, 모두 10초까지 기다리고, 멈출 때의 자동 놓아주기는 신호부터 3초로 묶는다 (P3) — records.md와 Portwarden의 대기 시간 — 틀리면 엔진은 놓아주기 답을 13초 넘게 기다려야 한다.
- Ruling: 중계기는 열린 범위가 500개를 넘으면 가장 오래된 것부터 잊고, 포기한 자기 요청 id는 최근 64개만 기억해 그 늦은 답을 삼킨다 (P3) — 기록과 메모리가 끝없이 늘지 않게 — 틀리면 그 한도를 넘은 아주 드문 경우만 놓친다.
- Ruling: activity 잠금은 Node에서 `open(O_EXLOCK|O_NONBLOCK)`, 파이썬에서 `fcntl.flock`으로 잡는다. 둘은 macOS에서 서로를 막는다 (P3·P2) — Node에는 flock이 없다 — 틀리면 activity 파일이 잘리지 않을 뿐이다.
- Ruling: 중계기 실행기는 exec 전에 `node --check`까지 보고 판단한다 (P3) — 실패한 exec는 셸을 끝내고, 망가진 사본은 exec 뒤에야 죽는다 — 런타임 시작마다 약 40 ms가 더 든다.
- Ruling: 시험은 버리는 HOME으로 돌고, 실제 지원·상태·호스트 폴더와 `com.chenjingdev.` 로그인 항목의 지문(경로, 종류, 크기, mtime, inode)을 앞뒤로 비교해 바뀌면 실패한다. 읽기만 한다 (P3 사고 뒤) — 시험이 실제 지원 폴더에 썼던 사고를 조용히 넘기지 않게 — 시험 중에 Codex를 정당하게 켜도 실패하므로 다시 돌려야 한다.
- Ruling: `relay.mjs`의 `CODEX_CUA_RELAY_TEST_FAIL`처럼 시험용 고리 둘을 제품 파일에 둔다 (P3) — spawn 전 실패를 시험할 다른 길이 없다 — 이 값을 정할 수 있는 쪽은 이미 실행기를 바꿀 수 있다.
- Ruling: 런타임이 답하지 않은 turn_ended도 턴 번호를 새로 만들고 옛 범위는 열어 둔다. 거절한 것은 그대로 둔다 (P2) — 끝난 짝으로 다시 부르면 멈추고(E1), 답 없는 요청도 처리됐을 수 있다 — 틀리면 시간 초과마다 열린 범위가 하나 남아 다음 놓아주기나 종료가 끝낸다.
- Ruling: 열린 범위가 없을 때 놓아주기는 아무것도 보내지 않고 `no_trusted_scope`로 답한다 (P2) — 계약의 "놓을 것 없음" — 틀리면 쉬는 연결에서 "놓을 것 없음"이 보인다.
- Ruling: 브리지 놓아주기의 `released`는 지금 호스트의 범위가 모두 확인됐을 때 참이다. 재연결 전 호스트의 범위는 놓지 못하고 기록에 `not_confirmed`로 남는다 (P2) — 브리지는 지금 스레드가 연 것만 끝낼 수 있다 — 그 범위는 엔진이 주인 없는 점유로 보고 콕 집어 푼다.
- Ruling: 놓아주기가 도는 동안 온 호출은 기다렸다가 새 턴으로 돈다. 종료가 시작된 뒤에만 거절한다 (P2) — P1에서는 놓아주기 뒤에 연결이 멈춘 채 남았다(놓아주기는 끄기가 아니다) — 틀리면 호출이 최대 2.5초와 놓아주기 시간만큼 늦는다.
- Ruling: 브리지 기록과 제어 소켓은 프로세스가 뜰 때 만든다 (P2) — 아직 연결 전인 브리지도 목록에 보이게 — 끝날 때 지운다.
- Ruling: 조작 기록과 마지막 호출 시각은 AI가 부른 호출만 남긴다. 앱이나 종료가 한 놓아주기는 남기지 않는다 (P2) — 앱이 놓아준다고 쉬는 연결이 일하는 것처럼 보이면 안 된다 — 중계기는 그 정리 호출도 기록하므로 두 기록이 그만큼 다르다.
- Ruling: 브리지 기록의 `host.relay`는 그 연결의 소켓과 같은 호스트 기록일 때만 읽고, 연결할 때마다 다시 읽는다 (P2) — 새 호스트의 값이 옛 연결에 붙지 않게 — 그 틈에는 중계기 없음으로 보고 브리지가 조작 기록을 쓴다.
- Ruling: `nohup`으로 SIGHUP을 무시한 채 뜬 브리지는 SIGHUP을 처리하지 않는다 (P2) — 터미널을 닫아도 계속되는 Claude의 브리지를 끄지 않게 — 그 브리지는 stdin 끝, SIGTERM, SIGINT에서만 놓는다.
- Ruling: 브리지 종료는 놓아주기 3초 안에, 남은 시간만 스레드 해제에 주고 웹소켓 닫기에 2초를 더 쓴다(최악 약 5초) (P2) — records.md는 놓아주기만 3초로 묶는다 — 그 사이 강제로 끝나도 기록은 이미 다시 쓰여 있다.
- Ruling: 호스트도 열린 범위도 없을 때 AI의 turn_ended는 오류가 아니라 "끝낼 것 없음"으로 답한다 (P2 검토 뒤 메인) — 호스트가 있을 때 빈 turn_ended는 성공하는데 둘이 어긋났다 — 없음.
- Ruling: osascript가 종료 요청에 오류로 답하면 3초 기다린 뒤 `quit_cancelled`로 본다 (P4 검토) — 앱이 답하기 전에 끝나도 osascript는 오류(-609)로 끝나서, 바로 판정하면 실제로 꺼진 Codex를 다시 켜지 않고 "안 꺼졌다"고 알린다 — 틀리면 진짜 취소(-128)도 3초 뒤에 알린다.
- Ruling: "Codex만"이 건너뛰는 "주인 모름"은 세션을 모르는 codex 연결이다. 열린 범위가 없는 중계기는 activity 기록에서 가장 최근에 섬긴 세션을 그 연결의 세션으로 본다 (P4 검토 뒤 메인) — 정상으로 끝난 Codex 턴은 범위를 닫지만 그 런타임은 여전히 그 대화를 섬긴다. 이것이 없으면 쉬는 Codex 런타임이 모두 "Codex만"에서 빠진다 — 틀리면 activity 기록(최근 200줄)에서 밀려난 오래 쉰 런타임은 하나씩 꺼야 한다.
- Ruling: `release --ended`는 옛 호스트 범위를 가진 살아 있는 브리지도 그 브리지의 연결 id로 결과에 넣는다 (P4 검토) — 그 범위는 주인 없는 점유로 풀린다 — 앱은 아직 `active`인 연결의 결과도 받는다.
- Ruling: 놓아주기 답 대기 `max(13, 3 + 5 × 열린 범위)`의 범위 수는 세션 id가 쓸 만한 항목만 센다 (P4 검토) — 쓰는 쪽이 놓아줄 범위만 센다 — 망가진 항목이 섞인 기록은 더 짧게 기다린다.
- Ruling: 확인된 쓰는 쪽이 "놓을 것 없음"으로 답하면 `ok: true`, 물어볼 곳이 없었으면 `ok: false`다. 이유는 둘 다 `no_trusted_scope` (P4) — 계약은 놓을 것 없음을 엔진 오류로 보지 않지만, 기록 없는 런타임은 점유를 가졌을 수 있다 — 틀리면 `ok`를 "놓았다"로 읽는 앱이 헷갈린다.
- Ruling: 종료 결과의 `released`는 글자 그대로 두고(놓을 것이 없었으면 false와 `no_trusted_scope`), `reason`은 종료 실패, 없으면 놓아주기 실패, 없으면 null이다 (P4) — 앱이 두 사실을 다 보인다 — 틀리면 "꺼짐, 놓을 것 없음"이 경고처럼 읽힌다.
- Ruling: Codex가 꺼져 있을 때 `restart-codex`는 `not_running`으로 답하고 아무것도 켜지 않는다 (P4) — 누른 것은 다시 켜기이고, 부르지 않았는데 Codex를 켜는 것은 R1의 반대다 — 틀리면 Codex가 혼자 꺼진 뒤의 "다시 켜기"는 켜지 않고 알림만 보인다.
- Ruling: 세션이 없는 중계기는 호스트 pid, 작업 폴더, 시작 시각(브리지 연결 시각의 -90초~+3초)이 모두 맞고 양쪽에서 하나뿐일 때만 그 브리지에 붙인다 (P4) — CUA를 아직 안 부른 Claude 대화의 런타임은 어디에도 세션이 없어 따로 `codex` 행으로 보이고 "Codex만"에 꺼질 뻔했다 — 틀리면 한 폴더에서 몇 초 사이에 연결한 두 Claude 대화의 런타임은 따로 보인다.
- Ruling: 주인 없는 점유의 `ended_at`은 기록의 `cleanup`이 `not_confirmed`일 때(쓰는 쪽이 끝나며 쓴 것)만 그 `updated_at`이고, 아니면 null이다 (P4) — 강제로 죽은 쪽은 죽은 시각이 없고, 마지막 활동 시각을 쓰면 알림이 바로 뜬다 — 틀리면 앱은 "처음 본 때"부터 센다.
- Ruling: 열린 세션이 모두 가장 이른 Chrome 주 프로세스 시작 전에 끝난 죽은 기록은 "열린 범위 없음" 기록과 함께 지운다. 60초가 안 된 기록은 지우지 않는다 (P4) — Chrome은 다시 켜질 때 점유를 모두 잊는다. 헤드리스와 따로 프로필 Chrome은 세지 않는다 — 틀리면 Chrome 시작을 잘못 본 만큼 기록이 지워진다.
- Ruling: 세션이 죽은 브리지의 것인 살아 있는 중계기는 `claude`/`ended`로 보고, 그 주인은 cua-repl의 지금 부모다 (P4) — 사라진 Claude 대화가 남긴 런타임은 "Codex만"으로 끄면 안 되고, 바로 "AI 대화가 사라졌는데 런타임이 남은 것"이다 — 중계기가 없으면 Claude 런타임을 Codex 것과 가를 수 없어 `codex`로 보인다.
- Ruling: `setup.relay`는 호스트가 ready이고 그 기록이 중계기를 켰다고 하며 `relay_launcher`가 고정 실행기와 같을 때만 `active`다. 고정 사본이 ready가 아니면 `unavailable`, 그 밖은 `inactive` (P4 검토) — 사본 확인은 P3의 `relay_status` 하나로 한다 — 틀리면 실행기를 적지 않는 래퍼가 쓴 기록은 `inactive`로 보인다.
- Ruling: 콕 집어 풀기의 브라우저 호출 코드는 `await (async () => { ... })();`로 감싼다 (P4) — E1에서 최상위 이름이 런타임에 남아 여러 호출 사이에 이어졌다 — 이 꼴로 한 번에 부르는 것은 아직 실기로 확인하지 않았다(E1b).
- Ruling: 콕 집어 풀기의 브라우저 호출은 45초, 준비 15초, 끝내기 10초를 준다. 시간이 다 된 호출도 turn_ended를 보내 보지만 결과는 `timeout`이고 기록은 남긴다 (P4) — E1에서 첫 호출은 브라우저 클라이언트를 불러오느라 오래 걸렸다 — 아주 느린 Chrome에서는 `timeout`으로 보인다.
- Ruling: 종료가 거절할 프로세스(엔진과 그 조상, 앱, app-server, AI 클라이언트, cmux-cua, Chrome)는 `can_stop: false`다 (P4) — 앱이 안 되는 버튼을 보이지 않게 — 없음.
- Ruling: `other_tools`에는 cmux-cua가 깔려 있기만 하면 `running: false`로 넣고, 없으면 뺀다 (P4) — 계약 예시대로 — cmux가 없는 맥에서는 그 항목이 없다.
- Ruling: 엔진 밖의 옛 명령은 새 인자를 받지 않는다(`doctor --force`는 그대로 거절) (P4) — 0.7.0 setup.py의 다른 동작을 바꾸지 않게 — 없음.
- Ruling: 엔진 시험은 가짜 프로세스 표와 임시 파일·소켓으로 세계를 만들고, `Path.home`, `os.kill`, `subprocess`를 부르면 실패하게 한다 (P4) — 실수로 이 맥을 건드리지 않게 — 실제 프로세스 목록을 읽는 시험 몇 개만 진짜 파이썬을 띄운다.
- Ruling: cmux-cua 연결(AI 대화가 띄운 `cmux-cua mcp` 프로세스)도 하나씩 끌 수 있게 계약과 엔진을 고친다. 데몬(`cmux-cua serve`)은 끄지 않고, 묶음 종료에는 넣지 않으며, 놓아줄 브라우저 점유가 없으니 놓아주기 없이 끈다 (P5 검토 중 메인) — R17과 Portwarden의 "cmux CUA connection" 끄기를 계약 v1이 빠뜨렸다 — 틀리면 클릭 한 번에 다른 AI 대화의 cmux-cua 도구가 다시 붙을 때까지 끊긴다.
- Ruling: cmux 연결의 `release`가 답하는 `unsupported`에도 `scope_count: 0`을 넣는다 (P6) — 계약의 `release --connection` 답은 네 키이고 다른 답도 모두 이 키를 가진다 — 틀리면 세 키로 통째 비교하는 쪽만 어긋난다.
- Ruling: AI 클라이언트가 사라진 `cmux-cua mcp`도 목록에 넣고 끌 수 있게 한다. 그 `pid`·`agent`·`cwd`는 null이고 목록 맨 뒤에 둔다 (P6 검토) — 새어 남은 mcp가 끄기가 가장 쓸모 있는 경우다. 1이나 이미 없는 번호를 주인으로 보이면 남의 프로세스와 묶인다 — 틀리면 주인 없는 행이 하나 더 보인다.
- Ruling: 다른 mcp를 띄운 mcp는 AI 클라이언트로 보고 끄지 않는다 (P6) — "AI 클라이언트는 끄지 않는다"를 글자대로 — 실제 cmux-cua는 이렇게 겹치지 않는다. 틀리면 그 부모만 못 끈다.
- Ruling: "아직 `cmux-cua mcp`인가"를 SIGTERM 직전뿐 아니라 SIGKILL 직전과 기다리는 동안에도 본다 (P6) — 같은 번호로 다른 프로그램이 뜨면 이미 끝난 것으로 보고 죽이지 않는다 — 틀리면 그 경우를 "꺼짐"으로 알린다.
- Ruling: R13을 바꿨다. 끝난 연결의 고치기는 먼저 놓아주기이고, 이번 실행에서 모든 끝난 연결의 놓아주기를 해 본 뒤에는 "끝난 연결 끄기 n"(한 번 묻는다)이다 (A2 검토 뒤 메인) — 엔진은 놓아준 뒤에도 런타임이 사는 동안 그 연결을 끝난 연결로 두어, 놓아주기만으로는 카드와 아이콘의 문제가 풀리지 않았다(F2의 고치는 버튼) — 틀리면 주인 없는 런타임을 끄기 전에 한 번 더 묻는다.
- Ruling: 엔진의 "놓을 것 없음"(`released: false` + `no_trusted_scope`)은 앱에서 성공으로 보인다. 물어볼 곳이 없었던 경우(`ok: false`)만 "놓아줄 길을 확인하지 못했어요"다 (A2 검토 뒤 메인) — 쉬는 연결은 대개 열린 범위가 없어, 흔한 끄기가 경고로 보였다 — 틀리면 기록 없는 런타임의 점유를 놓쳤는지 앱이 덜 알린다.
- Ruling: 앱의 엔진 시간 제한은 명령마다 따로 둔다. release 60초, stop 70초, release-session 100초, release --ended는 60초에 끝난 연결마다 20초, 풀 Claude 세션마다 90초를 더한다 (A2 검토 뒤 메인) — 30초 하나로는 엔진의 최악값(release-session 80초)보다 짧아, 성공할 놓아주기를 앱이 죽이고 확장 초기화 안내를 띄웠다 — 틀리면 정말 멈춘 엔진을 그만큼 늦게 포기한다.
- Ruling: cmux 줄의 강제 종료는 정상 종료가 시간 안에 안 끝났을 때만 보인다. 엔진의 `timeout`과 앱의 명령 시간 제한을 같이 세고, 그 줄에 "정상 종료가 시간 안에 안 끝남"을 남긴다. 표시는 꺼지거나 클라이언트가 사라지거나 상태를 못 읽으면 지운다 (A4) — 둘 다 "제때 안 꺼짐"이고, 배너는 곧 사라지므로 줄이 이유를 말한다 — 틀리면 엔진이 아직 일하는 중에 강제 종료가 조금 일찍 보인다(그래도 한 번 묻는다).
- Ruling: `can_stop`이 false이거나 `id`가 없는 cmux 줄에는 끄기 버튼을 아예 두지 않는다 (A4) — 지시 글자대로, 옛 엔진에는 버튼이 없다 — 틀리면 그 줄에 왜 끄기가 없는지 알 길이 없다.
- Ruling: cmux 끄기 도움말과 강제 종료 질문은 "그 대화의 cmux-cua 도구가 다시 붙을 때까지 끊겨요"를 알린다. 주인 없는 연결에는 이 경고가 없다 (A4) — 누르기 전에 결과를 알 수 있게 — 틀리면 말만 다르다.
- Ruling: 앱의 setup 시간 제한은 20분이다. 설치 흐름의 setup도 같다 (A3) — pip 중에 끊으면 환경이 깨진다 — 틀리면 멈춘 설치가 20분 동안 "설정하는 중"으로 보인다.
- Ruling: 설정이 실패한 뒤 카드는 "연결 설정에 실패했어요"와 다시 하기이고, 한 번도 안 해 본 설정은 고치기다 (A3) — 지시의 두 문장이 달랐다 — 틀리면 버튼 글자만 다르다.
- Ruling: 설치는 명령의 종료 코드만 믿지 않고 레지스트리에 플러그인과 `setup.sh`가 보여야 성공이다. 갱신 뒤 판이 그대로면 성공 줄 대신 경고를 내고 setup을 돌리지 않는다. `claude plugin …` 단계마다 300초를 준다 (A3) — 붙지 않았는데 "붙어요"라고 말하지 않게 — 틀리면 레지스트리 기록 방식이 바뀐 날 설치가 됐어도 실패 줄이 뜬다.
- Ruling: 제거가 호스트 때문에 거절됐는지는 실패 뒤 상태를 한 번 더 읽어 가른다. "설치된 것 없음"은 제거 명령 전에 `~/.local/share/codex-cua/source.json`이 없는 것으로 본다. 설정 중이면 제거를 거절하고, 성공하면 상태 읽기를 멈추고 로그인 항목 기억을 지운 뒤 결과를 6초 보이고 끝낸다 (A3) — 엔진 제거는 어떤 실패든 같은 종료 코드와 문장이다 — 틀리면 그 파일이 옮겨진 날 "되돌릴 것 없음"이 실패로 보인다(제거 자체는 된다).
- Ruling: 로그인 항목은 `/Applications`와 `~/Applications` 바로 아래에서 처음 켤 때만 등록하고, 이미 켜짐·승인 대기면 한 것으로 기억하며, 사용자가 끈 것은 다시 켜지 않는다 (A3) — 승인을 또 묻지 않고 일시적 오류에 영영 안 켜지지 않게 — 틀리면 영구 오류인 맥에서 실행마다 등록을 한 번 해 본다.
- Ruling: 단일 실행은 먼저 뜬 복사본이 있을 때만 나가고(같으면 낮은 pid가 남음), 번들 밖 실행은 검사하지 않는다 (A3) — 혼자 뜬 앱이 스스로를 남으로 보는 일을 막는다 — 없음.
- Ruling: 새 판 확인은 성공한 확인만 시각을 남겨 하루에 한 번이고, 실패하면 다음 실행에 다시 한다. 새 판은 창 아래 "새 버전 x.y.z" 버튼과 판마다 알림 한 번으로 알린다. 새 판을 모르면 맞는 판 받기는 릴리스 목록을 열고, github.com이 아닌 릴리스 주소는 태그로 만든 주소로 바꿔 연다 (A3·합칠 때 메인) — 하루 한 번 약속, 재시도 폭주 없음, 네트워크에서 온 주소를 그대로 열지 않음 — 틀리면 인터넷이 없던 날은 하루 늦게 알린다.
- Ruling: 포장은 `ditto --norsrc --noextattr`로 하고 출력하는 `gh release create`에 빌드한 커밋을 `--target`으로 준다. 앱 폴더나 plugin.json에 커밋 안 된 변경이 있으면 경고한다 (A3 검토 뒤) — 확장 속성이 zip의 `._*`가 되어 `unzip`으로 푼 앱의 서명이 깨졌고, 태그는 빌드한 커밋을 가리켜야 한다 — 없음.
- Ruling: 등록된 플러그인 판이 앱 판과 같은데 `status`가 실패하면 "연결 명령이 옛 판이거나 깨졌어요"와 고치기(등록된 플러그인의 `setup.sh setup`)를 보인다. 판을 비교할 때는 폴더가 남아 있는 기록만 본다. 앱을 켤 때 자동 설정은 명령이 없거나 남의 것일 때만 돈다 (A3 검토 뒤·합칠 때 메인) — 0.5.0 명령이 남은 채 플러그인만 갱신된 맥이 "상태를 못 읽음"에서 빠져나오지 못했다 — 틀리면 마켓플레이스가 저절로 갱신한 맥에서는 고치기를 한 번 눌러야 한다.
- Ruling: 진단 복사 끝에 앱 판과 로그인 항목 상태 두 줄을 덧붙이고, 기록 탭 아래에 로그인 항목 한 줄을 보인다 (A3) — 화면·요청·시크릿이 없다(R2) — 틀리면 줄 두 개를 지운다.
- Ruling: 명세 목록에 없는 문제 "CUA 상태를 읽지 못했어요"(다시 읽기)를 더했다. 좋은 답을 받은 적이 있으면 두 번 연속 실패해야 바뀐다. `schema_version`이 앱이 아는 것보다 크면 "판 다름"으로 보인다 (A1) — F1 "앱이나 플러그인이 깨짐 → 아이콘이 문제로"를 지키고, 느린 응답 한 번에 아이콘이 깜빡이지 않게 — 틀리면 실패 한 번은 4~5초 늦게 보인다.
- Ruling: 작업 중은 `screen.active_connection_id`가 있거나 도구 호출이 진행 중인 연결이 있을 때다 (A1) — 10초 넘는 호출에도 아이콘이 준비로 돌아가지 않게(R13) — 틀리면 짧은 틈에 "작업 중"이 뜬다.
- Ruling: `setup.command: missing`도 설정 문제로 센다. `login_environment: unknown`과 `relay: inactive`는 문제가 아니다. Codex가 켜져 있고 `host.state`가 `unknown`이면 "연결 없이 켜진 Codex"로 본다 (A1) — 고칠 것이 같은 setup이고, 모름만으로 경보를 올리지 않되 연결 없는 Codex는 놓치지 않으려고 — 틀리면 엔진이 상태를 못 알 때 불필요한 알림이 뜬다(누르기 전에는 아무것도 끄지 않음).
- Ruling: 브라우저 점유 탭은 점유 목록을 읽을 수 있어도 `maybe_left`를 같이 보인다. 결과 문구는 세션을 세고, 엔진이 돌려준 `tab_count`만 탭 수로 쓴다 (A1) — 카드가 띄운 문제의 근거가 탭에 있어야 하고, R14는 점유 개수 추측을 막는다 — 틀리면 같은 세션이 두 번 보일 수 있다.
- Ruling: 아이콘은 SF Symbols 템플릿 세 모양이고 문제일 때만 주황을 더한다. 앱 판은 번들의 판이고, 번들 밖 실행은 판을 비교하지 않는다. 명령 출력은 파이프 대신 0700 임시 폴더의 파일로 받는다 (A1) — 색만으로 구분하지 않고, 개발 중 "판 다름"을 막고, Codex를 남기는 `restart-codex`가 파이프를 쥐어 답을 막지 않게 — 없음.
- Ruling: 결과 배너는 상태 카드 바로 아래에 두고, 세션 풀기 결과는 그 줄에 붙인다. R15의 첫 거절은 질문이 곧 메시지이고, "다시 하기"는 다시 묻지 않는 따로 동작이다 (A2) — 두 번 말하거나 같은 질문을 두 번 하지 않게 — 틀리면 목록을 내린 사람이 배너를 못 볼 수 있다.
- Ruling: 알림의 "다시 켜기"는 알림을 만들 때의 Codex pid 묶음을 들고, 누를 때 같은 Codex가 아직 연결 없이 켜져 있을 때만 다시 켠다. 누르면 먼저 팝오버를 열어 결과를 보인다. 못 나간 알림은 1분 뒤에 다시 해 본다 (A2) — 오래된 알림이 멀쩡한 Codex를 끄지 않게(R1) — 틀리면 오래된 알림의 버튼은 배너만 띄운다.
- Ruling: Claude 대화의 놓을 수 있는 점유는 자동 정리가 먼저 해 보고, 실패한 뒤에야 "오래 남은 점유" 알림이 된다. 자동 정리는 `release --ended` 한 번으로 하고, 도는 동안 겹치는 버튼은 기다림으로 보이며 들어온 누름은 배너만 띄운다 (A2·A2 검토 뒤) — R16은 대신 놓아주기가 실패한 것만 알린다 — 틀리면 알림이 정리 한 번만큼 늦다.
- Ruling: 카드의 점유 놓아주기가 실패하면 점유 탭과 안내를 연다. Codex 대화의 점유만 남으면 카드 버튼은 "점유 보기"(탭만 고름)다 (A2) — Codex 대화는 줄에서 사용자가 눌러야 풀린다 — 틀리면 카드에서 누른 사람이 탭이 바뀌어 놀란다.
- Ruling: 물어야 하는 동작(다시 켜기, 묶음 끄기, 한 개 강제 종료, 끝난 연결 끄기, 일하는 연결 놓아주기)은 상태가 없거나 대상이 목록에서 사라지면 돌지 않고 이유를 한 줄 보인다. 기다리던 질문도 그때 거둔다. 대상 확인은 한 곳에서 하고 cmux 연결은 다른 도구 탭의 줄로 찾는다 (A2 검토 뒤·A4 합칠 때 메인) — 묻는 규칙이 실패하면 묻지 않고 도는 쪽으로 열리지 않게 — 틀리면 상태를 다시 읽은 뒤 한 번 더 눌러야 한다.
- Ruling: 진짜 알림은 앱 번들 안에서만 만들고, 밖에서는 아무것도 하지 않는다. 명령이 낸 글(stderr)은 값으로만 들고 어떤 문구에도 쓰지 않는다 (A2) — 번들 밖의 알림 센터는 예외를 던지고, 화면에 경로·비밀이 새지 않게 — 틀리면 번들 안에서도 알림이 안 나갈 수 있다(verify에서 확인).
- Ruling: `release --ended` 결과에서 "다시 연결되기 전 세션"은 살아 있는 연결의 항목이고 개수 없이 말한다. 실패 없이 `ok: false`이면 빈 항목은 "놓아줄 길을 확인하지 못했어요"로 말한다 (A2 검토 뒤 메인) — 엔진은 그 세션을 브리지 하나로 묶어 돌려주고, 항목만으로는 물어볼 곳이 없던 것을 가를 수 없다 — 틀리면 숫자 하나가 빠진다.
- Ruling: R11을 바꿨다. Claude 대화의 런타임은 래퍼의 `-c` 대신 대화 설정으로 중계기를 받는다. 래퍼가 host.json에 중계기 정의(`relay_config`)를 적고, 브리지가 대화를 열 때 그 정의를 `mcp_servers.cua_repl`로 보낸다 (build 2 메인) — 데스크톱 앱이 `config/batchWrite`로 `mcp_servers.cua_repl`을 지워 `-c`가 사라졌고, Claude 런타임이 중계기 없는 번들 정의를 받았다(S12·S23). 실제 Codex에서 대화 설정이 이기는 것을 확인했다 — 틀리면 Codex가 그 설정을 거부할 때 Claude 런타임이 다시 중계기 없이 돈다(로그 `owned_thread_config_refused`).
- Ruling: 브리지와 콕 집어 풀기가 여는 대화는 CUA 말고 사용자의 다른 플러그인과 MCP 서버를 대화 설정(`enabled=false`)으로 끈다 (build 2 메인) — 모델 차례를 돌리지 않는 대화인데 열 때마다 사용자의 MCP 서버 7개가 떠서 Codex가 꺼질 때까지 남았다 — 틀리면 Codex가 키 이름을 바꿨을 때 거절되어 예전처럼 모두 뜬다.
- Ruling: 브리지는 자기 이름(`bridge-<pid>-<시작>`)을 중계기에 넘기고 중계기는 기록의 `owner`에 적는다. 엔진은 이름으로 런타임을 Claude 연결에 붙이고, 이름 있는 런타임은 다른 브리지에 세션으로 붙이지 않는다. 이름의 브리지 프로세스가 사라졌으면 끝난 Claude 연결이고, 아직 돌면 기록이 없어도 끝난 것이 아니다 (build 2 메인) — 세션·시각 짐작은 CUA를 아직 안 부른 대화와 같은 폴더의 두 대화를 못 가렸다(S12) — 틀리면 이름 없는 옛 브리지는 예전 짐작을 쓴다.
- Ruling: 브리지는 나갈 때 자기 이름이 적힌 런타임의 cua-repl을 끈다. 엔진도 Claude 연결(끝난 것 포함)을 끈 뒤 그 이름의 cua-repl을 pid·시작 시각·명령을 다시 보고 끄고, 강제 종료면 3초 뒤 SIGKILL한다. 세션으로만 붙은 런타임과 Codex 런타임은 끄지 않는다 (build 2 메인) — Codex는 일회용 대화를 내리지 않아 런타임이 Codex가 꺼질 때까지 남았다(검수 끝 Codex 27개, 하나에 약 700 MB) — 틀리면 이름 없는 옛 런타임은 그대로 남는다.
- Ruling: 콕 집어 풀기의 대화는 새 0700 임시 폴더에서 열고, 끝나면 앱 서버 바로 밑에서 그 뒤에 뜬, 그 폴더에서 도는 cua-repl만 끄고 폴더를 지운다 (build 2 메인) — 엔진이 "/"에서 연 대화의 런타임이 쌓였다(검수 때 8개) — 틀리면 폴더를 못 만들 때는 예전처럼 남는다.
- Ruling: 중계기는 그 런타임에서 연 호출이 없는 짝의 turn_ended(Codex 앱이 차례마다 보낸다)를 활동 기록과 마지막 호출 시각에 넣지 않는다. 브리지가 활동을 직접 적을지는 host.json이 아니라 그 대화에 중계기가 실제로 붙었는지로 정한다 (build 2 메인) — 기록 탭이 Codex 차례 끝으로 덮였고, 중계기 없는 Claude 호출은 아무도 적지 않았다(S23) — 틀리면 붙었는지 확인이 어긋날 때 같은 호출이 두 번 적힐 수 있다.
- Ruling: 중계기 실행기는 `node --check` 전에 relay.mjs의 마지막 줄이 끝 표시인지 본다 (build 2 메인) — 머리 주석이 길어지자 잘린 사본도 빈 모듈로 `--check`를 통과했다 — 없음.
- Ruling: Codex를 뒤에서 켤 때 앞에 있던 앱은 lsappinfo가 내는 여러 줄에서 `bundleID="…"`(macOS 27)나 `"CFBundleIdentifier"="…"`(그 전) 어느 쪽으로든 읽는다 (build 2 메인) — macOS 27에서 형식이 바뀌어 앞 앱을 못 읽었고, Claude가 켠 Codex 창이 앞으로 나왔다(S4) — 틀리면 형식이 또 바뀔 때 Codex가 앞으로 나온다.
- Ruling: 명령이 실패하거나 못 읽을 글을 내고 Claude Code에 cua 플러그인 기록이 없으면 "Claude 플러그인이 없어요"(설치), 기록은 있는데 그 폴더가 없으면 "Claude 플러그인 폴더가 없어요"(다시 설치)로 본다. 다시 설치는 데이터를 남기고(`--keep-data`) 기록을 지운 뒤 설치한다 (build 2 메인) — 이미 있는 기록에 설치를 부르면 아무것도 바꾸지 않아 다시 읽기만 남았다(S5) — 틀리면 기록을 지우는 데 실패할 때 설치도 하지 않고 그렇다고 말한다.
- Ruling: 문제 아이콘은 주황을 그림 자체에 칠한다(템플릿이 아님). 준비됨·작업 중은 템플릿 그대로다 (build 2 메인) — macOS 27 메뉴 막대는 버튼의 색 지정을 무시해 문제도 흑백으로 보였다(S6) — 없음.
- Ruling: Codex가 켜진 지 30초 안이고 호스트가 아직 없으면 호스트를 `starting`으로 보고 "연결 없이 켜진 Codex"로 알리지 않는다 (build 2 메인) — 막 켠 Codex가 호스트를 띄우는 몇 초 사이에 아이콘과 알림이 문제를 말했다(S9) — 틀리면 정말 연결 없이 켜진 Codex를 30초 늦게 알린다.
- Ruling: 다시 켜기에서 Codex가 종료를 받았지만 30초 안에 끝나지 않으면 엔진은 `quit_cancelled`가 아니라 `quit_pending`으로 답하고 아무것도 켜거나 죽이지 않는다. 앱은 "아직 꺼지는 중"을 보이고, 그 Codex가 사라진 지 3초가 넘고 호스트가 준비되지 않았으면 Codex를 뒤에서 연다. 다른 Codex가 켜졌거나 10분이 지나면 그만둔다 (build 2 메인) — 느린 종료를 취소로 말했고 다시 켜지도 않았다(S10). 사람이 누른 다시 켜기의 끝이라 R1과 맞다 — 틀리면 10분 넘게 걸린 종료 뒤에는 직접 켜야 한다.
- Ruling: 기록 탭의 도구 이름은 쉬운 말로 보인다(js → 화면 조작, turn_ended → 차례 끝 · 점유 놓기, js_reset → 런타임 초기화). 모르는 이름은 그대로다 (build 2 메인) — 기록 줄이 내부 이름으로 가득했다(S23) — 없음.
- Ruling: 줄 버튼은 그 연결을 건드리는 일만 기다린다. 끝난 연결 놓아주기·끄기는 끝난 줄만, 묶음 끄기는 그 묶음 줄만, 다시 켜기·전체 끄기·설정은 모든 줄이 기다린다. 자동 정리 중에는 그 정리가 놓는 연결의 줄도 기다리고 이유를 말한다. 버튼 글자는 한 줄로만 쓴다 (build 2 메인) — 끝난 연결 끄기가 사용자의 살아 있는 연결에도 빙글이를 돌렸고, 자동 정리 대상 줄은 기다리지 않았고, "강제 종료"가 두 줄로 꺾였다(S18) — 틀리면 상태에 없는 줄은 예전처럼 넓은 일을 다 기다린다.
- Ruling: R21을 넓혔다. 앱은 켤 때와 팝오버를 열 때 알림 설정을 읽고, 꺼져 있거나 아직 허용하지 않았으면 창 아래에 "알림 켜기"(시스템 설정의 이 앱 알림을 연다)를 보인다. 진단 복사에도 알림 줄을 넣는다 (build 2 메인) — macOS는 한 번만 묻는다. 첫 실행의 질문에 아무도 답하지 않은 채 앱이 바뀌자 그 뒤 요청은 창 없이 바로 실패했다(S2·S30, usernoted 기록) — 틀리면 사람이 버튼을 누르기 전까지 알림이 오지 않는다(아이콘과 카드는 그대로 알린다).
- Ruling: 앱 아이콘은 빌드할 때 코드(scripts/make-icon.swift)로 그려 넣는다. 로그인 환경 항목은 `/bin/sh -c` 대신 자기 스크립트 `codex-cua-login-env`를 실행한다 (build 2 메인) — 알림 질문에 빈 아이콘이 보였고, 로그인 항목이 `sh`로 보여 무엇인지 몰랐다(S11) — 틀리면 그 이름으로도 무엇인지 모를 수 있다.
- Ruling: 이번 설정보다 먼저 켜진 Codex는 `host.started_before_setup`으로 알린다. host.json에 `relay_config` 칸이 없으면(이번 래퍼는 늘 적는다) 그렇게 본다. 앱은 문제로 올리지 않고 카드에 "Codex를 다시 켜면 새 설정이 적용돼요"와 이유를 보인다 (build 2 메인) — 갱신 전부터 켜진 Codex의 연결이 모두 "알 수 없음"이고 놓아주기가 꺼졌는데 아무 안내가 없었다(S8) — 틀리면 다음에 래퍼가 또 바뀔 때는 새 표시가 필요하다.
- Ruling: CUA 런타임은 node가 프로그램이고 그 첫 인자가 cua-repl.mjs인 프로세스만이다. host.json이 적은 래퍼·앱 서버·프록시 pid는 보호 목록에 넣는다 (build 2 메인, 재검수 준비 중 발견) — 호스트 프록시가 `--relay-node`·`--relay-script` 값 때문에 런타임으로 잡혀 Codex 연결로 보였고, 끄기·Codex만·전체 끄기가 그 프록시를 끌 수 있었다(1회차의 "/" 런타임 11395) — 틀리면 옵션을 앞에 붙여 띄운 런타임은 연결로 안 보인다.
- Ruling: "알림 켜기"는 아직 아무도 답하지 않았으면 macOS의 알림 질문을 다시 띄우고, 꺼 두었거나 질문이 여전히 뜨지 않으면 시스템 설정의 알림을 연다 (build 2 메인, 재검수 준비 중 발견) — 화면이 잠긴 동안 켜진 앱은 질문이 창 없이 바로 실패했고(두 번 모두 잠금 중), 답이 없는 앱은 시스템 설정 목록에 없어 "알림 켜기"가 막다른 길이었다. 위 R21 Ruling이 짚은 원인(첫 질문에 답하지 않음)은 잠금이었을 수 있다 — 틀리면 잠금 말고 다른 까닭으로 질문이 뜨지 않을 때는 여전히 설정만 열린다.
- Ruling: Codex가 호스트를 닫은 지 30초 안이고 그 전부터 켜져 있던 Codex면 호스트를 `stopping`으로 보고 "연결 없이 켜진 Codex"로 알리지 않는다. 켜질 때의 `starting`과 짝이다 (build 3 메인) — 연결된 Codex를 정상 종료할 때마다 래퍼가 먼저 닫힘을 적고 Codex 앱이 몇 초 더 남아, 그 사이 문제 아이콘과 "Codex가 연결 없이 켜져 있어요" 알림이 떴다(2회차 S2, S9의 종료 때도) — 틀리면 호스트만 죽고 Codex가 남은 경우를 30초 늦게 알린다.
- Ruling: 다시 켜기가 Codex의 종료를 기다리는 동안(`quit_pending` 뒤 10분) 카드의 다음 할 일은 "Codex가 꺼지기를 기다려요 — 종료를 물으면 '종료'를 눌러 주세요. 꺼지면 다시 켤게요"이고, 카드의 다시 켜기는 기다린다. 같은 Codex가 10분을 넘기면 다시 켜기를 그만뒀다고 한 줄 말한다 (build 3 메인) — 이 맥의 Codex는 예약 작업이 있으면 종료마다 한 번 더 묻는데, "아직 꺼지는 중" 배너는 6초 만에 사라지고 카드는 아무 일 없던 듯 다시 켜기만 보였다(2회차 S10) — 틀리면 기다리는 10분 동안 카드의 다시 켜기를 다시 누를 수 없다(알림의 다시 켜기는 된다).
- Ruling: 갱신 전에 켜진 Codex의 안내(다음 할 일과 경고)는 작업 중 카드에도 보인다 (build 3 메인) — AI가 화면을 쓸 때마다 카드가 그 안내와 "없음"을 오갔다(2회차 S8) — 없음.
- Ruling: "알림 켜기" Ruling(build 2 메인)의 원인 설명을 고쳐 적는다. 2회차에 macOS는 이 앱의 알림을 "거절됨"으로 기억하고 있었고(사용자가 거절한 기록은 없다), 알림 켜기는 시스템 설정의 CUA Bar 알림 화면을 바로 열어 켤 수 있었다. 추측: 처음 질문에 답하지 않은 채 앱을 끄고 다시 깔면서 질문이 치워진 것이 원인이고, 화면 잠금만의 일은 아니다. 다시 묻는 길은 그대로 둔다 (build 3 메인) — 2회차 1부 기록과 usernoted 기록 — 틀리면 답하지 않은 앱에 질문을 다시 띄우는 길은 단위 시험으로만 확인된 채로 남는다.
- Ruling: (사용자 결정, 2026-10-19) 버튼은 줄 상태마다 하나다. 살아 있는 AI의 연결은 탭 풀기, 끝난 연결과 주인 없는 cmux-cua 연결은 정리, 주인이 사라진 점유는 탭 풀기다. 끄기·강제 종료·묶음 끄기(전체·Claude만·Codex만)·끝난 연결 놓아주기·끝난 연결 끄기 버튼과 카드의 놓아주기·점유 보기·안내 보기는 없앤다. 엔진 명령은 그대로 둔다 (build 4 메인) — 사용자: "놓아주기는 뭐고 끄기는 뭐고 삭제는 뭐야? 컨셉만 비슷하고 너무 이상한데" — 틀리면 살아 있는 AI의 연결은 앱에서 끊을 수 없고 그 AI 쪽에서 꺼야 한다.
- Ruling: (사용자 결정, 2026-10-19) 한 가지 일은 한 곳에서만 누른다. 카드는 앱 전체 문제에만 버튼을 두고, 연결 하나의 문제는 목록 맨 위에서 정리하라고 말만 한다. 탭은 연결·기록 둘이고 손볼 줄이 맨 위에 온다. 알림 켜기·진단 복사·앱 지우기는 기록 탭 맨 아래로 옮기고, 제거는 앱 지우기로 이름을 바꾼다 (build 4 메인) — 사용자: "위아래로 클릭을 왔다갔다 시키는게 ux적으로 맞는지 잘 모르겠네" — 틀리면 기록 탭을 열어야 알림 켜기가 보인다.
- Ruling: 맨 아래 줄에는 끝내기와 함께 상태를 읽은 시각, 새 판이 있을 때만 새 버전 버튼을 남긴다 (build 4 메인) — 새 판은 드물고, 기록 탭 맨 아래에 묻히면 못 본다 — 틀리면 맨 아래 줄이 끝내기 하나보다 조금 길다.
- Ruling: Claude 대화가 Codex를 뒤에서 켜면 연결이 준비된 뒤 30초 동안 앞 앱을 뒤에서 지켜본다. 그동안 Codex가 앞으로 오면 그때마다 직전의 앞 앱을 다시 앞으로 보내고, 사람이 1초 안에 마우스를 눌렀으면(직접 고른 것) 그대로 둔다. 대화의 첫 호출은 이 지켜보기를 기다리지 않는다 (build 4 메인) — 2회차에 Codex가 연결 준비 8초 뒤 대화의 첫 화면 호출 때 스스로 다시 앞으로 와 36초 남았고(S4 두 번째 실패), 숨긴 채 켜기는 이미 쓰고 있었다 — 틀리면 30초 뒤에 스스로 앞으로 오는 Codex는 남고, 마침 1초 안에 다른 곳을 누른 때 온 Codex도 남는다.
- Ruling: 뒤에서 켠 Codex는 두 번 지켜본다. 연결이 준비된 뒤 30초(기한은 준비된 순간에 정한다)와, 그 Codex에 대화가 처음 화면 호출을 할 때 15초다. 첫 호출 때의 앞 앱은 호출을 보내기 전에 읽고, 그 앱이 Codex면 지켜보지 않는다. 첫 호출은 켠 Codex마다 한 번이고, 그 전에 연결이 끊겼다가 이미 준비된 호스트에 다시 붙어도 남는다. 지켜보기는 한 번에 하나만 돌고, 뒤의 요청은 기한만 늘린다 (build 4 메인) — MCP는 대화가 열릴 때 Codex를 켜므로 첫 호출이 30초보다 한참 늦을 수 있고, 2회차의 두 번째 앞으로 오기는 첫 호출 0.9초 뒤였다. 호출 뒤에 앞 앱을 읽으면 바로 앞으로 온 Codex를 원래 앞에 있던 것으로 본다 — 틀리면 다른 대화의 첫 호출이나 15초 뒤에 스스로 앞으로 오는 Codex는 남는다.
- Ruling: 사람이 Codex를 고른 것은 마우스 누름으로만 본다. Codex가 앞으로 오기 1초 안에 눌렀거나, 준비를 기다리는 동안 앞에 있는 Codex를 눌렀으면 그대로 두고 지켜보기를 끝낸다. 키보드(Cmd-Tab, 수정 키)는 보지 않고, 누름을 못 읽으면 고르지 않은 것으로 본다 (build 4 메인) — 수정 키를 보면 Codex가 앞에 오는 순간 Shift로 글을 치던 사람에게 Codex가 남는다(검토 지적) — 틀리면 Cmd-Tab으로 고른 Codex가 지켜보는 동안 최대 3번 되돌려진다.
- Ruling: 켠 한 번에 되돌리기는 모든 지켜보기를 합쳐 최대 3번이고, 3번째 뒤에는 지켜보지 않는다. Codex가 앞으로 올 때 한 번으로 세고, 되돌린 뒤 1초 넘게 Codex가 앞에 있으면 다시 온 것으로 센다. 되돌리기가 실패해도 한 번으로 센다 (build 4 작업자·메인) — 되돌림과 사람의 선택을 다 가를 수 없으니 끝없이 다투지 않게 한다 — 틀리면 네 번째로 스스로 오는 Codex는 남는다.
- Ruling: 되돌릴 앱이 이미 꺼졌으면 되돌리지 않고, 다음에 앞으로 오는 앱이 그 자리를 잇는다. 꺼졌는지 못 읽으면 켜져 있다고 본다. 준비를 기다리는 동안에도 앞 앱을 따라가, 그사이 사람이 옮겨 간 앱을 되돌린다 (build 4 작업자) — 방금 Cmd-Q로 끈 터미널을 다시 켜지 않게 — 틀리면 읽기 실패 때는 방금 끈 앱이 다시 켜질 수 있다.
- Ruling: 되돌리기는 앞 판처럼 `open -b`로 한다. 창을 모두 닫은 앱에는 새 창이 열릴 수 있고, Cmd-H로 숨긴 앱은 다시 보인다. 받아들인다 (build 4 메인) — 앞 판부터 쓰던 길이고, 30초와 3번 안에서만 쓴다 — 틀리면 드물게 창이 하나 더 열리거나 숨긴 앱이 보인다.
- Ruling: 첫 호출 기회는 호출이 Codex에 닿지 못했을 때(보내지 못했거나 연결이 끊김)만 다음 호출로 넘긴다. Codex가 오류로 답한 호출은 닿은 것이라 기회를 쓴 것으로 본다 (build 4 메인) — 닿은 호출은 Codex를 앞으로 부를 수 있고, 그 15초는 이미 지켜봤다 — 틀리면 오류로 끝난 첫 호출이 Codex를 부르지 않았을 때, 그 뒤 처음 성공한 호출이 부르는 앞으로 오기는 지켜보지 않는다.
- Ruling: 지켜보기는 곁가지라 연결과 호출을 막지 않는다. 지켜보기를 시작하지 못하면 연결은 그대로 하고 `open_watch_unavailable`을, 첫 호출 쪽이 실패하면 호출은 그대로 보내고 `first_call_watch_unavailable`을 기록에 남긴다. 그 밖의 오류는 숨기지 않는다 (build 4 작업자·메인) — 지켜보기의 잘못으로 AI가 화면을 못 쓰면 안 된다 — 틀리면 지켜보기가 안 돈 것은 기록에서만 알 수 있다.
- Ruling: 시험에 이 맥의 진짜 CoreGraphics에서 마우스 누름 시각을 읽는 시험 하나를 둔다(macOS에서만, 읽기만) (build 4 작업자) — 가짜 라이브러리로는 ctypes 선언이 맞는지 알 수 없다 — 틀리면 창 서버가 없는 곳에서 그 시험이 실패한다.
- Ruling: 팝오버는 열 때마다 연결 탭으로 연다 (build 4 작업자) — 카드의 "목록 맨 위의 정리를 눌러 주세요"가 열 때마다 참이어야 한다 — 틀리면 기록 탭을 보다 닫았다 열어도 연결 탭에서 시작한다.
- Ruling: 탭 풀기에 딸린 글은 "놓다" 대신 "풀다"로 맞춘다("탭을 풀었어요", "작업이 끝나지 않아 못 풀었어요" 등). 갱신 전 Codex의 "놓아줄 수 없을 수 있어요" 경고는 다른 기능이라 그대로 둔다. 앱 지우기의 실패 글도 "앱을 지우지 못했어요"로 바꾼다 (build 4 작업자) — 사용자가 놓아주기와 끄기를 헷갈렸고 버튼 이름이 탭 풀기·앱 지우기가 됐다 — 틀리면 말만 옛 글과 다르다.
- Ruling: 끝난 연결은 에이전트 이름과 상관없이 손볼 것과 모두 정리에 넣는다 (build 4 작업자) — 끝남은 상태이고, 줄에는 정리가 있는데 모두 정리에서만 빼면 개수가 어긋난다 — 틀리면 모르는 이름의 끝난 연결도 모두 정리가 건드린다.
- Ruling: 앱이 끌 수 없는 끝난 연결(신원을 확인하지 못한 프로세스)은 정리가 탭만 풀고 "탭만 풀었어요 — 이 연결은 앱이 끌 수 없어요"라고 하며, 모두 정리에서는 정리한 것으로 센다. 탭도 풀 길이 없으면 버튼을 끄고 까닭을 줄에 보인다. 탭을 풀었다는 말은 엔진이 확인해 준 때만 하고, 앱을 다시 켜면 잊는다 (build 4 작업자) — 앱이 할 수 있는 만큼 하고 모르는 것은 말하지 않는다 — 틀리면 그 연결은 목록에 남고, 다시 켠 앱에서는 정리를 한 번 더 눌러야 한다.
- Ruling: 정리의 도움말은 셋이다: 꺼서 정리할 때, 탭만 풀 때, 둘 다 못 할 때(버튼 꺼짐). cmux-cua 줄은 탭이 없어 "남은 연결을 꺼요"라고 한다 (build 4 작업자) — 하나로 두면 탭만 풀 때와 cmux-cua에는 거짓이 된다 — 틀리면 말만 다르다.
- Ruling: 정리로 꺼졌지만 탭을 풀었는지 확인되지 않으면 "정리했어요 — 탭을 풀었는지는 확인되지 않았어요. 남았으면 목록에 점유로 보여요"라고 경고로 말하고, 강제로 껐으면 그것도 덧붙인다 (build 4 작업자) — R15: 확인되지 않은 점유는 주인 없는 점유로 보인다 — 틀리면 경고 줄이 길다.
- Ruling: 모두 정리의 결과는 "n개 정리했어요", "n개 정리, m개는 못 했어요 — 까닭", "정리하지 못했어요 — 까닭", "정리할 것이 없어요" 넷이다. 강제로 껐거나 탭만 푼 설명은 한 줄 정리에만 있다 (build 4 작업자) — 짧은 꼴을 지키려고 — 틀리면 모두 정리의 결과로는 강제로 껐는지 모른다.
- Ruling: 엔진이 읽은 점유 목록에서 살아 있는 연결의 세션, 끝난 연결의 세션, 같은 세션의 남은 점유는 빼고 남은 것만 "점유 중" 줄로 둔다 (build 4 작업자) — 손볼 것의 개수가 한 세션을 두 번 세지 않게 — 틀리면 그 목록에만 있는 같은 세션의 줄이 안 보인다(지금 엔진은 그 목록을 못 읽는다).
- Ruling: 누른 일이 닿는 줄과 그 버튼만 기다린다. 한 줄의 정리·탭 풀기는 그 줄만, 모두 정리는 대상 줄과 모두 정리 버튼만 기다리고, 모두 정리는 이미 정리·탭 풀기 중인 줄을 건너뛴다 (build 4 작업자) — 상관없는 줄이 막히지 않고 같은 줄을 겹쳐 누르지 않게 — 틀리면 건너뛴 줄은 그 줄의 일이 끝나야 정리된다.
- Ruling: "연결 없음"은 손볼 줄, 살아 있는 줄, 살아 있는 cmux-cua 줄이 모두 없을 때만 보인다. 도구 머리 줄("cmux-cua · 꺼져 있음")은 연결로 세지 않고, 꺼진 도구는 한 줄만 보인다. 주인 없는 cmux-cua 연결은 본체가 꺼져 있어도 손볼 것에 보인다 (build 4 작업자) — 연결이 없을 때만 없다고 말한다 — 틀리면 꺼진 본체 옆에 남은 살아 있는 연결이 안 보인다.
- Ruling: 접힌 안내 "브라우저 탭이 계속 막히면"은 목록이 비었을 때도 맨 아래에 있다 (build 4 작업자) — 늘 같은 자리에서 찾게 — 틀리면 빈 목록 밑에 접힌 줄 하나가 더 보인다.
- Ruling: 묻는 것은 누른 곳에서 묻는다. 줄의 질문은 그 줄 바로 아래에 붙고, 목록이 질문이 보이게 가장 적게 스크롤하며, 탭을 바꾸면 거둔다. 카드 아래에서 묻는 것은 다시 켜기뿐이다 (build 4 메인·작업자) — 사용자: "위아래로 클릭을 왔다갔다 시키는게 ux적으로 맞는지 잘 모르겠네" — 틀리면 다른 탭을 보고 돌아오면 다시 눌러야 한다.
- Ruling: 답도 누른 곳에 붙는다. 줄 일의 답은 그 줄에, 모두 정리의 답은 손볼 것 머리 밑에, 진단 복사의 답은 그 버튼 줄 위에 붙고, 자리가 사라진 답만 맨 위 배너로 간다. 이 답들은 배너처럼 6초 뒤 지운다. 점유 줄의 실패, 확인되지 않은 탭 표시, 정리할 수 없는 까닭은 줄이 가진 상태라 남는다 (build 4 메인·작업자) — 위와 같은 사용자 말, 그리고 줄에 늘 남는 답은 낡은 말이 된다 — 틀리면 연결 줄의 정리 실패 까닭이 6초 뒤 사라진다.
- Ruling: 살아 있는 줄의 꺼진 탭 풀기는 까닭을 줄에 적지 않고 마우스를 올린 도움말에만 둔다 (build 4 작업자) — 중계기가 없는 Codex 줄마다 한 줄이 붙으면 시끄럽다 — 틀리면 그 까닭은 마우스를 올려야 보인다.
- Ruling: 답은 그 자리의 탭이 보일 때만 그 자리에 둔다(줄·손볼 것·모두 정리는 연결 탭, 진단 복사는 기록 탭). 답이 올 때 다른 탭이 보이거나, 답이 보이는 동안 다른 탭으로 옮기면 맨 위 배너가 말한다. 카드가 "탭은 풀었어요"라고 하는 것은 끝난 연결 모두의 탭을 푼 때뿐이고, 섞이면 줄마다의 까닭을 가리킨다. 끝난 연결의 다시 묻기는 거둔다 (build 4 메인, 2차 검토 뒤) — 진단 복사는 30초까지 걸려 그사이 탭을 옮길 수 있고, 보이지 않는 탭의 실패는 끝내 못 본다 — 틀리면 탭을 오가면 줄에 있던 답이 배너로 옮겨 가 한 번 더 보인다.
- Ruling: 카드는 그 줄의 버튼 이름을 말한다. 끝난 연결이면 "목록 맨 위의 정리를 눌러 주세요", 남은 점유면 "목록 맨 위의 탭 풀기를 눌러 주세요"다. 모두 정리는 앱이 할 줄이 둘 이상일 때만 보이고, 남은 점유 줄에는 세션 번호를 보이지 않는다(탭 풀기 도움말에만 있다) (build 5 메인, 3회차 S32) — 처음 보는 눈으로 보니 카드는 "정리"인데 줄 버튼은 "탭 풀기"였고, 손볼 줄이 하나일 때 모두 정리와 줄 버튼이 같은 일을 했고, "세션 01a15449"가 코드처럼 보였다. 사용자 결정 "누를 곳은 한 군데"를 따른다 — 틀리면 같은 폴더에서 같은 때 끝난 점유 둘은 도움말을 봐야 가린다.
- Ruling: 앱에 검수용 창을 둔다. SIGUSR1을 받으면 팝오버와 같은 화면을 같은 모델로 화면 밖의 패널에 띄우고(앱을 활성화하지 않고 키 창도 되지 않는다) 다시 받으면 거둔다. SIGUSR2를 받으면 그 창의 사진을 `~/Library/Caches/CUABar/verify-panel.png`에 쓴다. 다른 길로는 열리지 않는다 (build 5 메인) — 사용자: "앱을 따로 띄워서 검수하는 방법 없어? 상단 상태바에서 누르니까 뺏김". 팝오버는 열리면 키 창이 되어 사용자의 입력을 가져가므로, 사용자가 일하는 동안의 화면 검수는 이 창과 접근성 누르기로만 한다 — 틀리면 진짜 팝오버의 여닫이(아이콘 클릭, 바깥 클릭에 닫힘)와 알림 클릭은 이 창으로 볼 수 없어 사용자가 자리를 비울 때 따로 본다.
- Ruling: Codex가 되살린 빈 런타임(죽은 다리의 이름을 달았고, 한 번도 불리지 않았고, 다리보다 2분 넘게 늦게 켜졌고, 다리 기록이 없는 것)은 연결 목록·묶음 개수·끝난 연결·자동 정리·알림·확장 초기화 안내의 목록에서 빼고, 진단에만 개수와 메모리를 적는다. 한 번이라도 불리거나 점유를 가지면 지금처럼 끝난 연결이다 (build 6 메인, 3회차 S17 — 작업자 조사: Codex 앱 서버는 외부 클라이언트가 연 일회용 대화를 30분쯤 들고 있으면서 물결마다 그 대화의 cua_repl을 다시 켠다. 우리 명령이 켠 것이 아니다) — 어느 대화의 연결도 아니고 점유도 없어 막는 것이 없으며, Codex가 곧 스스로 내린다. Codex 줄로 보이면 사용자가 Codex를 쓰지 않은 폴더에 쓸모없는 탭 풀기 줄이 생기고, 앱이 끄면 다음 물결에 다시 켜진다 — 틀리면 그 메모리(하나 약 100 MB)가 목록에서는 보이지 않는다.
- Ruling: 연결의 놓아주기가 확인되면 그 연결이 맡던 세션을 죽은 기록에서만 지우고, 살아 있는 기록에는 `remember_released`도 하지 않는다(build 6 작업자, 3회차 S16·S21) — 살아 있는 다리와 중계기는 놓아주기가 지나가며 자기 범위를 스스로 닫고, 엔진이 중계기 같은 살아 있는 쪽에 "놓음"을 적어 두면 그 중계기가 같은 세션에 다시 연 범위를 나중에 죽을 때 가릴 수 있다(`_leases`가 `(writer, session)` 짝이 적혀 있으면 건너뜀) — 틀리면 죽은 기록이 아닌 살아 있는 기록(예: 살아 있는 다리의 옛 호스트 범위)이 이 길로는 안 지워지고 `release-session`이 맡는다.
- Ruling: 연결의 놓아주기 장부 정리가 푸는 세션은 연결 기록이 맡던 세션(`live_sessions()`: 중계기는 열린 범위의 세션 전부, 다리는 지금 세션)이다(build 6 작업자, 3회차 S16·S21) — 다리의 놓아주기는 지금 호스트의 범위만 끝내서(`host_mcp.py` `release_scopes`) 옛 호스트 범위를 푼 것으로 적으면 안 된다 — 틀리면 다리 쪽 옛 호스트 범위는 계속 `release-session`으로만 풀린다.
- Ruling: 같은 세션을 끝난 연결이 잡고 있어 점유가 풀 길이 없는 줄(`releasable: false`)은 따로 보이지 않고 숨긴다. 단 그 연결의 정리가 꺼져 있으면(앱이 끌 수도 풀 수도 없으면) 숨기지 않는다. 그 줄의 정리를 가리키는 문구로 바꾸는 안은 택하지 않았다(build 6 작업자, 3회차 S16·S21) — 지시가 둘 다 허락했고, 손볼 것 개수·모두 정리·확장 초기화 안내가 한 세션을 두 번 세지 않게 하는 쪽이 사용자 결정("누를 곳은 한 군데")과 build 4의 "한 세션을 두 번 세지 않게"에 맞고, 정리가 꺼진 연결 뒤에서는 확장 초기화가 남은 길이라 줄과 안내가 있어야 한다 — 틀리면 연결이 끝난 줄이 숨겨진 점유의 "탭이 풀렸는지 확인 안 됨"을 말해 주지 않는다(알림이 1분 뒤 알려 준다).
- Ruling: 숨긴 점유의 알림은 그 끝난 연결의 자동 정리가 시도되고 끝난 뒤에만 보낸다(build 6 작업자, 3회차 S16·S21) — 정리가 아직 도는 동안 막 풀릴 점유에 알림이 먼저 가지 않게 한다. 이 기다림이 S21을 막는다고 한 처음 근거는 틀렸다: S21의 알림은 정리가 끝나고 약 50초 뒤에 갔으니 이 기다림으로는 안 막힌다. S21을 막는 것은 아래 다시 묻기(확인되면 장부가 정리되어 점유 줄도 알림도 없다) — 틀리면 정리가 오래 걸리는 연결(멈춘 다리)의 점유 알림이 그만큼 늦다.
- Ruling: build 2 Ruling 두 곳(다른 MCP 서버 끄기, 다리가 나갈 때 자기 런타임 끄기)의 근거 "Codex가 꺼질 때까지 남았다"를 바로잡는다. Codex 앱 서버는 외부 클라이언트가 연 일회용 대화를 클라이언트가 떠난 뒤 약 30~37분 들고 있다가 내리고, 그사이 물결마다 그 대화의 cua_repl을 다시 켠다. 두 결정은 그대로 둔다 (build 6 메인, B6 작업자 조사와 검토) — 30분 넘게 하나에 수백 MB씩 남는 것도 막을 만하고, 다리가 끄면 그 시간을 아낀다 — 틀리면 잃는 동작은 없고 설명만 바뀐다.
- Ruling: 연결의 놓아주기에서 중계기·다리가 직접 `cleanup_not_confirmed`라고 답하면 같은 연결에 딱 한 번 더 묻고 두 번째 답을 결과로 한다(`release_one` 안: 자동 정리·탭 풀기·정리·`stop`이 모두 같다). 그 밖의 까닭과 엔진이 채운 `cleanup_not_confirmed`(끊긴 소켓, 이유 없는 답), `cleanup_tool_unavailable`에는 다시 묻지 않는다(build 6 작업자, 3회차 S16·S21) — S16: 중계기의 턴 끝 요청이 4초 한도를 넘겨 탭은 닫혔는데 범위가 열려 있었고, 런타임은 같은 짝의 둘째 요청을 이미 끝낸 턴으로 보아 곧 답할 것이다(결정 기록: node_repl은 같은 짝의 두 번째 알림을 무시한다) — 틀리면(둘째 요청도 곧 답하지 않으면) 미확인 연결의 최악 시간이 두 배가 되고 결과는 그대로 미확인이다.
- Ruling: 앱의 엔진 시간 제한을 두 번 묻는 최악값으로 늘렸다: `release` 60→120 s, `stop` 70→130 s, `stop --group` 120→180 s, `release --ended`는 끝난 연결마다 20→35 s(build 6 작업자, 3회차 S16·S21) — 한도가 최악보다 짧으면 끝낼 엔진을 죽여 정리를 건너뛴다(결정 기록 "A2 검토 뒤") — 틀리면 정말 멈춘 엔진을 그만큼 늦게 포기한다.
- Ruling: 두 번째 물음에서야 확인된 연결의 놓아주기는 죽은 다리 기록에서 바로 지우지 않는다. 그 세션은 같은 `release --ended`가 이어서 세션 ID로 브라우저를 불러 풀고, 그것이 확인되면 지운다(손으로 누른 탭 풀기·정리 뒤에는 앱의 자동 정리가 그 세션을 맡는다). 두 번 물은 놓아주기의 탭 개수는 두 답을 더한다 (build 6 메인, B6 2차 검토 뒤) — 두 번째 답은 런타임이 그 턴의 끝을 이미 받았다는 뜻일 뿐일 수 있어, 첫 요청이 확장에서 실제로 실패했으면 남은 점유가 줄도 알림도 없이 숨는다. 세션 ID 풀기는 실제로 브라우저를 부르니 그런 점유를 풀거나 다시 보인다 — 틀리면(두 번째 답이 늘 참이면) 그 드문 경우마다 짧은 확인용 대화가 하나 더 열린다. 엔진 자체가 멈추면 정리 스피너가 늘린 한도(130 s)를 채우고 강제로 한 번 더 기다리는 것(최악 약 260 s)은 받아들인다.
- Ruling: 풀 길 없는 남은 점유(`releasable == false`)는 그 세션을 지금 쥔 연결의 줄에 누를 버튼이 있으면(끝난 연결은 정리, 살아 있는 연결은 탭 풀기) 따로 보이지 않고 카드에도 세지 않는다. 여럿이 쥐면 살아 있는 쪽을 누를 곳으로 본다. 버튼이 꺼진 줄만 쥐고 있으면 점유 줄과 안내를 남긴다(build 7 작업자, 설치본 unified-login 줄) — 사용자 결정 "누를 곳은 한 군데"와 build 6 Ruling을 살아 있는 연결로 넓힌 것이고, 점유 줄이 가리키는 확장 초기화는 모든 연결의 점유를 한꺼번에 푸는 큰 조작인데 실제로는 그 줄의 탭 풀기면 되는 일이다 — 틀리면 그 다리에 열린 범위가 없어 탭 풀기가 "풀 것 없음"으로 답하는 경우에 죽은 기록의 오래된 범위가 지워지지 않고 숨은 채 남는다(그 대화가 끝나 점유가 풀 길이 생기면 자동 정리가 세션 ID로 푼다).
- Ruling: 살아 있는 연결이 쥔 점유는 버튼이 있든 없든 "주인이 사라진 점유" 알림을 보내지 않고, 주인(연결)이 끝나면 그때부터 1분을 센다(build 7 작업자, 설치본 unified-login 줄) — 스레드의 런타임이 범위를 연 채 죽고 같은 스레드가 다시 돈 경우라 주인이 사라진 것이 아니다 — 틀리면 살아 있는 대화가 쥔 점유가 정말 안 풀려도 알림이 없다(버튼이 꺼져 있으면 카드와 줄이 남아 알린다).
- Ruling: 기록의 `owner`가 다리 이름인 중계기(죽은 것)가 적은 세션은 maybe_left에서 `agent: claude`, `needs_user: false`로 본다. `connection_id`와 나머지 필드는 그대로 둔다(build 7 메인 결정·작업자 구현, B7 1차 검토가 찾음) — 그 중계기는 Claude 다리가 연 일회용 대화의 런타임이라 다시 이을 수 없고, 대화가 끝나면 F5대로 앱이 스스로(자동 정리가 세션 ID로 브라우저에 확인하며) 풀어야 한다. 그동안은 Codex 대화로 보여 사람이 눌러야 했고 화면에 "Codex" 꼬리표가 붙었다 — 틀리면 이름을 단 중계기가 Codex 앱이 같은 이름으로 연 대화일 때 사람 클릭 없이 풀릴 수 있다. 다리 이름은 다리가 대화를 열 때만 넣으므로 일어나기 어렵고, 푸는 것은 브라우저가 확인하는 세션 ID 풀기이며 다리가 살아 있으면(`session_live`) 하지 않는다.
- Ruling: 살아 있는 연결이 쥐었다가 주인을 잃은 점유의 알림 시계는 주인을 잃은 첫 look에서 시작하고 그 점유의 `ended_at`을 따로 안 쓴다(`max(ended_at ?? seen, seen)`)(build 7 작업자, 설치본 unified-login 줄) — `ended_at`은 점유를 연 중계기가 끝난 때라 주인이 사라진 때보다 한참 앞설 수 있다 — 틀리면 그 점유가 정말 오래 안 풀렸을 때도 알림이 주인이 사라진 지 1분 뒤에야 간다.
- Ruling: 앱이 이번 실행에서 할 수 있는 만큼 한(정리가 꺼진) 끝난 줄은 누를 곳으로 보지 않는다(build 7 작업자, 설치본 unified-login 줄) — 꺼진 버튼 뒤에 점유를 숨기면 아무도 못 누르는 점유가 남는다 — 틀리면 그 줄이 곧 사라질 때까지 점유 줄이 잠깐 같이 보인다.
- Ruling: 래퍼는 자식(app-server·proxy)을 끄기 전에 host.json에 `status: "stopping"`과 `stopping_at`(ISO UTC)을 먼저 쓰고, 끝나면 지금처럼 `closed`를 쓴다(`stopping_at`은 closed 기록에도 남는다). 엔진은 그 기록을 래퍼가 살아 있고 `stopping_at`부터 30초 안이면 `stopping`, 넘으면 `closed`로 본다(build 8 작업자, 4회차 S2) — 몇 시간 켜 둔 Codex는 host.json의 시각이 오래돼 build 3의 30초 유예가 걸리지 않았고, 끄는 순간 "연결 없이 켜져 있어요" 알림이 갔다 — 틀리면 30초를 넘겨 끝나는 정상 종료는 지금처럼 알림이 뜬다.
- Ruling: 기록이 `ready`인데 래퍼는 살아 있고 자식만 죽었으면 시간 한계 없이 `stopping`으로 본다. 래퍼 pid의 프로세스가 기록보다 늦게 시작했으면 래퍼가 아니라고 본다(build 8 작업자) — 지금 떠 있는 옛 래퍼에도 닿아야 하는데 옛 래퍼는 꺼지는 시각을 남기지 않는다. 래퍼는 자식이 죽으면 0.1초 안에 끝내기로 간다 — 틀리면 자식을 끄다 멈춘 래퍼가 `stopping`으로 남아 "연결 없이 켜짐"을 알리지 않는다.
- Ruling: `restart-codex`도 `stopping` 호스트의 pid를 기다린 뒤(최대 15초) Codex를 연다(build 8 작업자) — 래퍼가 점유를 쥔 채 새 Codex가 뜨면 둘이 겹친다 — 틀리면 다시 켜기가 최대 15초 더 기다린다. 앱의 S10 다시 켜기 길은 아직 `stopping`을 기다리지 않는다(회귀 아님, B8 검토 사소).
- Ruling: 알림을 눌러 이 앱이 앞에 온 뒤 팝오버가 닫히면, 직전 앱(이 앱이 아니고 Dock 아이콘이 있는 앱 가운데 마지막으로 앞에 온 것)에게 앞 자리를 돌려준다. 직전 앱이 없거나, 꺼졌거나, 시스템이 거절하면 이 앱이 숨는다(Cmd-H와 같다). 이 앱이 앞인지는 AppKit과 시스템 둘 다 그럴 때만 인정하고, 검수용 창이 열려 있으면 돌려주지 않는다(build 8 작업자, 4회차 S21) — 닫은 뒤 CUA Bar가 46초 앞에 남아 사람이 칠 곳이 없었고, 사용자는 포커스를 빼앗기는 것을 아주 싫어한다 — 틀리면 일하던 앱이 Dock 아이콘 없는 앱일 때 그 앞의 일반 앱으로 돌아간다.
- Ruling: 앞 자리를 넘긴 지 0.5초 뒤에 다시 보아, 이 앱이 아직 앞이고 이 앱의 것이 하나도 안 보이면 숨는다(build 8 메인, B8 검토 뒤) — 시스템의 `activate(from:options:)`는 승낙만 하고 넘기지 않을 수 있다(SDK 설명) — 틀리면 그 0.5초 사이에 사람이 CUA Bar를 다시 고른 드문 경우 앱이 숨고, 다음 아이콘 누르기로 다시 열린다.
- Ruling: 다리가 띄운 런타임의 중계기는 조작 기록 줄마다 그 다리 이름(`owner`)을 맨 뒤 키로 적고, 이름이 없으면 키를 두지 않는다. 엔진은 줄의 주인을 목록 연결의 writer → `bridge-` writer → `owner` → 다리 기록의 세션 → Codex 순으로 정한다(build 8 작업자, 4회차 S23) — 끝난 Claude 대화의 조작이 연결과 다리 기록이 사라지면 기록 탭에 'Codex'로 떨어졌다 — 틀리면 이름 없는 Claude 중계기의 줄은 옛 줄처럼 세션이 다리 기록에 남은 동안만 Claude로 보인다.
- Ruling: 끝난 대화의 조작 줄 폴더는 이번 판에서 남기지 않는다(기록 탭에서 '—')(build 8 메인) — 줄에 폴더를 더하면 진단 복사 글에 경로가 들어가는지까지 다시 봐야 해서, 밤사이 고치고 검수까지 끝내려고 에이전트 이름만 고쳤다 — 틀리면 끝난 대화의 조작에서 폴더를 볼 수 없다(다음 판 후보).
- Ruling: 되살아난 빈 런타임을 나이로만 가르지 않는다. 다리 이름을 단 중계기가 켜질 때 그 다리가 돌고 있는지 한 번 보고 `relay.json`에 `owner_running`(true/false, 확인하지 못하면 null, 이름이 없으면 키 없음)으로 적는다. 엔진은 `owner_running`이 JSON false인 중계기를 — 다리가 지금 안 돌고 기록이 없고 불린 적·도는 호출·열린 범위·조작 줄이 없다는 조건은 그대로 두고 — 다리 시작과의 간격과 상관없이 되살아난 빈 런타임으로 본다. true·null·키 없음(옛 중계기)은 build 6의 120초 규칙을 따른다 (build 9 작업자, 4회차 S4: 18초 만에 끝난 대화의 런타임을 Codex가 다시 켜 '끝난 연결'이 3분 남음) — 다리가 정리하며 자기 런타임을 끈 뒤에 Codex가 그 스레드의 런타임을 다시 켠다. 그 중계기는 켜질 때 다리가 이미 없었다 — 틀리면 `ps`가 다른 까닭으로 "프로세스 없음"처럼 답하는 드문 경우에 비정상으로 끝난 다리의 누수가 보이지 않는다.
- Ruling: 주인 확인은 `ps -p <주인 pid>` 한 건을 따로 부르고, 종료 코드 1에 stdout·stderr가 모두 비면 `false`, ps가 stderr로 까닭을 말하거나 그 pid 줄이 없거나 그 밖의 실패는 `null`이다. 중계기의 기록·중계는 이 확인이 실패해도 그대로 돈다 (build 9 작업자, B9 검토 뒤 메인이 좁힘) — 틀린 `false`는 보여야 할 누수를 숨기고 틀린 `null`은 예전 판정을 둘 뿐이라 모를 때는 `null`이 안전하다 — 틀리면 그 드문 경우 `false`가 되어 누수가 숨는다.
- Ruling: 다리의 `log_stderr`는 닫힌 stderr(파이프·기술자·파일 객체)에서 예외를 내지 않는다 (build 9 작업자, 4회차 Q3 조사) — Claude가 다리를 멈춘 뒤 82ms에 stdio를 닫고, 정리 중의 로그(`owned_thread_unsubscribe_confirmed`)가 던지면 확인된 일을 미확인으로 적고 연결 닫기에 이르지 못한다 — 틀리면 잃는 동작은 없다.
- Ruling: 릴리스를 ad-hoc 서명 zip에서 Developer ID 서명 dmg로 바꾼다. 앱과 dmg를 각각 공증해 티켓을 붙이고, 모든 빌드를 hardened runtime으로 서명하며 예외는 Apple Events 하나다(R6 바꿈, 2026-10-21 메인) — 사용자가 Apple 개발자 가입을 알렸고("나 애플 개발자 가입함."), 공증한 앱은 '그래도 열기' 없이 열린다. restart-codex는 osascript로 Codex에 종료를 보내므로 그 권한을 둔다 — 틀리면 릴리스마다 공증 대기가 몇 분 늘고, 종료 요청에 권한이 필요 없었다면 쓰지 않는 권한 한 줄이 남는다.
- Ruling: 받는 곳을 GitHub 릴리스와 함께 cua.chenjing.org에도 둔다. Cloudflare Worker가 dmg·SHA256SUMS·install.sh를 정적 파일로 내주고 첫 화면, `/download`, `/install`(에이전트용 안내), `/version`을 답한다. 한 줄 설치는 SHA-256과 서명한 팀(S3KC8R8VDL)을 확인한 뒤 깔고, 같거나 새 판이 있으면 받지 않는다 (사용자 2026-10-21 "그럼 ul처럼 해봐") — 통합 로그인처럼 링크 하나, 터미널 한 줄, 에이전트용 안내로 받게 한다 — 틀리면 릴리스마다 Worker를 한 번 더 올리는 수고가 남는다.
- Ruling: 받는 곳 첫 주소(`/`)는 설명 페이지 없이 `/download`와 똑같이 답한다. 맥 브라우저에는 바로 dmg를 넘기고, 휴대폰·curl·에이전트에는 맥에서 열라는 줄과 터미널 한 줄만 준다 (사용자 2026-10-21 "왜 바로 다운이 안되고, 설명이 붙냐?") — 통합 로그인의 `/download`가 그렇게 하고, 사용자는 링크를 열면 바로 받아지길 바랐다 — 틀리면 판과 SHA-256을 한 화면에서 보는 곳이 없어진다(README, `/version`, `SHA256SUMS.txt`에는 남는다).
- Ruling: 플러그인의 setup 스킬을 지운다. 설치·설정·고치기는 CUA Bar가 하고, 앱 없이 쓸 때는 플러그인 README의 `setup.sh setup` 한 줄로 한다. 진단 순서와 금지 사항(Codex를 대신 끄지 않기, 다른 엔진·프록시·권한 변경으로 대신하지 않기)은 computer-use 스킬로 옮긴다 (사용자 2026-10-21 "필요없는건 지워") — 앱이 같은 일을 하므로 스킬은 대화마다 설명 한 줄만 차지하고 쓰일 일이 거의 없다 — 틀리면 앱 없이 쓰는 사람이 Claude에게 설정을 맡기지 못하고 명령을 직접 친다.
- Ruling: 누른 뒤 다시 묻는 상자를 모두 없앤다 — 카드의 다시 켜기, 일하는 연결의 탭 풀기, R15의 "한 번 더 풀어 볼까요?", 앱 지우기. 끊기는 것은 누르기 전에 보인다(다시 켜기는 버튼 옆 글, 탭 풀기·앱 지우기는 마우스를 올리면). R15의 첫 거절은 바로 그 줄에 "작업이 끝나지 않아 못 풀었어요"를 보이고, 그 줄의 탭 풀기가 다시 해 본다. 상태가 없거나 대상이 목록에서 사라지면 돌지 않고 이유를 한 줄 보이는 규칙은 남긴다(0.8.4 메인, 위 R15·"일하는 중인 연결을 놓아줄 때는 한 번 묻는다"·"묻는 것은 누른 곳에서 묻는다"를 바꿈) — 사용자 2026-10-25 "이렇게 한번더 레이아웃 바꾸면서 재확인 받는게 맞는 방법인지 모르겠네", "저런식으로 뜨는 ux가 하나가 아닐텐데": 질문 상자가 끼어들며 레이아웃이 밀렸고, 누르는 것이 곧 동의다 — 틀리면 일하는 연결의 탭 풀기나 앱 지우기를 잘못 한 번 누른 것이 바로 실행된다(앱 지우기는 앱을 다시 켜면 다시 깔린다).
- Ruling: R1(누르기 전에는 끄지 않는다)의 예외로, 잠금 해제 실패 뒤 Codex CUA 서비스는 묻지 않고 끈다. Codex 앱과 AI는 여전히 끄지 않는다 (0.8.5 메인, 사용자 2026-10-25 "예. 최대 5번까지 시도하게") — 잠긴 동안에는 사람이 누를 수 없고, 서비스는 다음 호출 때 macOS가 다시 켠다 — 틀리면 그 순간 서비스를 쓰려던 Codex 자체 작업이 한 번 실패한다(도는 호출이 없을 때만 끄므로 드물다).
- Ruling: "최대 5번"을 잠금 한 번에 CUA 서비스를 다섯 번까지 다시 켜는 것과 cuabar 스킬이 30초쯤 뒤 다섯 번까지 다시 부르는 것으로 읽었다. 처음에는 서비스의 시도 두 번이 다 쓰였을 때만 다시 켰는데, 그러면 다시 켜기 한 번에 다시 부르기가 두 번 들어 다섯 번 다시 부르는 동안 세 번만 켜지고 다섯 번째 뒤의 알림도 오지 않아서 실패 한 번에 한 번 켜는 것(R24)으로 바꿨다 (0.8.5 메인) — 틀리면(사용자가 자동 잠금 해제를 더 많이 시도하길 바랐다면) 잠금마다 시도가 다섯 번 덜 된다.
- Ruling: 엔진이 쓴 기록 줄(writer `engine-<pid>-<시작>`)은 기록 탭에 "CUA Bar · CUA 서비스 다시 켜기"로 보이고, 연결·화면 사용·작업 중 판단에는 넣지 않는다. R7·R18에 잠금 해제 복구와 엔진 줄을 더했다 (0.8.5 메인) — 엔진이 그 줄로 이번 잠금의 횟수를 세고, 사람도 무엇이 일어났는지 볼 수 있게 — 틀리면 기록 탭에 줄이 하나씩 더 보인다.
- Ruling: "auto 모드에서 허용 규칙이 없을 때"의 안내를 기본 모드가 bypassPermissions가 아닌 모든 경우로 넓혔다(R26) (0.8.6 메인) — 앱이 읽을 수 있는 것은 settings의 defaultMode뿐이라 auto만 고르면 Shift+Tab으로 auto를 켜는 사람에게는 보이지 않고, 문제가 아닌 '안내' 줄이라 다른 모드에서도 해가 없다 — 틀리면 auto를 쓰지 않는 사람의 점검 탭에도 안내 한 줄이 보인다.
- Ruling: 옛 이름 검사가 프로젝트 폴더를 볼 때 macOS가 허락을 묻는 홈의 `Desktop`·`Documents`·`Downloads`·`Library`·`.Trash` 안과 링크를 거치는 폴더는 건너뛴다(R25) (0.8.6 메인) — 앱이 그 안의 파일을 건드리면 허락 창이 떠서 사람의 일을 막고, 이 Mac에도 그런 프로젝트가 둘 있다 — 틀리면 그 폴더들에 남은 옛 이름 규칙·훅은 점검 탭에 나오지 않는다(사용자 설정의 `mcp__cuabar` 허용 안내는 그대로 나온다).
- Ruling: `browser_blocked`를 확장 쪽 이유(`reasonsPointingAtTheExtension`)에 넣지 않았다(F10) (0.8.7 메인, 2026-10-28 사용자 요청) — 막는 쪽이 Codex라 확장 초기화로 풀리지 않고, 안내를 열면 사용자가 헛수고를 한다 — 틀리면 Codex가 막지 않는 때에도 같은 이유로 끝난 탭 풀기에 안내가 열리지 않는다.
- Ruling: Codex의 접근 통제는 우회하지 않는다 (0.8.7 메인, 2026-10-28 사용자 요청) — 허락에 쓰는 환경값(`BROWSER_USE_ACCESS_EXECUTOR_ID` 따위)을 넣지 않고 허락 통로에 직접 말하지도 않는다. 브리지는 이 오류를 담은 js 결과 끝에 사실만 적은 영어 한 줄을 덧붙이고, 스킬은 한국어로 같은 뜻을 적는다 — 틀리면 AI가 오류 글만 보고 Work 설정이나 확장을 탓한다.
- Ruling: 한 번에 여러 세션을 풀다가 `browser_blocked`가 나오면 엔진도 남은 세션에 브라우저 호출을 하지 않고 같은 이유로 답한다 (0.8.7 메인) — 같은 대화가 같은 거절을 받으므로 — 틀리면 일부 세션에는 실제 이유 대신 이 이유가 적힌다.
- Ruling: 26.1023의 새 번들 정의(`--import` 한 줄 앞붙음)를 0.8.7부터 받아들인다(R29) (0.8.7 메인, 2026-10-28 사용자 요청) — 0.8.6까지는 `not_bundled`로 거절해 중계기 없이 켜졌고 기록 탭과 Codex 대화 연결이 비었다. 이전 판 래퍼로 켜진 호스트는 `restart_adds_relay`가 `true`라 다시 켜면 붙는다 — 틀리면 새 모양에서 중계기가 정의를 잘못 만들어 런타임이 켜지지 않을 수 있어, 계획은 CLI가 만든 표를 다시 읽어 맞춰 보고 맞지 않으면 중계기 없이 켠다.
- Ruling: `browser_blocked` 뒤 자동 정리는 세션(`lease:`)만 멈추고 끝난 연결(`connection:`)은 계속한다 (0.8.7 메인, 2026-10-28 사용자 요청) — 끝난 연결의 놓아주기는 연결 자신의 제어 소켓으로 하고 브라우저를 거치지 않는다(`release_one`). 다만 `release --ended`는 연결 뒤에 세션도 브라우저로 풀어 보므로, 막힌 뒤에는 앱이 `--connections-only`를 붙여 연결만 시킨다 — 틀리면 막힌 뒤에도 연결 정리가 세션 한 번씩 더 시도하게 된다.
